# Communication and Language

Применяется во всех проектах. Язык вывода зависит от контекста.

## Язык
- Ответы в чате: русский, простыми словами. Короткие предложения, частые слова.
  Технический термин оставляй, но поясняй просто.
- Комментарии в коде: только русский.
- Commit-сообщения и описания PR/MR: только русский.
- Документация (README, docs, design-заметки): только русский.
- Идентификаторы (классы, методы, переменные), имена веток, Jira-ID, ключи конфигов: английский.

## Логи
Формат ниже - из командной конвенции, обязателен в профиле **work** (правило 10). В профиле personal
это просто хорошая практика: параметризация и отсутствие PII важны везде, коды SPR не нужны.

- Сообщения логов: на русском (согласуется с примерами SPR-903/904 в конвенции).
- Параметризированная подстановка, без конкатенации (SPR-902):
  `log.info("Заказ {} обработан", orderId)`, а не `log.info("Заказ " + orderId + " ...")`.
- Не логировать PII/секреты (SPR-907); если надо - маскировать всё, кроме первого/последнего символа.

## Любой текст
Действует для чата, комментариев, коммитов, документов и отчётов.

- Без воды: каждое предложение - факт, решение или причина. Абзац, который можно удалить без потери
  смысла, удалить. Без вступлений-пересказов, итоговых "таким образом", "важно отметить", "это не X, а Y".
- Имена систем, классов, кодов и числа - конкретные, а не "компонент", "модуль", "значительно".
- Только символы с клавиатуры. Без эмодзи, рамок и декоративных разделителей. Замены:

  | Не писать | Писать |
  |---|---|
  | стрелки `→ ← ⇒ ↔` | `->`, `<-`, `=>`, `<->` или слова |
  | тире `—`, `–` | дефис `-` или перестроить предложение |
  | кавычки `«» “” „`, апостроф `’` | `""`, `'` |
  | `…`, `•`, `·` | `...`, `-`, запятая |
  | `✓ ✗ ≤ ≥ ≠ ×` | `[x]`, `[ ]`, `<=`, `>=`, `!=`, `x` |
  | неразрывный и нулевой пробел | обычный пробел |

- Русский; английское слово только там, где нет устоявшегося русского. Идентификаторы и пути - в `inline code`.
- Чат: GitHub-flavored markdown (списки, таблицы, блоки кода).
- Список того, что сделать, - с галочками `- [ ]` (кроме описаний задач Jira). Второстепенное в документе -
  в `<details>`.
- Комментарии в коде: объясняй "почему", а не "что". Не дублируй код словами. Javadoc - только там, где
  добавляет смысл. Следуй java-convention.
- Документ, отчёт, анализ, план, README, ADR, описание задачи: сначала загрузи скил `writing`.

## Ширина строки
- Мягкий лимит ~140 символов для кода, комментариев и документации. Не делать слишком
  узкую колонку (не переносить ради переноса).
- Если у проекта есть более строгая конвенция - она важнее (rule 05). Напр. каноническая
  java-convention: preferred 90, hard limit 120 - для Java соблюдать её, а не 140.
