# Workflow — как работать каждый день

Практические сценарии под текущий конфиг. Все команды и скилы уже установлены глобально
(симлинки в `~/.claude/`), правила подключены через `~/.claude/CLAUDE.md`.

Память:
- Чат — русский, простыми словами. Комментарии в коде, commit-сообщения, документация, логи — русский.
- TDD — iron-law (падающий тест до прод-кода). Разделение по умолчанию (rule 06): **что проверять** — ты
  (список случаев, подтверждаешь и добавляешь ≥1 свой), **как** — Claude (код теста).
- Rule 08: при отладке и проектировании агент сначала спросит твою гипотезу / первый вариант.

## Шпаргалка: команды и что делать самому

Правило: **думать — сам, набирать — агент.** Рутина (boilerplate, форматирование, git, конфиг, Sonar-правки)
уходит агенту без угрызений; гипотеза, вариант решения, случаи для тестов, первый проход по чужому MR — твои.

| Ситуация | Что делаю сам (30 с – 10 мин) | Команда | Что отдаю агенту |
|---|---|---|---|
| Баг, «не работает», трейс | одна фраза «думаю, причина в …» (rule 08 спросит) | `/fix` | подтверждение причины, тест на баг, минимальная правка |
| Новая фича / доработка | 3 строки: как бы сделал я; 3–5 случаев для тестов | `/feature` (план → одобрение → TDD) | план, код, тесты по моим случаям |
| Большая фича на несколько контекстов | то же + критерий «готово» | `/task` | фазы, подагенты, артефакты `.ai/` |
| Только план / выбор подхода | мой первый вариант (1–3 строки) | `/plan`, `/arch` | варианты, trade-off, план; сверка с моим |
| Принято архитектурное решение | суть решения одной фразой, минусы | `/adr` | текст ADR по шаблону репо, без слопа |
| Задача/подзадача в Jira | что и зачем, 1–2 случая Дано/Когда/Тогда | `/jira` | формат, остальные сценарии, чек-лист |
| Ревью своих изменений | прочитать свой дифф, назвать 1 слабое место | `/review` | список находок по стеку |
| Ревью MR коллеги | 10 мин свой проход, 1–3 находки записать | `/review-mr` | полный список с кодами, вопросы автору; сверить со своими |
| Поправил руками то, что написал агент | — | `/reflect` | `reflect: N`, один урок в память/правило |
| Незнакомый репозиторий | 15 мин руками: структура, точки входа | `/onboard` | `CLAUDE.md`, карта проекта |
| Хочу понять технологию/паттерн | сформулировать, что именно непонятно | `/explain` | объяснение; потом пересказать своими словами |
| Проверка конвенции перед MR | — | `/convention-check` | список нарушений с кодами |
| Тесты к готовому коду | список случаев (что может сломаться) | `/test` | код тестов, фикстуры, testcontainers |

Отдавать полностью: boilerplate/DTO/мапперы, Sonar «fix this», оформление Jira/ADR по моему черновику,
git-операции, Spring-конфиг/YAML, поиск по незнакомому API, суммаризация ресёрча.

**Про тесты — прямой ответ.** Да, код тестов пусть пишет Claude: это рутина (моки, фикстуры, testcontainers).
Не отдавать — *придумывание случаев*: «что здесь может сломаться?» — это и есть понимание задачи, а не отдельный
навык «писать тесты». Практика на 2 минуты перед каждым тестом: три строки — обычный путь / граница (пусто, дубль,
максимум) / ошибка (зависимость упала, невалидный вход). Если не можешь назвать ни одного случая — ты не понял
задачу; это сигнал вернуться к плану, а не к агенту. Лень придумывать — нормально; поэтому Claude предлагает список,
а ты добавляешь один свой — этого достаточно, чтобы навык не ушёл. «Сложно понять, как проверить» — спрашивай
агента *как* (Testcontainers? WireMock? какой уровень?), но не *что*.

Раз в месяц: `python3 scripts/audit/extract.py && python3 scripts/audit/report_phase1.py` → 5 индикаторов из
`docs/audit-2026-08/05-growth.md`.

## Сценарий 1 — Новая фича + план

1. Проверь, что в проекте есть заполненный `CLAUDE.md`. Новый проект → `/onboard`.
2. Включи Plan Mode (Shift+Tab) для нетривиальной задачи.
3. `/feature <описание или Jira-ID>` — определит стек, подгрузит скилы
   (`java-service-convention`, `testing` и др.), разметит затронутые слои, задаст уточняющие
   вопросы, выдаст план. Если нужен только план без реализации — `/plan`.
4. Согласуй план (ExitPlanMode).
5. Реализация пошагово по TDD: RED → GREEN → REFACTOR. На RED — выбор авторства теста.
6. Перед финализацией — `/review`.

Когда что: `/feature` — фича/значимое изменение; `/fix` — мелкий баг/правка; `/plan` — только план.

## Сценарий 2 — Рефакторинг + самостоятельное ревью

Цель: рефакторить по java-convention, со свежей документацией и лучшими практиками под конкретный случай.

1. Контекст: `java-service-convention` подхватится авто на `.java`. При нужде —
   `spring-best-practices` (Spring-механики) или `java-patterns` (паттерны/SOLID).
2. Актуальная документация: `context7` MCP (`resolve-library-id` → `query-docs`) для свежих
   доков Spring/библиотек. Не полагайся на память модели.
3. Рефактори мелкими коммитами:
   - rule 03 — не мешать функциональные правки со стилевыми в одном коммите;
   - rule 05 — не приводить к единому стилю частично мигрированный код в той же правке
     (предложи отдельной задачей).
4. Самопроверка:
   - `/convention-check` — быстрый проход по конвенции (дёшево по токенам);
   - `/review` → агент `java-reviewer` — глубокое ревью (баги, риски, конвенция);
   - если затронута БД/схема — агент `migration-reviewer`.
5. TDD: тесты остаются зелёными; на изменённое поведение — тест.

## Сценарий 3 — Поиск альтернатив, выбор подхода/технологии

1. `/arch <вопрос>` — варианты дизайна с trade-offs, границами контекстов, рисками
   (для глубокого reasoning — модель Opus).
2. `/explain <тема>` — глубокий разбор конкретной технологии/паттерна (подробный тон).
3. Свежие данные: `context7` — актуальные возможности библиотек; skill `deep-research` —
   мультиисточниковое сравнение для крупного выбора.
4. Узкие скилы под решение: `java-patterns` (паттерн), `integration-patterns` (интеграции),
   `jpa-db-review` (БД).
5. Решение зафиксируй в `CLAUDE.md` проекта или в ADR/`SPEC.md` → реализуй по Сценарию 1.

## Сценарий 4 — Ревью MR коллеги

1. `/review-mr <id|url>` — через `glab`, без checkout (тянет дифф vs `master` и метаданные:
   автор, title, ветка, ссылка). Без аргумента — текущая ветка (fallback на `git diff`).
2. Приоритет №1 — каноническая java-convention; анализ делегируется агенту `java-reviewer`.
3. Вывод на русском в формате «3 части + код конвенции» (`LANG-410`, `SPR-902` ...),
   сначала нарушения конвенции.
4. Ревью сохраняется: `<каталог ревью из ~/.claude/workspace.md>/<project>/<дата>__<ветка>__<автор>.md`
   (папка на каждый проект, в шапке — автор MR, ветка, дата, база).
5. В чат — краткая сводка (счётчик по severity) и путь к файлу.
