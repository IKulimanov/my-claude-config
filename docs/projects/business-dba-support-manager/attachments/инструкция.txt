При получении ошибок по свободному пространству в TS

К примеру, 
DB: loading: PS_SERVICEDATA_PGW_072026 - 101182 MB

1. Подключаемся к БД loading
2. Находим тбс PS_SERVICEDATA_PGW_072026
3. Смотрим на каком диске и каким форматом созданы датафайлы:
   +DATA006/loading/ps_pgwsvc_202607_01.dbf
4. Добавляем следующую: 
	ALTER TABLESPACE PS_SERVICEDATA_PGW_072026
	ADD DATAFILE '+DATA006/loading/ps_pgwsvc_202607_02.dbf'
	SIZE 10M
	AUTOEXTEND ON NEXT 100M MAXSIZE UNLIMITED;
	
5. При заполнении ASM диска на +DATA006, только по разрешению ответственного за архивацию и удаление данных можно переправить датафайл на другой диск
6. На месячных табличных пространствах добавить столько датафайлов, сколько в предыдущем месяце

При авариях репликации PostgreSQL:

Проверки репликации на стороне PostgreSQL:
Rep PGDWH,Rep KAMAILIO находятся в бд PGDWH на 172.27.129.54:5432 
Rep MFS, Rep PGDWH_GT в PGDWH_GT на 172.27.208.100:7542
Rep PGDWH_CS в DWH_CS на 172.27.205.105:5432


1. Подключаемся к БД по необходимому адресу
2. Смотрим какая проблема возникла с репликацией в таблице zabbix.mon_rep_pgdwh

  1) Если LAGGING, то необходимо проверить 
     1.1 Долгие транзакции в бд, кроме процессов постгреса и активных сессий, работающих меньше 6 часов убиваем так:
         select pg_terminate_backend(pid)
         Подождать минут 20 и проверить таблицу zabbix.mon_rep_pgdwh
	 1.2 Логи базы, если пишет дублируются ID, то удалить эту запись и перезалить таблицу, как в 3.3*
  2) Если NO_ACTIVITY, то подключаемся к серверу и смотрим на логи БД, обычно выходит при добавлении новых колонок на источнике.
     a) Подключаемся к источнику БД, адрес базы узнаем через:
	    select subconninfo from pg_subscription
        where subname ='название проблемного слота'
     b) Находим новое поле в БД
	 с) Добавляем новое поле в приемнике (PGDWH)
	 d) Проверить статус слота в zabbix.mon_rep_pgdwh
  3) Если SLOT_MISSING, то 
     3.1 надо узнать причину почему пропал слот:
     a) Заполнения диска
	 Понять причину заполнения, при необходимости попросить сис.админов расширить диск
	 b) Рестарт Patroni или смена мастера, падение БД 
	 При необходимости вернуть мастера, поднять базу
     с) Долгие транзакции, блокирующие таблицу на стороне источника (незакрытые транзакции, vacuum)
	 При необходимости удаления данных или вакуумирования, надо убрать таблицу с репликации
	 
	 3.2 Пересоздать subscription на стороне приемника:
	 
	    К примеру, проблемный слот subs_dts_tables:
	    ALTER SUBSCRIPTION subs_dts_tables DISABLE;
 		ALTER SUBSCRIPTION subs_dts_tables SET (slot_name=NONE);
 		DROP  SUBSCRIPTION subs_dts_tables  ;
 
 		CREATE   SUBSCRIPTION subs_dts_tables CONNECTION 'host=172.27.204.134 dbname=dts port=5432 user=pglogical password=пароль' PUBLICATION dts_tables_for_pgdwh  
		WITH (synchronous_commit = 'off', copy_data = false); 
		
     3.3 Перепроверить таблицы на рассинхрон, необходимые данные пролить
	 
	    Скрипт для примера:
		a) Проверить по кол-ву данных:
		   select count(*) from public.accounts_transaction union all  select count(*) from public_fdw.accounts_transaction;
        b) При несовпадении найти ID, ограничив по времени:
		
			CREATE TABLE TEMP AS SELECT ID FROM (

			SELECT *
			FROM CREDIT_PROD_FDW.ACCOUNTS_TRANSACTION
			WHERE CDT >= '2025-01-01'
			AND CDT <  '2026-01-01'
			EXCEPT
			SELECT *
			FROM CREDIT_PROD.ACCOUNTS_TRANSACTION
			WHERE CDT >= '2025-01-01'
			AND CDT <  '2026-01-01');

		с) Перезалить 
			DELETE FROM CREDIT_PROD.ACCOUNTS_TRANSACTION
			WHERE ID IN (SELECT ID FROM TEMP);

			INSERT INTO CREDIT_PROD.ACCOUNTS_TRANSACTION
			SELECT *
			FROM CREDIT_PROD_FDW.ACCOUNTS_TRANSACTION
			WHERE ID IN (SELECT ID FROM TEMP);

	
3. Проверяем таблицу zabbix.mon_rep_pgdwh, везде должно быть 'OK'

Статус GG по алармам проверять на серверах
Rep NURSTB - 172.27.129.59, 
Rep SLRDB - 172.27.128.144, 
Rep SP - 172.27.129.216, 
Rep SDGT - 172.27.204.65, 
Rep DWH - 172.27.129.151, 
Rep NDWH - 172.27.129.11


1. Rep NURSTB
	1.1 Подключиться к бд NURSTB на 172.27.129.59
    1.2 Остановить накат логов в базе:
		ALTER DATABASE RECOVER MANAGED STANDBY DATABASE CANCEL;
		RECOVER STANDBY DATABASE UNTIL CANCEL; (написать CANCEL после запуска скрипта)
	1.3 Открыть базу:
		ALTER DATABASE OPEN READ ONLY;
	1.4 Найти директорию GG и зайти в нее
	    cd /u01/app/oracle/product/ogg
		./ggsci
	1.5 В большинстве случаев падает экстракт EXT_ST1, достаточно его просто запустить 
	    start EXT_ST1
	1.6 Перезапустить БД и открыть ее в режиме чтения:
		shut immediate; 
		startup mount;
		alter database open read only;
	1.7 Запустить накат логов:
		ALTER DATABASE RECOVER MANAGED STANDBY DATABASE DISCONNECT;
	1.8 Проверить GG на статус RUNNING и логи бд на накат логов командой log

2. Для всех остальных репликации действует одна схема:
	2.1 Зайти на соответствующий сервер
	2.2 Найти директорию GG и посмотреть с каким репликатом или экстрактом проблема:
	    cd /u01/app/oracle/product/ogg
		./ggsci
	    GGSCI 1> info all
	2.3 Основные статусы:
		RUNNING, но растет Time Since Chkpt - подождать пока применятся trail-файлы и все обнулится
		STOPPED - если должен работать, то запустить START REPLICAT
		ABENDED - проверить логи VIEW REPORT, устранить причину и запустить снова
		STARTING - подождать пока запустится, если зависает - смотреть на логи
		STOPPING - подождать пока завершится, если долго идет - кильнуть процесс 
		KILLED - проверить причину и при необходимости запустить снова
		
	Обычно в статусе ABENDED возникают следующие проблемы:
		a) Отстуствие колонки или изменение типа - необходимо синхронизировать структуру таблицы
		b) Недостаточно места в TS - добавить датафайл в TS
		с) Повреждение trail-файл - применить следующий файл и проверить данные таблиц внутри данного репликата, при необходимости актуализировать данные
	2.4 После устранения проблем, аларм сходит в течении 30мин
