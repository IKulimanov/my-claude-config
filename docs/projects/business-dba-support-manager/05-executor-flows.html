Исполнитель-агент: развертывание, пароли, выполнение, жизненный цикл

Проект dba-ops-assistant. Статус: исследование, не принятое решение. 0. Участники, обозначения, что где лежит

Вводные

  • Исполнитель работает как агент на хосте СУБД (или на выделенной ВМ в сегменте СУБД — тогда к базам он ходит по сети). Входящих соединений в агент нет: все взаимодействия начинает он сам, наружу — только HTTPS к Core.
  • На хосте нет Vault. Vault есть только у Core (если инфраструктура его даст — это открытый вопрос).
  • CI/CD до хостов не дотягивается: первичная установка — руками DBA один раз, дальше агент обновляется сам.
  • Парк разнородный: разные версии Oracle, PostgreSQL, MySQL; часть хостов на Solaris (возможно, SPARC — тогда агент только на Java 8).

Участники

УчастникРоль
DBA-администраторЧеловек. Ставит агент на хост один раз, заводит пароли баз, отзывает агента, подтверждает break-glass.

CoreЦентральный сервис (business-dba-ops-assistant). Единственная точка, куда ходит агент: регистрация, lease, ключи или расшифровка, задания, отчёты, обновления, журнал.
VaultХранилище секретов у Core. Ветка A1 — хранит ключ данных агента K_agent; ветка A2 — Transit-ключ, приватная часть которого Vault не покидает.
Хост СУБДСервер, на котором работают СУБД и агент. Две учётки ОС: root (устанавливает и обновляет) и dbagent (под ней работает агент; без пароля, без shell, без sudo).
Агент = два процессаdbagent-updater — под root, по таймеру: скачивает, проверяет и раскладывает новые версии, перезапускает worker. dbagent (worker) — под dbagent: lease, пароли, задания, выполнение SQL. Worker не имеет права записи в каталог с кодом.
СУБДЦелевая база (Oracle, PostgreSQL, MySQL). В ней есть учётка агента dba_agent с ограниченными привилегиями (или OS-аутентификация — профиль os).

Почему так разложено. Ни один компонент в одиночку не восстанавливает пароль базы: хосту нужен Core (ключ или расшифровка), Core в ветке A1 — шифртекст с хоста. Код агента принадлежит root, а работает агент под dbagent: захвативший dbagent не может подменить код и закрепиться. Ключ подписи релизов лежит вне Core: захвативший Core не может подсунуть агентам свой код.

Обозначения на схемах

  • Стрелка со сплошной линией — запрос; пунктирная — ответ. Все запросы агента к Core идут по HTTPS и подписаны ключом агента (раздел 2.4), это на схемах не повторяется.
  • alt / else — развилка (например, ветка A1 и ветка A2), loop — повторение, opt — необязательный шаг.
  • Имена эндпоинтов Core — эскиз, для наглядности; окончательный контракт зависит от ADR-002.

1. Развертывание и обновление агента

Задача раздела: агент должен появиться на 100+ хостах, куда не ходит CI/CD, и потом обновляться без участия DBA. Решение: DBA ставит агент один раз, дальше root-процесс dbagent-updater сам забирает подписанные версии из Core.

1.1. Первичная установка и регистрация (один раз на хост)

sequenceDiagram
    autonumber
    actor DBA as DBA-администратор
    participant UI as Cockpit UI
    participant Core
    participant Host as Хост СУБД (root)
    participant Agent as agent enroll
    DBA->>UI: создать карточку агента (hostname, группа обновления)
    UI->>Core: POST /agents {hostname}
    Core-->>UI: enrollment-token (TTL 15 минут, одноразовый)
    UI-->>DBA: показать токен один раз
    DBA->>Host: скопировать tarball, запустить install.sh под root
    Note over Host: useradd dbagent (без пароля и shell), каталоги и права, юнит systemd или манифест SMF, таймер updater
    DBA->>Agent: agent enroll --core https://core.company --token T
    Agent->>Agent: сгенерировать ключ подписи (ECDSA P-256) и ключ обёртки (RSA-3072), записать identity.json 0600
    Agent->>Core: POST /agents/enroll {token, hostname, pubSign, pubWrap}
    Core->>Core: токен жив и не использован, hostname совпадает: сохранить ключи, погасить токен
    Core-->>Agent: {agentId}
    DBA->>Host: включить сервисы: systemctl enable --now dbagent dbagent-updater.timer

Схема 1a. Установка и регистрация агента.

Что делает install.sh. Идемпотентный скрипт под root: создаёт группу и учётку dbagent (useradd -r -s /usr/sbin/nologin, на Solaris -s /bin/false; passwd -l), раскладывает каталоги с правами из таблицы раздела 0, ставит юнит systemd (User=dbagent, Restart=always, RestartForceExitStatus=75, LimitCORE=0) или манифест SMF (method_credential user='dbagent', duration=child), таймер updater (systemd timer, SMF periodic на Solaris 11.3+, cron root на старых системах). Пути ORACLE_HOME/ORACLE_SID/JAVA_HOME берёт из /etc/oratab и параметров.

Что такое enrollment-token. 32 случайных байта, живёт 15 минут, используется один раз, привязан к hostname. Он не расшифровывает ничего — это только право один раз зарегистрировать публичные ключи агента. Утёкший токен через 15 минут бесполезен; повторная регистрация под тем же hostname видна в журнале Core и требует явного разрешения DBA.

Что делает DBA один раз, а что — никогда больше. Один раз: карточка агента, установка, регистрация, заведение паролей баз (раздел 2). Дальше DBA не трогает хост ради обновлений: версии приходят через updater.

1.2. Цикл обновления

flowchart TD

Схема 1b. Самообновление: updater под root, worker под dbagent.

Кто и что решает

  • Core — «желаемое состояние». На GET /agents/me/desired Core отвечает не «последней версией для всех», а версией, назначенной группе агента: сначала canary (несколько некритичных хостов), потом остальные. Rollout можно остановить одной операцией в Cockpit. Ответ: {version, artifactUrl, sha256, signature, downgrade, config}.
  • Артефакты раздаёт Core. Агент видит только Core, поэтому Core проксирует Nexus/Artifactory: GET /artifacts/agent/<version>.
  • Подпись — не у Core. Релизный пайплайн подписывает артефакт ключом, которого у Core нет (HSM или офлайн-ключ). Публичный ключ вшит в updater. Смысл: захват Core даёт возможность раздать всем агентам любую версию — но не подписать её; агенты откажутся. Иначе Core стал бы точкой удалённого выполнения кода на всех хостах СУБД. Для Java 8 без сторонних библиотек: RSA-SHA256 или ECDSA P-256 через JCA, либо подписанный jarsigner jar с проверкой цепочки против вшитого сертификата. Ed25519 в JDK 8 нет.
  • Anti-rollback. Updater хранит максимальную установленную версию и не ставит более старую, если манифест не содержит подписанного флага downgrade: true. Так нельзя откатить агентов на версию с известной уязвимостью, подсунув старый (когда-то честно подписанный) артефакт.
  • Атомарность. Новая версия целиком лежит в releases/<ver>/, переключение — замена одного симлинка. Нет состояния «половина файлов новые».
  • Откат по факту, а не по надежде. Новый worker обязан за 2 минуты отправить heartbeat со своей версией; updater ждёт подтверждения от Core или смотрит локальный маркер. Нет подтверждения — откат на previous, Core останавливает rollout группы.

Почему обновляет root, а не сам worker

Если бы worker под dbagent сам писал в каталог с кодом, то захвативший dbagent мог бы подложить туда свой код и закрепиться на хосте. Разделение: код принадлежит root, updater под root делает ровно три вещи (скачать, проверить, переложить и перезапустить), worker про обновления не знает и лишь сообщает версию в heartbeat. Поверхность root-процесса минимальна: он не выполняет ничего скачанного до проверки подписи.

Как обновляется сам updater

Updater маленький и меняется редко. Его новая версия приходит тем же путём внутри артефакта; текущий updater после проверки подписи заменяет свой файл атомарно (rename), сохраняя updater.prev. Новый updater применяется со следующего тика таймера; при падении новой версии таймер запускает updater.prev (обёртка проверяет код выхода).

2. Как агент получает пароль и как его хранит

Здесь описан вариант, когда база требует пароль. Если СУБД допускает OS-аутентификацию (Oracle ops$-пользователь или / as sysdba, PostgreSQL peer, MySQL auth_socket), профиль базы получает auth: os, и весь этот раздел для неё не нужен: пароля нет, агент подключается локально под своим uid. Профиль назначается на каждую базу отдельно по итогам инвентаризации; агент поддерживает оба режима одновременно.

2.1. Идея одной фразой

На хосте лежит только зашифрованный пароль. Расшифровать его можно только с участием Core — по подписанному запросу, при живом lease. Пароль появляется в памяти worker и никогда не пишется на диск открытым.

Две ветки, отличающиеся одним шагом:

  • A1 — ключ данных выдаётся агенту. Ключ K_agent хранит Core (в Vault). При старте агент получает K_agent и расшифровывает файл сам. Core никогда не видит пароль.
  • A2 — расшифровка на стороне Core. Ключ не покидает Vault (Transit). Агент шлёт шифртекст, Core расшифровывает и возвращает пароль, завернув его в публичный ключ агента. Core видит пароль транзитно, каждая расшифровка попадает в аудит.

Дополнение D к любой ветке: агент сам создаёт себе учётку в базе dba_agent со случайным паролем и сам её ротирует. Привилегированный пароль DBA вводит один раз при заведении, и агент его тут же забывает.

2.2. Заведение пароля базы

sequenceDiagram
    autonumber
    actor DBA
    participant A as agent add-db (на хосте, под dbagent)
    participant DB as СУБД
    participant Core
    participant V as Vault
    DBA->>A: agent add-db --id ORCL_HOSTA --type oracle --sid ORCL --create-account
    A-->>DBA: запрос привилегированного пароля (ввод без эха)
    DBA->>A: пароль
    A->>DB: подключиться привилегированной учёткой
    A->>DB: CREATE USER dba_agent IDENTIFIED BY случайный пароль, GRANT только нужные привилегии
    A->>A: привилегированный пароль обнулить в памяти
    alt A1: ключ данных выдаётся агенту
        A->>Core: GET /agents/me/keys/current
        Core->>V: прочитать K_agent
        V-->>Core: K_agent
        Core-->>A: K_agent, обёрнутый в pubWrap агента
        A->>A: распаковать приватным ключом, AES-256-GCM(K_agent, пароль, AAD), K_agent обнулить
    else A2: ключ не покидает Core
        A->>Core: GET /agents/me/encryption-key
        Core-->>A: публичный ключ шифрования (ключ Transit агента)
        A->>A: случайный DEK, AES-256-GCM(DEK, пароль, AAD), DEK зашифровать RSA-OAEP публичным ключом
    end
    A->>A: записать creds/ORCL_HOSTA.enc.new (0600), fsync, rename в creds/ORCL_HOSTA.enc
    A-->>DBA: база добавлена, пароль в открытом виде нигде не сохранён

Схема 2a. Заведение пароля базы на хосте. Пароль не проходит через Jira, Cockpit UI и журнал.

  • Без флага --create-account DBA заранее создаёт учётку агента сам и вводит её пароль; шаги 4–6 пропускаются.
  • AAD (дополнительные аутентифицированные данные) = agentId | dbId | keyId: шифртекст одной базы нельзя подсунуть агенту как шифртекст другой — проверка GCM не сойдётся.
  • Запись через .new + fsync + rename: при сбое питания не останется полузаписанного файла.
  • Если ИБ запрещает ввод пароля на хосте, эта же операция делается из Cockpit UI: Core получает пароль, шифрует (A1 — K_agent, A2 — Transit) и отдаёт шифртекст агенту при следующем lease. Тогда Core видит пароль один раз при заведении — это ослабляет A1, и решение стоит фиксировать отдельно.

2.3. Получение пароля в память при старте

sequenceDiagram
    autonumber

Схема 2b. Получение паролей при старте. Одна и та же обёртка pubWrap закрывает содержимое от балансера или прокси, терминирующего TLS.

2.4. Как агент подписывает запросы

После регистрации каждый запрос к Core несёт заголовок:

X-Agent-Auth: agentId=17, ts=1755432000, nonce=<16 случайных байт, base64>, sig=<base64>
sig = ECDSA_P256_sign(privSign, ts + "\n" + nonce + "\n" + METHOD + "\n" + path + "\n" + sha256(body))

Core находит агента по agentId, проверяет подпись его публичным ключом, что |now − ts| ≤ 5 минут, что nonce не встречался за это окно, что агент не revoked и IP в разрешённом списке (если ведём). Приватный ключ никогда не покидает хост. Подпись живёт внутри HTTP, поэтому балансеры и прокси между агентом и Core ей не мешают — в отличие от mTLS, который требует настройки клиентского CA на том, кто терминирует TLS.

Условие: часы на хосте синхронизированы (NTP) — иначе окно ±5 минут отсечёт легитимные запросы.

    DB-->>W: OK
    W->>W: зашифровать новый пароль (A1: K_agent, A2: публичный ключ Core)
    W->>W: записать .enc.new, fsync, переименовать .enc в .prev и .new в .enc
    W->>DB: пробное подключение новым паролем
    alt успех
        W->>W: удалить .prev
        W->>Core: POST /agents/me/credentials/rotate {dbId, keyId, ciphertext} как escrow
    else отказ
        W->>W: оставить .prev, при следующем старте пробовать оба файла
        W->>Core: heartbeat со статусом rotate_failed
    end

Схема 2c. Ротация пароля агентом.

  • Ротируется пароль учётки dba_agent, а не root/SYSDBA: привилегированный пароль остаётся у DBA, и его смена не ломает другие системы.
  • Escrow — копия шифртекста в Core на случай потери файла на хосте. Нюанс ветки A1: Core с ключом K_agent и escrow восстановит пароль, поэтому escrow дополнительно шифруется публичным ключом «аварийного» ключа DBA, приватная часть которого лежит офлайн. В ветке A2 Core по определению может расшифровать escrow — это осознанное доверие Core.
  • Сбой посередине (пароль в базе сменился, файл не записался): при следующем старте агент пробует .enc, затем .prev. Оба не подходят — алерт в Core, DBA сбрасывает пароль штатно и повторяет agent add-db.

2.7. Почему пароль хранится именно так

  • Не в аргументах запуска. ps -ef показывает аргументы всех процессов любому пользователю хоста. Это касается и шифртекста, и SQL — всё идёт через файлы 0600 и stdin.
  • Не открытым на диске. Файл, бэкап, снимок ВМ, копия образа — не должны отдавать пароль без Core.
  • Только в памяти worker. Против чтения памяти: процесс под отдельным dbagent, ptrace_scope=1 на Linux, -XX:+DisableAttachMechanism и -XX:-HeapDumpOnOutOfMemoryError для JVM, LimitCORE=0 / coreadm -d process. Root на хосте память прочитает при любой схеме — это вне модели угроз: root хоста СУБД и так владелец базы.
  • Lease, а не «получил и забыл». Раз в leaseTtl/2 агент продлевает lease. Отказ Core (403 revoked) — агент стирает пароли из памяти и перестаёт брать задания. Это и есть централизованный отзыв.

Критерий выбора — чему доверяем меньше: Core или хосту. Если ИБ формулирует требование «система и её операторы не должны знать пароли баз» — A1+D. Если Core доверенный, важнее простой агент на двух стеках, мгновенный отзыв и аудит каждого обращения — A2 + обёртка + D. Интерфейс агента одинаковый («получить пароль базы в память при старте»), меняется только реализация одного шага, поэтому старт с одной ветки не запирает от другой.

2.9. Break-glass

Обычно пароль dba_agent человеку не нужен: DBA заходит / as sysdba и сбрасывает его. Если всё же нужен, на хосте выполняется agent reveal --db X: агент вызывает POST /agents/me/reveal, Core выполняет его только после подтверждения DBA-администратора в Cockpit (второй человек, запись в журнал), результат печатается в терминал один раз.

3. Как агент выполняет запросы

Канал заданий — REST-опрос Core (ADR-002, рабочая гипотеза: пошаговая выдача, порядок шагов гарантирует Core, агент без состояния между шагами). Агент никогда не получает входящих вызовов: он сам спрашивает задание, сам отчитывается.

sequenceDiagram
    autonumber
    participant W as worker (dbagent)
    participant Core
    participant P as JDBC или подпроцесс sqlplus / psql
    participant DB as СУБД
    loop каждые N секунд, пока нет задания
        W->>Core: POST /tasks/claim
        Core-->>W: задание (taskId, dbId) или 204 нет заданий
    end
    W->>Core: GET /tasks/{taskId}/steps/next
    Core-->>W: шаг: code, SQL с подставленными значениями, таймаут, output_keys
    W->>W: дособрать значения (generator.password, выходы прошлых шагов), взять пароль по dbId из памяти
    W->>P: открыть подключение (JDBC thin с паролем из памяти, либо sqlplus -S /nolog с CONNECT через stdin), окружение ORACLE_HOME и ORACLE_SID
    P->>DB: выполнить SQL
    DB-->>P: результат или ошибка
    P-->>W: результат, код выхода, stdout и stderr
    alt таймаут шага истёк
        W->>P: закрыть соединение или kill подпроцесса
        W->>W: статус шага error, причина timeout
    end
    W->>Core: POST /tasks/{taskId}/steps/{code}/report {status, output по output_keys, duration, error} (идемпотентно, с ретраями)
    Core-->>W: OK, есть ли следующий шаг
    Note over W,Core: следующий шаг тем же циклом, пока Core не ответит: задание завершено

Схема 3. Выполнение задания по шагам.

Подключение к базе

  • Профиль password. JDBC thin (Oracle, PostgreSQL, MySQL) с паролем из памяти — самый прямой путь. Через CLI: не sqlplus dba_agent/пароль@alias (аргументы видны в ps), а sqlplus -S /nolog и строка CONNECT dba_agent/"пароль"@alias через stdin. Для psql — временный PGPASSFILE 0600 в /var/lib/dbagent/tmp, удаляемый сразу после подключения; PGPASSWORD в окружении читается тем же uid и root через /proc, но не через ps.
  • Профиль os. Только подпроцесс: sqlplus -S / (или / as sysdba), psql -U dba_agent через unix-сокет, mysql --socket=…. JDBC thin OS-аутентификацию не умеет; JDBC OCI умеет, но требует совпадения версий клиента и драйвера.
  • SQL всегда через stdin, не через аргументы. Несколько инстансов на хосте — свои ORACLE_SID/ORACLE_HOME в окружении каждого подпроцесса, из профиля базы.

Таймауты и зависания

У каждого шага есть таймаут из шаблона флоу. Для JDBC — setQueryTimeout и таймаут соединения; для подпроцесса — ожидание с предельным временем и destroyForcibly() / kill -9 по истечении. Зависший подпроцесс без таймаута держал бы worker и, что хуже, сессию в базе — поэтому таймаут обязателен, а не желателен.

Что попадает в отчёт, а что нет

  • В отчёт: статус, длительность, значения по output_keys (колонки итогового SELECT), текст ошибки без чувствительных данных.
  • Не в отчёт и не в логи агента: пароль подключения, значение generator.password (временный пароль новой учётки — по ADR-004 уходит в Core отдельной сущностью, не в отчёт шага), полный текст SQL, если он содержит пароли (IDENTIFIED BY). Агент маскирует такие фрагменты до записи в лог.

Core недоступен посреди задания

Отчёт по шагу отправляется с ретраями и backoff; шаг не повторяется, пока отчёт не доставлен (идемпотентность по taskId + code + попытка). Если Core не отвечает дольше порога, worker завершает текущий шаг, отчёт откладывает в память и не запрашивает следующий; при восстановлении сначала доставляет отложенный отчёт. Если worker перезапустился с недоставленным отчётом — Core по таймауту шага помечает попытку как «прервана», задача уходит DBA на разбор (автоперезапуск шагов не делаем по решению brief).

4. Старт, остановка, отзыв доступа

4.1. Старт

sequenceDiagram
    autonumber
    participant SM as systemd / SMF
    participant W as worker (dbagent)
    participant Core
    SM->>W: запуск под uid dbagent, окружение из /etc/dbagent/env
    W->>W: прочитать identity.json и agent.conf, проверить права 0600, время (NTP)
    W->>Core: GET /agents/me/lease
    alt Core недоступен
        W->>W: повтор с backoff (5 с ... 5 мин), заданий не брать, паролей нет
    else 403 revoked
        W->>W: пароли не запрашивать, статус revoked, ждать (только heartbeat)
    else 200 active
        Core-->>W: leaseTtl, список баз и профили
        W->>Core: получить пароли для профилей password (схема 2b)
        W->>Core: POST /agents/me/heartbeat {version, ready, список баз}
        Note over W: готов брать задания (раздел 3)
        loop каждые leaseTtl/2
            W->>Core: POST /agents/me/lease
            Core-->>W: продлён или 403
        end
    end

Схема 4a. Старт worker.

Без Core агент не стартует в рабочий режим: паролей нет, заданий нет. Это осознанно — кэш расшифрованных паролей на диске свёл бы на нет раздел 2. Если потребуется «grace-режим» (работа по кэшу при недоступном Core ограниченное время), это отдельное решение с отдельными рисками; по умолчанию его нет.

4.2. Остановка и перезапуск

sequenceDiagram
    autonumber
    participant SM as systemd / SMF
    participant W as worker (dbagent)
    participant Core
    SM->>W: SIGTERM (stop, restart, обновление от updater)
    W->>W: новых заданий и шагов не брать
    alt идёт шаг
        W->>W: дождаться завершения шага, но не дольше stop-таймаута (например, 60 с)
        W->>Core: отчёт по шагу
    end
    W->>W: обнулить буферы с паролями, закрыть соединения с базами
    W->>Core: heartbeat {stopping}
    W-->>SM: exit 0 (штатно) или exit 75 (перезапусти меня)
    SM->>W: перезапуск по Restart=always или duration=child

Схема 4b. Остановка. Код 75 — сигнал сервис-менеджеру перезапустить процесс (после обновления, смены конфигурации).

Если шаг не уложился в stop-таймаут, worker убивает подпроцесс, отправляет отчёт со статусом «прерван остановкой» и выходит; задача попадает DBA на разбор. Пароли обнуляются в любом случае перед выходом.

4.3. Отзыв доступа

sequenceDiagram
    autonumber
    actor DBA
    participant UI as Cockpit UI
    participant Core
    participant W as worker (dbagent)
    participant DB as СУБД
    DBA->>UI: отозвать агента host-a (причина в журнал)
    UI->>Core: POST /agents/17/revoke
    Core->>Core: статус revoked, A1: пометить K_agent к ротации
    W->>Core: POST /agents/me/lease (очередное продление)
    Core-->>W: 403 revoked
    W->>W: обнулить пароли в памяти, закрыть соединения, задания не брать
    W->>Core: heartbeat {revoked} (принимается и в статусе revoked)
    Note over Core,W: A2: любой decrypt теперь отклоняется. A1: выданный ключ есть только в памяти агента и исчезнет при перезапуске
    DBA->>DB: сменить пароль dba_agent или заблокировать учётку на базах хоста
    Note over DB: закрывает пароль, который уже был в памяти агента до отзыва
    opt восстановление доверия к хосту
        DBA->>UI: новый enrollment-token
        DBA->>W: agent enroll заново, затем agent add-db
    end

Схема 4c. Отзыв агента. Между отзывом и следующим продлением lease проходит не больше leaseTtl/2 — этот интервал и есть цена варианта A1; в A2 decrypt отклоняется сразу.

Отзыв закрывает будущие расшифровки. Пароль, уже находящийся в памяти работающего процесса, закрывается только сменой пароля в базе — поэтому шаг «сменить пароль dba_agent» входит в процедуру отзыва, а не остаётся на усмотрение.

4.4. Состояния агента

stateDiagram-v2
    [*] --> enrolled: agent enroll с одноразовым токеном
    enrolled --> active: первый успешный lease
    active --> active: продление lease каждые TTL/2
    active --> suspended: DBA приостановил или lease не продлевался дольше TTL
    suspended --> active: lease принят
    active --> revoked: DBA отозвал
    suspended --> revoked: DBA отозвал
    revoked --> enrolled: повторный enroll новым токеном
    revoked --> [*]: карточка удалена

Схема 4d. Состояния агента в Core.

  • suspended — временная пауза без отзыва: агент не получает ключи/decrypt и задания, но identity и шифртексты остаются валидными; используется на время работ на хосте или при пропаже heartbeat.
  • revoked — окончательно: identity недействительна, для возврата нужен новый enrollment-token и, при подозрении на компрометацию, новые пароли баз.

6. Глоссарий

enrollment-token
Одноразовый короткоживущий токен для первичной регистрации агента в Core. Даёт право один раз зарегистрировать публичные ключи, ничего не расшифровывает.
identity агента
Пара приватных ключей (подпись запросов и распаковка ответов) плюс agentId. Лежит на хосте в файле 0600, никогда не покидает хост.
lease
«Аренда» права работать: агент периодически продлевает её у Core; отказ в продлении означает отзыв — агент стирает пароли и останавливает выполнение.
обёртка (wrap)
Шифрование ответа Core публичным ключом агента (RSA-OAEP), чтобы содержимое не видел никто между Core и агентом, включая прокси с TLS-терминацией.
AAD
Additional Authenticated Data в AES-GCM: данные, которые не шифруются, но защищены от подмены. Здесь — привязка шифртекста к агенту, базе и ключу.
K_agent
Ключ данных агента (AES-256) в ветке A1: хранится у Core, выдаётся агенту на время работы.
Vault Transit
Режим Vault «шифрование как сервис»: ключ не покидает Vault, клиенты просят encrypt/decrypt/rewrap. Основа ветки A2.
escrow
Копия шифртекста пароля в Core на случай потери файла на хосте.
D (собственная учётка агента)
Агент создаёт в базе учётку dba_agent с ограниченными правами и случайным паролем и сам её ротирует; привилегированный пароль остаётся у DBA.
OS-аутентификация
Вход в СУБД по OS-пользователю процесса без пароля, только локально: Oracle bequeath (/ as sysdba, ops$-пользователь), PostgreSQL peer, MySQL auth_socket. Ядро ОС сообщает СУБД uid клиента.
canary
Небольшая группа агентов, получающая новую версию первой; остальные — после подтверждения, что canary работает.
anti-rollback
Запрет ставить версию ниже текущей без явно подписанного разрешения.
symlink swap
Атомарное переключение активной версии заменой символической ссылки current.
SMF
Service Management Facility — сервис-менеджер Solaris 10/11 (аналог systemd): манифесты, svcadm, автоперезапуск, запуск под заданной учёткой.
break-glass
Аварийная процедура получения пароля человеком с подтверждением второго лица и записью в журнал.
SPARC
Процессорная архитектура Sun/Oracle. Solaris бывает на SPARC и x86; под SPARC нет Go и JDK новее 8.
