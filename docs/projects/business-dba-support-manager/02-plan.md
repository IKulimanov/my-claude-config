# Plan: dba-ops-assistant

Статус: черновик
Архитектурное описание: [[01-design]] (система целиком)

Задачи разделены на этапы «по нарастающей»: сначала Core (движок флоу), независимый от
источника событий, затем Executor, адаптеры источников, экраны. Приоритет источников
может меняться (заявки или события мониторинга) — Core от этого не зависит.

## Приложения

| Код | Репозиторий | Что это |
|---|---|---|
| Core | `business-dba-ops-assistant` | главный репозиторий: сущности, движок флоу, приём заявок и алармов, задания Executor, уведомления, переходы задач в Jira, регламентные процессы |
| Cockpit | `cockpit-dba-ops-assistant` | бэк для фронта: вход, сессии, роуты экранов; бизнес-логики не содержит, вызывает операции Core |
| Cockpit UI | `cockpit-dba-ops-assistant-ui` | фронт для DBA |
| Executor | `integration-dba-ops-assistant` | исполнитель заданий рядом с целевыми базами; только у него доступ к кредам и целевым СУБД. Вынесен отдельно: рантайм и форма поставки могут отличаться от серверных приложений вплоть до отдельного бинарника |

# Этап 1. [dba-ops-assistant] Основание — контекст «конфигурация»

## Зачем
Система конфигурируется флоу и шаблонами скриптов; всё остальное их только исполняет.
Прежде чем строить движок, нужно уметь хранить, загружать и проверять конфигурацию:
невалидный флоу должен быть отвергнут при загрузке, а не обнаружен на живой задаче.
Архитектура: 01-design «Конфигурация: флоу, словари, шаблоны», «Валидация конфигурации».

## Результат этапа
Валидные версии флоу, шаблонов скриптов и шаблонов сообщений загружаются миграцией и
активируются; невалидная версия не активируется и не даёт сервису подняться; каталог баз
отвечает на запросы словаря БД.

## Открытые вопросы
- 1.1 — состав модулей проекта: какие контексты домена выделяются в отдельные модули.

## Состав
1. Каркас: БД системы, миграции и приложение Core
2. Реализовать модель определения флоу и разбор yml
3. Реализовать хранение конфигурации: версии флоу, шаблонов и сообщений, каталог баз
4. Реализовать валидатор конфигурации
5. Документирование: README локальной разработки

### 1.1 [Core] Каркас: БД системы, миграции и приложение Core

Что сделать: развернуть БД системы и механизм версионируемых миграций схемы — применение при
выкладке и локально, фиксация применённых версий, порядок и конвенция нумерации; обеспечить
локальный запуск базы для разработки и тестов. Создать многомодульный проект с разделением
по контекстам домена и приложение Core, которое поднимается с подключением к БД системы:
конфигурация окружений задаётся снаружи, логирование по конвенции, единый формат ошибок.
Зависимости между модулями направлены к домену; модули переиспользуются другими приложениями
системы. Прикладных таблиц здесь нет — они появляются в подзадачах своих контекстов; без
экранов, метрик и проверок работоспособности.

Критерии приёмки:
- Дано: чистая локальная БД системы. Когда: запуск приложения. Тогда: приложение стартует,
  миграции применены, версии зафиксированы, лог фиксирует готовность.
- Дано: база с применёнными миграциями. Когда: повторный запуск. Тогда: изменений нет.
- Дано: миграция с ошибкой в середине набора. Когда: прогон. Тогда: применение остановлено,
  последующие миграции не применены, причина видна в выводе.
- Дано: БД системы недоступна. Когда: запуск. Тогда: приложение завершается с внятной
  ошибкой, а не зависает наполовину поднятым.
- Дано: конфигурация другого окружения. Когда: запуск с ней. Тогда: параметры взяты из
  окружения, в коде и артефакте значений нет.
- Дано: модуль с зависимостью против направления к домену. Когда: сборка с архитектурным
  тестом. Тогда: сборка падает с указанием нарушения.

Открытые вопросы:
- Состав модулей проекта: какие контексты домена выделяются в отдельные модули
  (конфигурация, каталог, задача и движок, приём, канал Executor, журнал, outbox, общие
  типы) — зафиксировать до создания каркаса.

Зависимости: нет.

Оценка: 6 часов.

### 1.2 [Core] Реализовать модель определения флоу и разбор yml

Что сделать: типизированная модель определения флоу — шапка, переменные, стадии с
параметрами, слушатели, шаги стадии сборки — и разбор yml в неё. Имя обработчика стадии
определяет схему его параметров; неизвестный или лишний ключ — ошибка разбора с указанием
места. Модель и разбор не зависят от БД и сети. Flow-файлы и шаблоны переносятся из папки
документации в репозиторий кода в этой задаче; тесты — на этих реальных файлах
(pg-1, pg-2, pg-3, ora-1, ora-2, zbx-1).

Критерии приёмки:
- Дано: шесть flow-файлов репозитория. Когда: разбор. Тогда: каждый разобран без ошибок,
  стадии и переменные соответствуют файлу.
- Дано: yml с ключом, которого нет в схеме. Когда: разбор. Тогда: ошибка с путём до ключа.
- Дано: yml, где параметры стадии не соответствуют её обработчику. Когда: разбор. Тогда:
  ошибка с кодом стадии и именем обработчика.

Зависимости: нет.

Оценка: 6 часов.

### 1.3 [Core] Реализовать хранение конфигурации: версии флоу, шаблонов и сообщений, каталог баз

Что сделать: хранение флоу, шаблонов скриптов и шаблонов сообщений; каждая версия —
неизменяемая запись:
определение хранится целиком, поисковые поля загрузчик извлекает из него сам, правка
возможна только загрузкой новой версии. Загрузка новой версии миграцией с активацией вместо
предыдущей; откат — возврат активности прежней. Поиск активного флоу по источнику и
внешнему ключу; поиск шаблона по коду и версии. Каталог целевых баз — стабильный код
записи, адрес подключения, тип СУБД, окружение, признаки критичности и ручного режима,
ссылка на секрет — и реестр словарей, сопоставляющий имя словаря его источнику записей;
доступ к атрибутам записи по имени для выражений флоу. Наполнение — миграцией или служебным
вызовом.

Шаблоны сообщений — одна сущность для всех текстов, которые система отправляет наружу:
комментарий в заявку, письмо заказчику, сообщение в чат команды. Атрибуты: код, канал
(заявка, почта, чат), тема (для писем), текст с подстановками, описание для того, кто правит
текст. Хранение и загрузка — тем же механизмом, что у шаблонов скриптов; резолв по коду.
Ни один отправляемый текст не живёт в коде приложений.

Критерии приёмки:
- Дано: активная версия флоу. Когда: загрузка новой версии того же кода. Тогда: активна
  новая, прежняя сохранена и неактивна.
- Дано: источник и внешний ключ. Когда: поиск. Тогда: находится ровно одна активная версия.
- Дано: существующая версия. Когда: попытка изменить её содержимое. Тогда: отказ — версии
  неизменяемы, правка возможна только новой версией.
- Дано: откат активации. Когда: возврат прежней версии. Тогда: прежняя снова активна, задачи
  с новой версией продолжают ссылаться на неё.
- Дано: запись каталога. Когда: запрос по коду. Тогда: запись найдена, атрибуты доступны
  по именам.
- Дано: выражение с атрибутом записи. Когда: вычисление со значением-кодом. Тогда: атрибут
  разрешается через точку.
- Дано: неизвестный код или имя словаря. Когда: запрос. Тогда: внятная ошибка с именем.
- Дано: шаблон сообщения. Когда: резолв по коду. Тогда: найдены канал, тема и текст с
  подстановками.
- Дано: новая версия шаблона сообщения. Когда: загрузка. Тогда: активна новая, прежняя
  сохранена и неактивна — как у шаблонов скриптов.

Зависимости: 1.2.

Оценка: 9 часов.

### 1.4 [Core] Реализовать валидатор конфигурации

Что сделать: полный набор проверок из архитектурного описания: уникальность пары источник +
внешний ключ среди активных; ровно одна словарная переменная баз в флоу; наличие стадии
подтверждения; существование ссылок на словари, шаблоны скриптов и шаблоны сообщений; закрытость
обязательных параметров шаблонов; объявленность подстановок в текстах сообщений; непустой список согласующих у стадии согласования; парс выражений и объявленность
имён; литералы против закрытых списков; одно поле источника — одна переменная во всех флоу
источника; ссылки на выход только предшествующих шагов; терминальные исходы закрыты
переходом заявки. Запуск при загрузке версии и при старте сервиса для всех активных;
невалидная версия не активируется, невалидное состояние не даёт сервису подняться.

Критерии приёмки:
- Дано: шесть flow-файлов репозитория и их шаблоны. Когда: валидация. Тогда: все проходят.
- Дано: флоу со ссылкой на несуществующую версию шаблона. Когда: загрузка. Тогда: версия не
  активирована, в ошибке — код флоу и ссылка.
- Дано: выражение с необъявленной переменной. Когда: валидация. Тогда: ошибка с кодом флоу,
  стадии и именем переменной.
- Дано: два активных флоу с одной парой источник + ключ. Когда: старт сервиса. Тогда: сервис
  не поднимается, причина в логе.

Зависимости: 1.2, 1.3.

Оценка: 7 часов.

# Этап 2. [dba-ops-assistant] Движок флоу — контекст «задача»

## Зачем
Сердце системы: универсальный интерпретатор ведёт задачу по стадиям, описанным в
конфигурации; знание об операциях живёт только в конфигурации. Все остальные этапы либо
подают движку сигналы, либо читают его состояние. Архитектура: 01-design «Движок флоу»,
02-flow-runtime.

## Результат этапа
Задача из тестового события проходит флоу до «Готова к выполнению» — стадии
активируются по выражениям и режиму выполнения, шаги собраны с подставленными значениями,
подтверждение выполнено служебным вызовом, ход по стадиям и статус видны в БД системы.

## Состав
1. Реализовать модель задачи
2. Реализовать вычисление выражений и подстановок
3. Реализовать интерпретатор стадий и статусную модель
4. Реализовать механику приёма событий и тестовый вход
5. Реализовать transactional outbox и вызов слушателей
6. Реализовать стадию сборки шагов
7. Реализовать стадию подтверждения и права DBA
8. Реализовать действия DBA над задачей
9. Реализовать обработку повторных событий
10. Реализовать координатор джобов: локи в ZooKeeper

## Зависимости
Этап 1 закрыт: конфигурация загружается и валидируется, каталог баз отвечает.

### 2.1 [Core] Реализовать модель задачи

Что сделать: задача с закреплением за версией флоу, значениями переменных и идемпотентностью
по паре источник + внешняя ссылка. Ход по стадиям — запись на каждый вход в стадию:
состояние, полезная нагрузка, кто решил и когда. Шаги выполнения — порядок, код, снапшот
шаблона, итоговый скрипт, включённость, признак кастомного, статус и результат. Правила
целостности встроены в операции модели: у задачи не больше одной активной стадии, шаги
меняются только в разрешённых статусах.

Критерии приёмки:
- Дано: задача с парой источник + ссылка. Когда: создание второй с той же парой. Тогда:
  вторая не создаётся, вызов идемпотентен.
- Дано: задача с активной стадией. Когда: попытка открыть вторую стадию. Тогда: отказ.
- Дано: задача в статусе, где шаги заморожены. Когда: попытка правки шага. Тогда: отказ с
  причиной.

Зависимости: нет.

Оценка: 6 часов.

### 2.2 [Core] Реализовать вычисление выражений и подстановок

Что сделать: вычисление выражений над контекстом задачи — переменные, атрибуты словарной
записи через точку, атрибуты флоу, результат старта текущей стадии, упавший шаг — и
подстановок `${{ }}` в параметрах стадий, слушателей и шагов. Значения времени выполнения
(генераторы, выход шагов) остаются плейсхолдерами. Значения экранируются при подстановке в
текст скрипта — защита от инъекции через свободный текст заявки. Логика вычисления не
зависит от БД и внешних систем; тесты — без БД.
Архитектура: 01-design «Выражения и подстановки».

Критерии приёмки:
- Дано: контекст с переменными и словарной записью. Когда: вычисление выражения с атрибутом
  через точку. Тогда: результат верен.
- Дано: параметр шага с подстановкой переменной. Когда: сборка. Тогда: значение в тексте,
  ссылки генераторов и выходов шагов остались плейсхолдерами.
- Дано: значение со спецсимволами SQL. Когда: подстановка в текст скрипта. Тогда: значение
  экранировано, структура скрипта не изменилась.
- Дано: выражение с именем вне контекста. Когда: вычисление. Тогда: ошибка с именем.

Зависимости: нет.

Оценка: 6 часов.

### 2.3 [Core] Реализовать интерпретатор стадий и статусную модель

Что сделать: цикл интерпретации задачи по стадиям её версии флоу. При входе в стадию движок
решает активацию: по выражению стадии, для стадии подтверждения — ещё и по режиму выполнения
флоу и флагу базы; неактивная стадия помечается пропущенной, её события не происходят.
Активная стадия запускается обработчиком и ждёт внешнего сигнала; синхронная завершается
сразу. Все сигналы приходят в единственную точку приёма: обработчик активной стадии решает,
завершена ли она (промежуточный сигнал оставляет её активной), движок — куда двигаться.
Продвижение — единственная точка изменений: в одной транзакции фиксируется исход, ставятся
в очередь слушатели завершающего события, открывается следующая стадия; терминальный исход
закрывает задачу. Статус задачи определяется позицией во флоу по диаграмме статусов
(01-design «Статусная модель») и меняется только движком при продвижении; выборки по
статусу — очередь «Готова к выполнению» для Executor, списки для экранов; терминальные
статусы — «Не распознана», «Отклонена», «Выполнена»; «Ошибка» не терминальна. Сам цикл не
зависит от БД и внешних систем: в тестах вместо реальных обработчиков и слушателей —
заглушки, сценарии проверяются на настоящих flow-файлах из репозитория.
Архитектура: 01-design «Движок флоу», «Статусная модель»; 02-flow-runtime.

Критерии приёмки:
- Дано: флоу из трёх стадий, у второй ложное выражение. Когда: задача проходит флоу. Тогда:
  вторая пропущена, третья запущена, события второй не происходили.
- Дано: активная стадия согласования с двумя согласующими. Когда: решение одного. Тогда:
  стадия активна, продвижения нет.
- Дано: тот же случай. Когда: решение второго. Тогда: исход зафиксирован, слушатели в
  очереди и следующая стадия открыта в одной транзакции.
- Дано: активная стадия. Когда: сигнал чужой стадии или задачи. Тогда: отклонён, состояние
  не изменилось.
- Дано: обработчик падает при запуске стадии. Когда: движок открывает стадию. Тогда: задача
  в «Ошибка», исход зафиксирован, задача доступна для разбора.
- Дано: задача проходит флоу с согласованием и подтверждением. Когда: смена стадий. Тогда:
  статусы меняются по диаграмме.
- Дано: флоу, где подтверждение не активируется. Когда: сборка завершена. Тогда: задача
  сразу «Готова к выполнению».
- Дано: попытка сменить статус мимо движка. Когда: вызов вне продвижения. Тогда: отказ.

Зависимости: 2.1, 2.2.

Оценка: 8 часов.

### 2.4 [Core] Реализовать механику приёма событий и тестовый вход

Что сделать: единый контракт приёма события источника: поиск активного флоу по источнику и
типу, маппинг полей события в переменные по блоку переменных флоу, валидация (обязательность,
закрытые списки, словарные значения), создание задачи и старт первой стадии. Исходы: флоу не
найден — событие пропускается с уведомлением; событие невалидно — задача «Не распознана»,
реакцию в источнике выполняет его адаптер (этап 4); дубль — второй задачи нет. Тестовый
вход — служебный роут, подающий событие этим же контрактом; остаётся инструментом отладки.

Критерии приёмки:
- Дано: валидное тестовое событие известного типа. Когда: приём. Тогда: задача создана с
  переменными, первая стадия открыта.
- Дано: событие без обязательного поля. Когда: приём. Тогда: задача «Не распознана», причина
  сохранена.
- Дано: событие неизвестного типа. Когда: приём. Тогда: задачи нет, пропуск зафиксирован.
- Дано: повторное событие той же пары источник + ссылка. Когда: приём. Тогда: второй задачи
  нет.

Зависимости: 2.1, 2.2, 2.3.

Оценка: 6 часов.

### 2.5 [Core] Реализовать transactional outbox и вызов слушателей

Что сделать: реестр слушателей по имени с объявленной гарантией доставки. Слушатели с
гарантией — через outbox: запись в одной транзакции с исходом стадии, порядок в пределах
задачи; идемпотентность эффекта — требование к каждому слушателю с гарантией. Формат
повторов единый для всех таких слушателей: 5 попыток с задержками 1 минута, 15 минут,
1 час, 2 часа, 5 часов. Слушатель либо использует этот формат, либо объявляется без
повторов — своих расписаний у хендлеров нет. Исчерпание попыток останавливает доставку,
запись остаётся в outbox для разбора; отдельной реакции у слушателя нет. Слушатели без
гарантии доставки вызываются после фиксации транзакции, их падение не влияет на задачу.
Доставку выполняет джоб-диспетчер под локом координатора (2.10): единственный активный
диспетчер сохраняет порядок доставки в пределах задачи.

Критерии приёмки:
- Дано: завершение стадии со слушателем через outbox. Когда: транзакция фиксируется. Тогда:
  запись поставлена в той же транзакции; при падении процесса сразу после — запись есть.
- Дано: доставка падает. Когда: повторы. Тогда: интервалы идут по 1 минуте, 15 минут,
  1 часу, 2 и 5 часам, попытки считаются.
- Дано: пятая попытка неудачна. Когда: очередной цикл доставки. Тогда: доставка остановлена,
  запись видна для разбора, задача не меняет статус.
- Дано: слушатель объявлен без повторов. Когда: доставка падает. Тогда: повторов нет.
- Дано: слушатель без гарантии доставки бросает ошибку. Когда: вызов. Тогда: задача
  продвинулась, ошибка в логе.
- Дано: рестарт приложения с недоставленными записями. Когда: подъём. Тогда: доставка
  возобновляется.
- Дано: два экземпляра Core с недоставленными записями. Когда: доставка. Тогда: каждая
  запись доставлена один раз.

Зависимости: 2.3, 2.10.

Оценка: 6 часов.

### 2.6 [Core] Реализовать стадию сборки шагов

Что сделать: синхронная стадия: для каждого шага из параметров стадии вычислить условие
включения, разрешить подстановки уровня задачи в тексте шаблона по коду и версии, создать
шаги задачи со снапшотом шаблона и итоговым скриптом; плейсхолдеры времени выполнения
остаются. Если сборка не удалась (неразрешимая подстановка, отсутствующий шаблон) — исход
ошибки: задача переходит в «Ошибка» с причиной для разбора. Пересборка при возврате задачи
на начало флоу (автошаги заново, кастомные сохраняются) вызывается обработкой повторных
событий (2.9).

Критерии приёмки:
- Дано: флоу pg-1, флажок прав включён. Когда: сборка. Тогда: включены шаги по условиям,
  остальные отсеяны, значения подставлены, генератор пароля остался плейсхолдером.
- Дано: собранный шаг. Когда: загружена новая версия шаблона. Тогда: шаг не изменился —
  снапшот держит свою версию.
- Дано: шаг с подстановкой, которую нечем разрешить. Когда: сборка. Тогда: задача «Ошибка»,
  в причине — код шага и имя подстановки.

Зависимости: 2.2, 2.3.

Оценка: 6 часов.

### 2.7 [Core] Реализовать стадию подтверждения и права DBA

Что сделать: учётки инженеров с ролью (оператор, администратор) и закрепления за базами.
Проверка прав — одна общая операция: оператор действует по закреплённым базам, администратор
по любым, задачи на критичной базе — только администратор; наполнение — служебными вызовами.
Стадия подтверждения: активация по режиму выполнения флоу — ручной всегда, авто не
активируется, «по базе» решает флаг записи каталога — плюс выражение стадии поверх режима.
Старт назначает ответственных по закреплениям целевой базы, для критичной —
администраторов. Завершение — решение DBA служебным вызовом: подтверждение — успех, отказ с
причиной — отклонение; право решающего проверяется этой же операцией прав.

Критерии приёмки:
- Дано: оператор с закреплением. Когда: проверка права на задачу своей базы. Тогда:
  разрешено; на чужой — отказ.
- Дано: задача на критичной базе. Когда: проверка права оператора этой базы. Тогда: отказ;
  администратору — разрешено.
- Дано: неизвестная учётка. Когда: проверка. Тогда: отказ с причиной.
- Дано: флоу в ручном режиме. Когда: задача доходит до подтверждения. Тогда: стадия активна
  независимо от флага базы.
- Дано: флоу «по базе», флаг базы снят. Когда: та же точка. Тогда: стадия пропущена, задача
  «Готова к выполнению».
- Дано: активное подтверждение. Когда: решение ответственного. Тогда: задача продвинулась,
  решивший зафиксирован.
- Дано: активное подтверждение. Когда: решение DBA без прав на базу. Тогда: отказ, стадия
  активна.

Зависимости: 2.3.

Оценка: 7 часов.

### 2.8 [Core] Реализовать действия DBA над задачей

Что сделать: серверные операции с проверкой прав, доступные в статусах «Ждёт подтверждения»
и «Ошибка»: отключить шаг, изменить текст скрипта, переставить порядок, добавить свой шаг
(помечается кастомным, без шаблона); отклонение задачи с обязательной причиной. Правки
живут только в шагах задачи; флоу и шаблоны неизменны. В остальных статусах шаги заморожены.
До появления экранов операции вызываются служебно.

Критерии приёмки:
- Дано: задача «Ждёт подтверждения». Когда: DBA правит текст шага и порядок. Тогда: правки
  сохранены, видны в шагах задачи, шаблон не изменился.
- Дано: задача «Выполняется». Когда: попытка правки. Тогда: отказ.
- Дано: добавление своего шага. Когда: вставка на позицию. Тогда: шаг помечен кастомным и
  стоит на месте.
- Дано: отклонение без причины. Когда: вызов. Тогда: отказ; с причиной — задача «Отклонена»,
  причина сохранена.

Зависимости: 2.1, 2.7.

Оценка: 5 часов.

### 2.9 [Core] Реализовать обработку повторных событий

Что сделать: событие изменения данных существующей задачи. До подтверждения задача
возвращается в начало флоу и проходит все проверки заново: значения перевалидируются и
обновляются, решения прежнего согласования сбрасываются, стадии стартуют с чистого листа —
сигналы прежнего раунда к перезапущенной стадии не относятся и не применяются. Автошаги
пересобираются заново; кастомные шаги DBA сохраняются в задаче и добавляются к пересобранным
(это касается только состава шагов выполнения). DBA уведомляется. После подтверждения: изменения не применяются, в источник уходит
комментарий. Невалидные изменения не применяются никогда.

Критерии приёмки:
- Дано: задача на согласовании, DBA добавил кастомный шаг. Когда: событие изменения данных.
  Тогда: задача на первой стадии, автошаги пересобраны по новым значениям, кастомный шаг
  сохранён в конце.
- Дано: возврат на начало после изменения. Когда: приходит поздний сигнал прежнего
  согласования. Тогда: отброшен.
- Дано: задача подтверждена. Когда: событие изменения. Тогда: данные прежние, слушателю
  поставлен комментарий для источника.
- Дано: изменение с невалидными значениями. Когда: приём. Тогда: данные прежние, задача не
  сдвинулась.

Зависимости: 2.4, 2.6.

Оценка: 6 часов.

### 2.10 [Core] Реализовать координатор джобов: локи в ZooKeeper

Что сделать: подключить `zookeeper-client-starter` и сделать обвязку «джоб = прогон по
расписанию под локом»: регистрация джоба, взятие своего лока перед прогоном, пропуск
прогона без лока с записью в лог. Лок ephemeral — падение держателя освобождает его
автоматически. Недоступность ZooKeeper не роняет приложение: прогоны пропускаются с
ошибкой в логе. Архитектура: 01-design «Джобы», ADR-008.

Критерии приёмки:
- Дано: два экземпляра, время прогона. Когда: срабатывание расписания. Тогда: прогон
  выполняет один экземпляр, второй пропускает с записью в лог.
- Дано: держатель лока упал посреди прогона. Когда: следующий прогон. Тогда: лок
  свободен, прогон выполняется на живом экземпляре.
- Дано: ZooKeeper недоступен. Когда: время прогона. Тогда: прогон пропущен, ошибка в
  логе, приложение работает.

Зависимости: 1.1.

Оценка: 4 часа.

# Этап 3. [dba-ops-assistant] Executor — контекст «исполнение»

## Зачем
Executor выполняет собранные шаги на целевых базах и отчитывается по каждому; только у него
доступ к кредам и целевым СУБД, о флоу и источниках он не знает. Архитектура: 01-design
«Обзор», «Выполнение задачи исполнителем»; ADR-001, ADR-002.

## Результат этапа
Executor выполняет собранные шаги на тестовой базе, результат и журнал видны в
БД системы, ошибка шага останавливает задание.

## Открытые вопросы
- 3.1 — ADR-002: канал получения заданий и возврата отчётов, форма выдачи задания.
- 3.1 — ADR-001: хранение и выдача кредов целевых баз.

## Состав
1. Анализ: канал заданий и креды целевых баз (ADR-002, ADR-001)
2. Реализовать серверную сторону канала
3. Реализовать каркас Executor и цикл выполнения задания
4. Реализовать выполнение скрипта на целевой базе
5. Реализовать стадию выполнения: результаты, журнал, перезапуск

## Зависимости
Этап 2 закрыт. До закрытия 3.1 этап не дробится и не раздаётся; до принятия
ADR-001 проверка только на тестовой базе.

### 3.1 [Core] [Executor] Анализ: канал заданий и креды целевых баз (ADR-002, ADR-001)

Что сделать: два архитектурных решения этапа.

ADR-002 — канал получения заданий и возврата отчётов: выбрать между REST-опросом, очередью
сообщений и чтением БД системы, выбрать форму выдачи (задание целиком или пошагово).
Обязательные вопросы: направление соединений (входящих в Executor нет), атомарность захвата,
идемпотентность отчётов, поведение при недоступности сторон, совместимость контракта на
версию назад — обновление Executor идёт руками DBA, версии разъедутся неизбежно.

ADR-001 — хранение и выдача кредов целевых баз с учётом решения о развертывании Executor:
внешнее хранилище секретов (постоянные или разовые креды) или локальная поставка секретов к
экземпляру. Обязательные вопросы: радиус поражения при компрометации, ротация, аудит
обращений, доступность из сегмента Executor, требования безопасности.

По результату — пересмотреть состав и наполнение подзадач этапа: выбранный канал определяет
объём серверной стороны (3.2) и цикла Executor (3.3), выбранное хранилище — работу с кредами
в 3.4.

Критерии приёмки:
- ADR-002 в статусе «принят»: вариант выбран с обоснованием против альтернатив; контракт
  канала зафиксирован в архитектурном описании — операции, идемпотентность, ошибки, версия.
- ADR-001 в статусе «принят»: зафиксировано, где лежит секрет, кто имеет доступ, как
  ротируется, что попадает в логи.
- Разобраны отказы: Core недоступен при выполнении задания — что с заданием и отчётами;
  хранилище секретов недоступно при выполнении.
- Состав и наполнение подзадач этапа пересмотрены под принятые решения, оценки уточнены.

Зависимости: нет.

Оценка: 7 часов (лимит).

### 3.2 [Core] Реализовать серверную сторону канала

Что сделать: по принятому контракту: выдача задания с атомарным захватом — задачу «Готова к
выполнению» получает ровно один экземпляр, задача переходит в «Выполняется»; приём отчётов
по шагам идемпотентно — повторный отчёт не дублирует эффект; проверка подлинности Executor
по принятому в ADR-002 способу. Совместимость контракта на версию назад — с первого релиза.

Критерии приёмки:
- Дано: одна готовая задача, два одновременных запроса. Когда: захват. Тогда: задание
  получает один, второй — пусто.
- Дано: отчёт по шагу доставлен. Когда: повторная доставка того же отчёта. Тогда: состояние
  не изменилось.
- Дано: отчёт по чужой или несуществующей задаче. Когда: приём. Тогда: отказ, состояние
  нетронуто.

Зависимости: 3.1.

Оценка: 6 часов.

### 3.3 [Executor] Реализовать каркас Executor и цикл выполнения задания

Что сделать: приложение Executor поднимается с конфигурацией снаружи, проверяет связность
с Core по принятому каналу и пишет логи по конвенции; секреты — по ADR-001, не в коде, не в
аргументах запуска и не в логах. Цикл: получить задание, выполнить шаги строго по порядку
позиций — только включённые и ожидающие, — после каждого шага отправить отчёт с повторами
при недоставке; упавший шаг завершает задание, судьбу остальных шагов решает сервер.
Executor не хранит состояние между заданиями и ничего не знает о флоу. До готовности
серверной стороны (3.2) канал в тестах подменяется заглушкой по контракту.

Критерии приёмки:
- Дано: валидная конфигурация. Когда: запуск. Тогда: приложение стартует и подтверждает
  связность с Core.
- Дано: Core недоступен. Когда: запуск. Тогда: Executor не падает, повторяет попытки
  с задержкой, пишет причину.
- Дано: запущенный процесс. Когда: осмотр аргументов, окружения и логов. Тогда: секретов в
  открытом виде нет.
- Дано: задание из трёх шагов, второй отключён. Когда: выполнение. Тогда: выполнены первый
  и третий по порядку, по каждому отчёт.
- Дано: второй шаг падает. Когда: выполнение. Тогда: третий не запускался, отчёт об ошибке
  отправлен.
- Дано: отчёт не доставлен. Когда: повтор. Тогда: доставка повторяется, следующий шаг не
  начинается до подтверждения приёма.

Зависимости: 3.1.

Оценка: 8 часов.

### 3.4 [Executor] Реализовать выполнение скрипта на целевой базе

Что сделать: подключение к Oracle и PostgreSQL по адресу из задания и кредам по ADR-001.
Перед запуском шага дособрать плейсхолдеры времени выполнения: генератор пароля —
криптостойкое значение, которое нигде не сохраняется и не попадает в отчёты, журнал и логи;
выход предыдущих шагов — значения из их результатов по коду шага и ключу; неразрешимый
плейсхолдер — шаг падает без выполнения скрипта. Выполнение скрипта шага по контракту:
успех — отсутствие ошибки СУБД, текст и код ошибки сохраняются как результат шага; шаг с
ключами выхода завершается запросом, значения колонок извлекаются в результат. Таймаут
выполнения шага.

Критерии приёмки:
- Дано: успешный скрипт. Когда: выполнение. Тогда: успех, вывод сохранён.
- Дано: скрипт с ошибкой СУБД. Когда: выполнение. Тогда: шаг упал, код и текст ошибки в
  отчёте.
- Дано: шаг с ключами выхода. Когда: выполнение. Тогда: значения извлечены по именам колонок.
- Дано: база недоступна. Когда: подключение. Тогда: шаг упал без выполнения, причина внятна.
- Дано: шаг с генератором пароля. Когда: выполнение. Тогда: пароль подставлен только в
  отправляемый на базу текст; в отчёте, журнале и логах его нет.
- Дано: шаг со ссылкой на выход предыдущего. Когда: выполнение. Тогда: значение подставлено.
- Дано: ссылка на шаг, который не выполнялся. Когда: дособирание. Тогда: шаг падает без
  запуска скрипта, причина — код шага и ключ.

Зависимости: 3.3.

Оценка: 9 часов.

### 3.5 [Core] Реализовать стадию выполнения: результаты, журнал, перезапуск

Что сделать: стадия выполнения: старт переводит задачу в «Готова к выполнению»; отчёты
шагов записываются в шаги задачи (статус, вывод, результат, ошибка, время); упавший шаг —
остальные помечаются пропущенными, исход ошибки; все выполнены — исход успеха. Запись
попытки в журнал самодостаточна: содержит все шаги, скрипты и результаты попытки и читается
без обращения к другим таблицам; одна запись — одна попытка; журнал только пополняется,
записи не меняются. Перезапуск из статуса «Ошибка»: упавшие и пропущенные шаги сбрасываются
в ожидание, выполненные не перевыполняются, задача снова «Готова к выполнению»; перед
перезапуском DBA может поправить шаги (операции 2.8); каждая новая попытка — новая запись
журнала. Перезапуск доставки — отдельная операция, шаги при нём не трогаются.

Критерии приёмки:
- Дано: все шаги успешны. Когда: последний отчёт. Тогда: стадия завершена успехом, попытка
  в журнале со всеми шагами и скриптами.
- Дано: шаг упал. Когда: отчёт об ошибке. Тогда: остальные пропущены, задача «Ошибка»,
  попытка в журнале.
- Дано: запись журнала. Когда: попытка изменить или удалить. Тогда: отказ — журнал только
  пополняется.
- Дано: задача «Ошибка», два шага выполнены, один упал, один пропущен. Когда: перезапуск.
  Тогда: выполненные нетронуты, упавший и пропущенный ожидают, задача «Готова к выполнению».
- Дано: перезапущенная задача выполнена. Когда: просмотр журнала. Тогда: две записи — по
  одной на попытку.
- Дано: задача не в «Ошибке». Когда: перезапуск. Тогда: отказ.

Зависимости: 2.3, 3.2.

Оценка: 8 часов.

# Этап 4. [dba-ops-assistant] Адаптеры источников — контекст «интеграции»

## Зачем
Живые события внешних систем превращаются в задачи той же механикой приёма, что и тестовый
вход; адаптер знает только свой источник, движок не знает ни одного. Архитектура: 01-design
«Создание задачи из заявки», «Статусная модель» (переходы источника); ADR-006.

## Результат этапа
Живая заявка из внешнего источника доходит до выполнения и закрытия без ручных
вызовов; неизвестное событие мониторинга становится задачей ручного разбора.

## Открытые вопросы
- 4.1 — ADR-006: канал доставки событий мониторинга и состав события.

## Состав
1. Анализ: канал событий мониторинга (ADR-006)
2. Реализовать адаптер заявок: вебхуки, переходы и комментарии
3. Реализовать стадию согласования
4. Реализовать роут списка баз для формы заявки
5. Реализовать адаптер событий мониторинга

## Зависимости
Этап 2 закрыт. Полный сквозной прогон — от живой заявки до выполнения — возможен после
этапа 3.

### 4.1 [Core] Анализ: канал событий мониторинга (ADR-006)

Что сделать: выбрать канал доставки событий мониторинга — очередь сообщений, вебхук или
опрос хранилища мониторинга; зафиксировать состав события: идентификатор базы, тип аларма,
имя объекта, текущее заполнение, время и идентификатор события. Обязательные вопросы:
идемпотентность доставки, поведение при недоступности системы, закрытие события в
мониторинге.

По результату — пересмотреть состав и наполнение подзадачи 4.5, которая этот канал
реализует.

Критерии приёмки:
- ADR-006 в статусе «принят», вариант выбран с обоснованием; состав события зафиксирован и
  покрывает реакции по архитектурному описанию.
- Разобран отказ: система недоступна в момент события — событие не теряется.
- Состав и наполнение подзадач этапа пересмотрены, оценки уточнены.

Зависимости: нет.

Оценка: 7 часов (лимит).

### 4.2 [Core] Реализовать адаптер заявок: вебхуки, переходы и комментарии

Что сделать: обе стороны интеграции с источником заявок. Приём вебхуков — создание,
изменение полей, решения согласующих — с проверкой подлинности и маппингом в контракт
механики приёма; реакции: заявка невалидна — перевод «Отменена» с комментарием причины;
активный флоу не найден — пропуск с уведомлением DBA, статус заявки не меняется; решение
согласования — сигнал активной стадии задачи. Обратная сторона — слушатель с гарантией
доставки через outbox: переход статуса заявки, комментарий по шаблону, заполнение полей;
идемпотентность: переход в текущий статус — пустое действие (иначе повторы outbox
зациклятся), комментарии не дублируются при повторной доставке; недоступность источника —
повторы outbox, задача не блокируется. Тексты комментариев берутся из каталога шаблонов
сообщений (1.3) по коду, в коде адаптера их нет.

Критерии приёмки:
- Дано: вебхук создания по переведённому типу. Когда: приём. Тогда: задача создана общей
  механикой, статус заявки обновлён.
- Дано: вебхук типа без активного флоу. Когда: приём. Тогда: задачи нет, заявка нетронута,
  уведомление отправлено.
- Дано: невалидная заявка. Когда: приём. Тогда: задача «Не распознана», заявка «Отменена» с
  причиной в комментарии.
- Дано: вебхук без подлинности. Когда: приём. Тогда: отклонён, следа в задачах нет.
- Дано: завершение стадии с переходом и комментарием. Когда: доставка. Тогда: статус заявки
  и комментарий соответствуют шаблону.
- Дано: заявка уже в целевом статусе. Когда: повторная доставка перехода. Тогда: пустое
  действие, ошибки нет.
- Дано: источник недоступен. Когда: доставка. Тогда: повторы с задержкой, задача не ждёт.

Зависимости: 4.1, 2.4, 2.5, 1.3.

Оценка: 10 часов.

### 4.3 [Core] Реализовать стадию согласования

Что сделать: каталог согласующих по базам (модель и наполнение). Старт
стадии: список из параметра стадии и каталога по целевой базе, дедупликация, снапшот с
решениями в нагрузке стадии, заполнение поля согласующих в заявке. Сигнал решения: все
согласовали — успех, любой отказ — отклонение; решения вне снапшота отклоняются. Пустой
итоговый список при активной стадии — задача «Ошибка».

Критерии приёмки:
- Дано: согласующие в параметре и в каталоге с пересечением. Когда: старт. Тогда: список
  без дублей, снапшот сохранён, поле заявки заполнено.
- Дано: два согласующих. Когда: решение одного «за». Тогда: стадия ждёт.
- Дано: решение второго «против». Тогда: задача отклонена с причиной.
- Дано: решение логина вне снапшота. Когда: сигнал. Тогда: отклонён, стадия не изменилась.
- Дано: пустой итоговый список. Когда: старт. Тогда: задача «Ошибка» — автосогласование
  исключено.

Зависимости: 2.3, 4.2.

Оценка: 6 часов.

### 4.4 [Core] Реализовать роут списка баз для формы заявки

Что сделать: роут выдачи каталога баз для наполнения поля формы: фильтры по компании и типу
СУБД, только пригодные для выбора записи, формат по контракту потребителя формы.
Аутентификация вызова — по api_key: ключ выдаётся источнику заявок, передаётся в заголовке
запроса, хранится как секрет и в логи не попадает.

Критерии приёмки:
- Дано: каталог с базами двух компаний и двух СУБД. Когда: запрос с фильтрами. Тогда: только
  подходящие записи.
- Дано: фильтр без совпадений. Когда: запрос. Тогда: пустой список, не ошибка.
- Дано: запрос без api_key или с неизвестным ключом. Когда: вызов. Тогда: отказ, данные не
  выданы, ключ в логах не появляется.
- Дано: БД системы недоступна. Когда: запрос. Тогда: внятная ошибка роута, а не пустой успех.

Зависимости: 1.3.

Оценка: 3 часа.

### 4.5 [Core] Реализовать адаптер событий мониторинга

Что сделать: приём событий мониторинга по принятому каналу: маппинг полей события в контракт
механики приёма, идемпотентность по идентификатору события. Известный тип аларма — задача
общей механикой; неизвестный — задача «Ручной разбор» без флоу. Закрытие события в
мониторинге — слушателем с гарантией доставки по архитектурному описанию.

Критерии приёмки:
- Дано: событие известного типа. Когда: приём. Тогда: задача создана общей механикой с
  переменными из события.
- Дано: событие неизвестного типа. Когда: приём. Тогда: задача «Ручной разбор», DBA
  уведомлены.
- Дано: повторная доставка события. Когда: приём. Тогда: вторая задача не создана.

Зависимости: 4.1, 2.4.

Оценка: 5 часов.

# Этап 5. [dba-ops-assistant] Уведомления и доставка результата

## Зачем
Команда DBA видит ход задач в своём чате, заказчик получает результат и креды защищённым
каналом мимо заявки и журнала. Архитектура: 01-design «Уведомления»; ADR-004.

## Результат этапа
Сообщение задачи в чате команды обновляется по ходу флоу; письмо с кредами доставляется
заказчику; пароль нигде не сохраняется в открытом виде.

## Состав
1. Реализовать сообщения команде DBA
2. Реализовать стадию доставки письма заказчику
3. Реализовать передачу пароля из Executor

## Зависимости
Этап 2 закрыт. Доставка пароля (5.3) требует этапа 3. Комментарии в заявку используют
слушатель этапа 4. Тексты сообщений берутся из каталога шаблонов (1.3).

### 5.1 [Core] Реализовать сообщения команде DBA

Что сделать: слушатель уведомлений без гарантии доставки: одно сообщение на задачу в топике
команды — первый вызов публикует, последующие редактируют то же сообщение (статус, ссылки,
согласующие). Идентификатор сообщения в чате хранится в отдельной сущности «сообщение
задачи в чате» — задача, топик, идентификатор; она чистится вместе с задачей. Текст берётся
из каталога шаблонов сообщений (1.3). При ожидании подтверждения — упоминание ответственных. Ошибка задачи — сообщение редактируется и дополнительно
отправляется новое. Недоступность чата не влияет на продвижение задачи.

Критерии приёмки:
- Дано: задача проходит две стадии со слушателями уведомлений. Когда: доставка. Тогда: в
  топике одно сообщение, отражает последний статус.
- Дано: задача падает в «Ошибка». Когда: уведомление. Тогда: сообщение задачи обновлено и
  отправлено отдельное новое.
- Дано: чат недоступен. Когда: уведомление. Тогда: задача продвинулась, ошибка в логе.

Зависимости: 2.5, 1.3.

Оценка: 5 часов.

### 5.2 [Core] Реализовать стадию доставки письма заказчику

Что сделать: стадия доставки: письмо заказчику через outbox по шаблону из каталога
сообщений (1.3) — тема и текст лежат там, в коде их нет. Успех стадии — доставка
состоялась; исчерпание повторов — задача «Ошибка»: стадия обязана чем-то завершиться, это
единственное место, где исчерпание попыток меняет статус задачи. Перезапуск доставки
повторяет только письмо, шаги выполнения не трогаются. Пароль берётся из сущности передачи
секрета (5.3) и после успешной отправки стирается — по ADR-004.

Критерии приёмки:
- Дано: выполненная задача с активной стадией доставки. Когда: доставка успешна. Тогда:
  задача «Выполнена», финальный переход заявки после доставки.
- Дано: почта недоступна. Когда: повторы исчерпаны. Тогда: задача «Ошибка» с причиной.
- Дано: перезапуск доставки. Когда: вызов DBA. Тогда: отправлено только письмо, шаги
  нетронуты.

Зависимости: 2.5, 1.3.

Оценка: 5 часов.

### 5.3 [Executor] Реализовать передачу пароля из Executor

Что сделать: по ADR-004: после шага с генератором Executor передаёт пароль в Core, письмо
отправляет Core. Пароль живёт в отдельной сущности БД системы до отправки: не попадает в
задачу, шаги, журнал, отчёты и логи. Запись удаляется после успешной отправки письма,
просроченные записи удаляются регламентным процессом (7.1). Записи нет или она просрочена —
внятная ошибка доставки и путь повторной установки пароля.

Критерии приёмки:
- Дано: задание с генератором пароля. Когда: выполнение и доставка. Тогда: письмо содержит
  пароль; в журнале, отчётах, логах и БД в открытом виде его нет.
- Дано: письмо отправлено. Когда: проверка хранилища секретов. Тогда: записи с паролем нет.
- Дано: доставка позже срока жизни записи. Когда: повтор. Тогда: доставка падает с причиной
  «секрет истёк», путь повторной установки описан в ошибке.

Зависимости: 3.4, 5.2.

Оценка: 5 часов.

# Этап 6. [dba-ops-assistant] Cockpit — интерфейс и управление

## Зачем
DBA работает с задачами и каталогами с экранов. Бизнес-правил в Cockpit и Cockpit UI нет —
только вызовы серверной логики этапа 2; до этого этапа те же действия выполнялись служебными
вызовами. Архитектура: 01-design «Интерфейс Cockpit UI», «Роли и доступ».

## Результат этапа
DBA входит своей учёткой, видит задачи по правам, подтверждает, правит шаги,
разбирает ошибки; администратор ведёт каталоги.

## Состав
1. Согласовать и зафиксировать контракт Cockpit UI с Cockpit
2. Реализовать Cockpit: вход, сессии и роуты экранов
3. Реализовать каркас Cockpit UI и список задач
4. Реализовать карточку задачи
5. Реализовать действия DBA на карточке
6. Реализовать экраны администратора

## Зависимости
Этап 2 закрыт. Перезапуск после ошибки проверяется целиком с этапом 3.

### 6.1 [Cockpit UI] Согласовать и зафиксировать контракт Cockpit UI с Cockpit

Что сделать: перечень экранов по 01-design «Интерфейс Cockpit UI»; для каждого — данные и
действия, состояния, столбцы списков и форматирование значений (даты, статусы), поля форм с
проверками, положение в навигации, поведение после сохранения; выпадающие списки длиннее
десяти значений — с фильтрацией (выбор базы из 100+). Роуты с параметрами, обязательностью,
форматом ошибок и правами — по командному чек-листу описания роутов. Результат — документ
контракта рядом с архитектурным описанием; серверная (6.2) и экранная (6.3–6.6) работа идут
по нему параллельно. Макеты экранов приложены к задачам фронта отдельно.

Критерии приёмки:
- Контракт покрывает все экраны раздела «Интерфейс Cockpit UI» и все действия DBA над
  задачей.
- Каждый экран описан до столбцов, полей и форматов значений; каждый роут — метод, параметры
  и их обязательность, тело по назначению полей, формат ошибок, требуемая роль.
- Сценарии ошибок описаны для каждого действия: нет прав, неверный статус задачи, конфликт
  одновременного решения.

Зависимости: нет.

Оценка: 5 часов.

### 6.2 [Cockpit] Реализовать Cockpit: вход, сессии и роуты экранов

Что сделать: приложение Cockpit по ADR-007: операции Core вызываются по REST, к БД системы
Cockpit не подключается. Вход через global-id (учётная запись LDAP) и сессия — на стороне
Cockpit; учётка DBA передаётся в вызовы Core, а право на задачу и базу проверяет Core.
Серверные роуты по контракту 6.1 — списки и карточка задачи, действия DBA, каталоги.
Бизнес-логики не содержит. Проверка прав включается на реальные учётки вместо служебных.

Критерии приёмки:
- Дано: каждый роут контракта. Когда: валидный запрос. Тогда: ответ по контракту.
- Дано: действие без прав на базу. Когда: запрос оператора. Тогда: отказ сервером с кодом
  прав, состояние не изменилось.
- Дано: действие в неверном статусе задачи. Когда: запрос. Тогда: отказ с причиной, формат
  ошибки единый.
- Дано: Core недоступен или несовместим по версии. Когда: запрос экрана. Тогда: внятная
  ошибка, а не пустой ответ.

Зависимости: 6.1, 2.8.

Оценка: 7 часов.

### 6.3 [Cockpit UI] Реализовать каркас Cockpit UI и список задач

Что сделать: приложение Cockpit UI с навигацией, входом через внешнюю систему аутентификации
и ролями; разделы видны по роли; необработанные ошибки сервера показываются внятным
состоянием, не пустым экраном. Первый экран — список задач по правам (оператор — свои базы,
администратор — все) с фильтрами по статусу и базе, сортировкой по времени и переходом в
карточку; состояния: загрузка, пустой список, ошибка загрузки; пагинация серверная.

Критерии приёмки:
- Дано: пользователь без входа. Когда: открытие любого экрана. Тогда: переадресация на вход.
- Дано: оператор. Когда: навигация. Тогда: разделы администратора не видны и недоступны
  прямой ссылкой.
- Дано: сервер вернул ошибку. Когда: загрузка экрана. Тогда: видно состояние ошибки с
  возможностью повторить.
- Дано: оператор с закреплёнными базами. Когда: открытие списка. Тогда: только задачи своих
  баз.
- Дано: фильтры статуса и базы. Когда: применение вместе. Тогда: условия сочетаются.
- Дано: фильтр без совпадений. Когда: применение. Тогда: явное пустое состояние.

Зависимости: 6.1, 6.2.

Оценка: 8 часов.

### 6.4 [Cockpit UI] Реализовать карточку задачи

Что сделать: карточка: данные заявки и целевая база, ход по стадиям — включая пропущенные —
с временем и решившими, шаги со скриптами, статусами, выводом и ошибками, попытки из
журнала. Упавший шаг выделен с текстом ошибки. Данные обновляются после действий.

Критерии приёмки:
- Дано: задача с пропущенной стадией и упавшим шагом. Когда: открытие карточки. Тогда: видны
  все стадии с состояниями, упавший шаг выделен, текст ошибки читается.
- Дано: перезапущенная задача. Когда: просмотр попыток. Тогда: видны обе попытки журнала.
- Дано: задача изменилась после действия. Когда: возврат на карточку. Тогда: данные
  актуальны.

Зависимости: 6.2, 6.3.

Оценка: 6 часов.

### 6.5 [Cockpit UI] Реализовать действия DBA на карточке

Что сделать: экранные действия поверх роутов: подтверждение запуска, правка текста шага,
включение и отключение, перестановка порядка, добавление своего шага, отклонение с
обязательной причиной, перезапуск после ошибки. Опасные действия — с подтверждением;
доступность кнопок следует правам и статусу; отказ сервера показывается с причиной.

Критерии приёмки:
- Дано: задача «Ждёт подтверждения» у ответственного. Когда: правка шага и подтверждение.
  Тогда: правки сохранены, задача ушла дальше, кнопки правки исчезли.
- Дано: задача «Ошибка». Когда: правка упавшего шага и перезапуск. Тогда: задача снова в
  очереди выполнения.
- Дано: отклонение. Когда: попытка без причины. Тогда: действие заблокировано до ввода
  причины.
- Дано: отказ сервера в правах. Когда: действие. Тогда: причина показана, экран не сломан.

Зависимости: 6.2, 6.4.

Оценка: 6 часов.

### 6.6 [Cockpit UI] Реализовать экраны администратора

Что сделать: экран каталога баз: список с поиском, форма записи — адрес, тип СУБД,
окружение, компания, критичность, флаг ручного режима, ссылка на секрет; проверки формы с
текстом причины у невалидных полей. Экраны закреплений операторов за базами, согласующих по
базам и флага ручного режима записи каталога. Изменения действуют на новые задачи; активные
стадии не пересобираются.

Критерии приёмки:
- Дано: администратор. Когда: создание записи с валидными полями. Тогда: запись в каталоге
  и доступна выбору в задачах.
- Дано: запись с занятым адресом. Когда: сохранение. Тогда: ошибка у поля с причиной.
- Дано: оператор. Когда: попытка открыть каталог. Тогда: раздел недоступен.
- Дано: назначение оператора на базу. Когда: сохранение. Тогда: задачи базы видны оператору
  в списке.
- Дано: изменение согласующих базы. Когда: новая задача. Тогда: список согласования собран
  по-новому; активная стадия старой задачи не изменилась.
- Дано: включение флага ручного режима. Когда: новая задача флоу с режимом «по базе». Тогда:
  подтверждение активируется.

Зависимости: 6.2, 6.3.

Оценка: 8 часов.

# Этап 7. [dba-ops-assistant] Регламентные процессы

## Зачем
Система сама напоминает о зависших задачах и не копит отработанные. Архитектура: 01-design
«Джобы».

## Результат этапа
Зависшие задачи поднимаются напоминанием в чате команды; отработанные удаляются через
неделю, журнал не тронут; секреты доставки и доставленные записи outbox не залёживаются.

## Состав
1. Реализовать регламентные джобы: контроль зависших, очистка задач и технических таблиц

## Зависимости
Этап 2 закрыт; напоминания используют канал сообщений этапа 5.

### 7.1 [Core] Реализовать регламентные джобы: контроль зависших, очистка задач и технических таблиц

Что сделать: регламентные процессы, работающие часто и малыми порциями — каждый прогон
выгребает записи за небольшой период, чтобы запросы оставались короткими. Контроль зависших:
задачи, ждущие согласования или подтверждения дольше порога, поднимаются напоминанием в чат
команды со ссылками; порог настраивается; повторное напоминание по той же задаче не чаще
раза в день. Очистка задач: задачи в терминальных статусах старше недели удаляются вместе с
ходом стадий и шагами; журнал не трогается — история выполнений живёт долго, срок для неё
задаём отдельно, когда понадобится. Очистка технических таблиц: одним прогоном удаляются
отправленные и просроченные записи с паролями (5.3) и доставленные записи outbox старше
недели; недоставленные записи outbox и записи с исчерпанными попытками не трогаются.
Каждый джоб регистрируется в координаторе (2.10) и бежит под своим локом в ZooKeeper —
прогоны не накладываются и при нескольких экземплярах Core.

Критерии приёмки:
- Дано: задача ждёт дольше порога. Когда: прогон. Тогда: напоминание со ссылкой на карточку.
- Дано: задача моложе порога. Когда: прогон. Тогда: напоминания нет.
- Дано: напоминание уже было сегодня. Когда: повторный прогон. Тогда: дубля нет.
- Дано: чат недоступен. Когда: прогон. Тогда: процесс не падает, ошибка в логе, следующий
  прогон повторит.
- Дано: терминальная задача старше недели. Когда: прогон. Тогда: задача, стадии и шаги
  удалены, записи журнала целы.
- Дано: нетерминальная задача старше недели. Когда: прогон. Тогда: не удалена.
- Дано: журнал за любой срок. Когда: прогоны очистки. Тогда: записи журнала не удаляются.
- Дано: отправленная и просроченная записи с паролем. Когда: прогон. Тогда: обе удалены.
- Дано: доставленная запись outbox старше недели. Когда: прогон. Тогда: удалена.
- Дано: недоставленная запись outbox и запись с исчерпанными попытками. Когда: прогон
  очистки. Тогда: обе не удалены.
- Дано: два экземпляра Core. Когда: время прогона джоба. Тогда: прогон один, дублей
  напоминаний и удалений нет.
- Дано: ошибка на середине прогона. Когда: следующий прогон. Тогда: удалённое консистентно,
  обработка продолжается с того же места.

Зависимости: 2.10, 5.1, 5.3.

Оценка: 7 часов.

# Этап 8. [dba-ops-assistant] Выкладка и эксплуатация

## Зачем
Core и Cockpit собираются и выкладываются воспроизводимо; Executor поставляется так, что
его ставит и обновляет DBA без доступа разработчиков к ВМ. Архитектура: ADR-005; 01-design
«Обзор».

## Результат этапа
Core и Cockpit выкладываются конвейером; Executor устанавливается DBA по инструкции с
самопроверкой; состояние всех приложений видно по метрикам и проверкам.

## Открытые вопросы
- 8.1 — ADR-005: где и как работает Executor — топология, форма поставки, порядок установки
  и обновления руками DBA, наблюдение при отсутствии доступа к ВМ.

## Состав
1. Анализ: развертывание Executor (ADR-005)
2. Настроить сборку и выкладку Core и Cockpit
3. Подготовить поставку Executor
4. Реализовать наблюдаемость: метрики, проверки, наблюдение за экземплярами Executor

## Зависимости
«Анализ» и заготовка поставки — параллельно этапу 3; финал — после стабилизации контракта
Executor. Совместимость контракта на версию назад проверяется с этапа 3.

### 8.1 [Инфраструктура] Анализ: развертывание Executor (ADR-005)

Что сделать: вместе с DBA и безопасностью решить, где и как работает Executor: сегменты
сети и достижимость баз, число экземпляров (на сегмент или на базу), форма поставки
(архив с рантаймом, пакет, иное), способ передачи секретов на ВМ, порядок установки и
обновления руками DBA, наблюдение при отсутствии доступа к ВМ. Связано с ADR-001: способ
доставки секретов зависит от выбранной топологии.

По результату — пересмотреть состав и наполнение подзадач этапа: форма поставки определяет
объём 8.3, способ наблюдения — 8.4.

Критерии приёмки:
- ADR-005 в статусе «принят»: топология, форма поставки, порядок обновления и отката.
- Зафиксированы ограничения площадки: ОС, доступ в сеть, кто и как ставит.
- Разобран отказ: обновление Core при необновлённых экземплярах — контракт совместим
  на версию назад.
- Состав и наполнение подзадач этапа пересмотрены, оценки уточнены.

Зависимости: нет.

Оценка: 7 часов (лимит).

### 8.2 [Инфраструктура] Настроить сборку и выкладку Core и Cockpit

Что сделать: конвейер: сборка Core и Cockpit из чистого состояния, прогон тестов, сборка
артефактов с версией, выкладка по окружениям с применением миграций до старта нового кода;
откат на прежнюю версию.

Критерии приёмки:
- Дано: чистое окружение сборки. Когда: конвейер. Тогда: артефакты собраны воспроизводимо,
  версия проставлена.
- Дано: упавший тест. Когда: конвейер. Тогда: выкладки нет.
- Дано: выкладка с миграциями. Когда: развертывание. Тогда: миграции применены до старта
  нового кода.
- Дано: неудачная выкладка. Когда: откат. Тогда: прежняя версия работает.

Зависимости: нет.

Оценка: 6 часов.

### 8.3 [Инфраструктура] Подготовить поставку Executor

Что сделать: по принятой форме: артефакт с контрольной суммой в репозитории артефактов,
инструкция установки на русском для DBA, установка и обновление с откатом на прежнюю
версию, режим самопроверки после установки — конфигурация, связность с Core, доступ к
базам сегмента — с человекочитаемым отчётом.

Критерии приёмки:
- Дано: чистая ВМ по требованиям ADR-005. Когда: установка по инструкции. Тогда: Executor
  работает; шаги инструкции достаточны без участия разработчика.
- Дано: установленный Executor. Когда: самопроверка. Тогда: отчёт по каждому пункту;
  сломанный пункт называется явно.
- Дано: обновление на новую версию. Когда: откат. Тогда: прежняя версия работает.
- Дано: артефакт из репозитория. Когда: сверка суммы. Тогда: подлинность проверяема.

Зависимости: 8.1, этап 3.

Оценка: 6 часов.

### 8.4 [Core] [Executor] Реализовать наблюдаемость: метрики, проверки, наблюдение за экземплярами Executor

Что сделать: метрики Core и Executor: размер очереди готовых задач, время выполнения,
ошибки стадий, отставание доставки outbox — возраст самой старой недоставленной записи и
число недоставленных, отдельным счётчиком записи с исчерпанными попытками, ошибки и
длительность регламентных процессов, пропуски прогонов джобов по локу,
доступность целевых баз у Executor; проверки работоспособности для выкладки и наблюдения —
готовность отражает реальную способность работать. Core знает о каждом экземпляре Executor:
версия, время последнего контакта, доступность баз его сегмента — по данным, которые
Executor сообщает сам (доступа к ВМ нет); отображение администратору; молчание дольше
порога и несовместимая версия видны как проблема. Форма — по ADR-005. Двойной префикс
осознанный: одна задача покрывает обе стороны наблюдаемости.

Критерии приёмки:
- Дано: работающая система. Когда: съём метрик. Тогда: метрики доступны и меняются с
  нагрузкой.
- Дано: копятся недоставленные записи outbox. Когда: наблюдение. Тогда: рост виден по
  метрике.
- Дано: БД системы недоступна. Когда: проверка готовности Core. Тогда: не готов.
- Дано: целевая база сегмента недоступна. Когда: метрики Executor. Тогда: недоступность
  видна.
- Дано: работающий экземпляр. Когда: просмотр. Тогда: видны версия и время контакта.
- Дано: экземпляр молчит дольше порога. Когда: наблюдение. Тогда: помечен проблемным,
  команда уведомлена.
- Дано: экземпляр устаревшей версии. Когда: просмотр. Тогда: несовместимость видна.

Зависимости: 8.1, этап 3.

Оценка: 9 часов.

# Этап 9. [dba-ops-assistant] Внешние системы и запуск

## Зачем
Работы вне кодовой базы: настройка внешних систем, наполнение каталогов, включение операций.
Архитектура: 01-design «Настройка во внешних системах», «Формы заявок в Jira».

## Результат этапа
Пилотная операция включена и проходит путь целиком: заявка из формы — выполнение на тестовой
базе — статус и письмо. Порядок включения следующих операций задокументирован.

## Состав
1. Завести формы и типы заявок с полями
2. Настроить вебхук, workflow статусов и поле согласующих
3. Завести проект во внешней системе входа и назначить роли
4. Настроить чат уведомлений
5. Настроить канал событий мониторинга
6. Наполнить каталоги и включить операции по порядку

## Зависимости
Формы и поля — в любой момент; включение операций — после этапов 1–6 и 8. Канал
мониторинга — по ADR-006.

### 9.1 [Внешние системы] Завести формы и типы заявок с полями

Что сделать: новые типы заявок по формам из 01-design «Формы заявок в Jira»: поля со
справочниками и масками, обязательность, каскад «компания -> база» из роута каталога;
кастомные поля создаются один раз и переиспользуются между формами — одно поле всегда
означает одну переменную; существующие типы не трогаются.

Критерии приёмки:
- Дано: каждая форма из архитектурного описания. Когда: создание заявки с валидными полями.
  Тогда: заявка создаётся, поля уходят в вебхуке.
- Дано: поле, используемое двумя формами. Когда: сверка. Тогда: это одно и то же поле
  источника.
- Дано: невалидное значение по маске. Когда: отправка формы. Тогда: форма не отправляется.

Зависимости: 4.4.

Оценка: 6 часов.

### 9.2 [Внешние системы] Настроить вебхук, workflow статусов и поле согласующих

Что сделать: вебхук на систему по событиям создания, изменения полей и решений согласующих;
workflow новых типов заявок с переходами «На согласовании», «Готово», «Отменена»; поле
согласующих, заполняемое системой; повторный переход в текущий статус не ломает заявку.

Критерии приёмки:
- Дано: созданная заявка нового типа. Когда: событие. Тогда: вебхук доставлен системе с
  нужными полями.
- Дано: команда системы на переход. Когда: выполнение. Тогда: заявка в целевом статусе,
  комментарий виден.
- Дано: повторный переход в текущий статус. Когда: выполнение. Тогда: заявка не сломана,
  ошибки нет.

Зависимости: 4.2, 9.1.

Оценка: 5 часов.

### 9.3 [Внешние системы] Завести проект во внешней системе входа и назначить роли

Что сделать: заведение проекта во внешней системе аутентификации, вход по учётной записи
каталога организации, назначение ролей оператора и администратора команде DBA.

Критерии приёмки:
- Дано: DBA с учёткой каталога. Когда: вход в систему. Тогда: вход успешен, роль
  соответствует назначению.
- Дано: пользователь без роли в проекте. Когда: вход. Тогда: доступ закрыт.

Зависимости: 6.3.

Оценка: 3 часа.

### 9.4 [Внешние системы] Настроить чат уведомлений

Что сделать: бот, группа команды и топик уведомлений; бот с правом публиковать и
редактировать свои сообщения; параметры подключения переданы системе безопасным способом.

Критерии приёмки:
- Дано: настроенный бот. Когда: система публикует и редактирует сообщение. Тогда: обе
  операции работают в топике.
- Дано: ключ бота. Когда: осмотр конфигурации и логов системы. Тогда: ключа в открытом
  виде нет.

Зависимости: 5.1.

Оценка: 3 часа.

### 9.5 [Внешние системы] Настроить канал событий мониторинга

Что сделать: настроить доставку событий мониторинга по принятому каналу: отправка с нужным
составом полей, идемпотентность повторной доставки, доступ системы к каналу.

Критерии приёмки:
- Дано: тестовый аларм в мониторинге. Когда: срабатывание. Тогда: событие доставлено системе
  со всеми обязательными полями.
- Дано: повторная доставка события. Когда: приём. Тогда: вторая задача не создаётся.

### 9.6 [Внешние системы] Наполнить каталоги и включить операции по порядку

Что сделать: наполнение каталога баз выгрузкой от DBA, закрепления и согласующие, флаги
ручного режима; включение операций по порядку: форма — флоу и шаблоны миграцией — каталог —
вебхук или канал; пилот — одна операция на тестовой базе; порядок включения следующих
задокументирован.

Критерии приёмки:
- Дано: пилотная операция включена. Когда: живая заявка. Тогда: путь целиком — от формы до
  выполнения на тестовой базе, статуса и письма.
- Дано: следующий тип операции. Когда: включение по документу. Тогда: порядок воспроизводим
  без участия автора.

Зависимости: этап 1, этап 2, этап 3, этап 4, этап 5, этап 6, этап 8, 9.1, 9.2, 9.3, 9.4, 9.5.

Оценка: 5 часов.
