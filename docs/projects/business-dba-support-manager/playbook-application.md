## Дыры относительно плейбука (что дописать)

Brief:
1. Результат без чисел: «рутина уходит с DBA» непроверяемо. Нужна метрика: например,
   «N% заявок типовых операций выполняются без ручного разбора, время заявки с X до Y».
2. Нет appetite: сколько недель/людей готовы потратить на первую версию.
3. Scope In/Out не выделен явно (сейчас разбросан по тексту: «универсальную форму не делаем»,
   «набор шаблонов фиксированный»).

Design:
4. Нет схемы компонентов (Container): система, Jira, Zabbix, целевые БД, дашборд, vault, почта.
5. Контракты не зафиксированы: webhook Jira (payload, auth, retry), webhook Zabbix, API дашборда.
6. Модель данных без объёмов/владельцев/выборок (требование `task-writing.md` по сущности).
7. NFR отсутствуют: сколько заявок в день, сколько алармов, допустимая задержка выполнения.
8. Сценарии отказа частично есть (§ 4 «Ошибка»), но нет: недоступна целевая БД, Jira не отвечает
   на обновление статуса, дубль вебхука (идемпотентность), частичное выполнение скрипта.
9. Альтернатив нет вообще: почему своя система, а не Jira Automation / Ansible / Rundeck.
10. Тестирование и выкатка отсутствуют: как тестировать против реальных СУБД, пилот на
    test-окружениях, порядок подключения БД, откат.
11. Хранение кредов подключения к 100+ БД — помечено «обсуждаемо», должно стать ADR.

Кандидаты в ADR (решения уже приняты в CONCEPT, зафиксировать):
- формы разделены по СУБД, универсальной нет;
- пароль: генерация системой, защищённый канал, PASSWORD EXPIRE / VALID UNTIL;
- правка скрипта оператором действует только на задачу, шаблон неизменен;
- auto/approval — свойство типа заявки, критичные БД всегда approval;
- шаблоны скриптов в git через ревью DBA-администратора.

## Порядок действий

1. `00-brief.md`: выделить из CONCEPT, добавить метрики результата, appetite, явный Scope
   In/Out. Согласовать с DBA (заказчик).
2. Получить ответы на § 10 (это блокер design: операции, режимы, апрув, алармы, ошибки,
   уведомления).
3. `01-design.md` по шаблону: перенести § 3–8 из CONCEPT, закрыть дыры 4–10. Ревью коллегой.
4. `adr/`: зафиксировать пять решений выше + решение по кредам (дыра 11).
5. `02-plan.md`: вехи. Кандидат M1 (walking skeleton): вебхук Jira → валидация →
   PG-1 в режиме approval → выполнение на тестовой PG → журнал → статус в Jira.
   Zabbix, Oracle, auto-режим, уведомления — следующие вертикали. Отложенное — явно.
6. Задачи: dev-задача + подзадачи 3–7 ч по формату плейбука; подзадача «Документирование» сразу.
