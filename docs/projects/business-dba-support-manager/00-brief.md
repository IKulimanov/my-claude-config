## Проблема

В управлении DBA больше 100 баз (Oracle, PostgreSQL, MySQL) нескольких компаний группы. Заявки приходят через Jira («Центр подќдержки»), но ключевые поля заполняются свободным текстом, и каждую заявку DBA разбирает руками: уточняет, подбирает скрипт, выполняет, отписывается. Медленно, качество зависит от исполнителя, история размазана по тикетам.
Алармы Zabbix тоже разбираются вручную, даже типовые.

## Результат

Типовые операции над БД проходят без ручного разбора DBA: заявка из Jira автоматически валидируется, превращается в согласованный скрипт и выполняется — сразу или после апрува на дашборде. Все изменения на БД идут через один журналируемый канал, заказчик видит статус в Jira без переписки.

Метрики:

- заявки на типовые операций, выполняются без ручного разбора;
- типовые алармы Zabbix, закрываются автоматической реакцией.

## Пользователи и сценарии

- Заказчик (разработчик, аналитик — не эксперт по БД): создаёт заявку в Jira, выбирает тип операции и БД из справочников, заполняет поля, отвечает на уточнения.
- DBA-оператор (дежурный, за ним закреплён набор БД): работает с дашбордом по задачам своих БД — подтверждает, правит, отклоняет, возвращает на уточнение, разбирает ошибки.
- DBA-администратор (старший, владелец процесса): ведёт каталог типов заявок и шаблонов, назначает операторам их БД, обслуживает критичные инстансы.
- Система: принимает вебхуки Jira и Zabbix, валидирует, готовит и выполняет скрипты, пишет журнал, обновляет статус заявки в Jira.

## Scope

In:

- типизированные заявки из Jira: создание учётки, выдача прав, отзыв роли - для PostgreSQL и Oracle;
- выполнение по согласованным шаблонам: режим auto для безопасных операций, approval - через дашборд ответственного оператора;
- журнал всех выполнений (кто запросил, кто одобрил, что и где выполнено, результат);
- обновление статуса заявки в Jira;
- реакции на известные алармы Zabbix по каталогу (auto или через оператора).

Out:

- MySQL — базы есть в управлении, но типы заявок первой версии его не покрывают;
- универсальная форма для всех СУБД — формы Oracle и PostgreSQL раздельные;
- self-service добавление типов операций и шаблонов — новый тип добавляет разработка;
- автоматический перезапуск упавших скриптов — только решением DBA после разбора;
- заявки «Прочее» и нераспознанные алармы — остаются в ручном разборе, система их только маршрутизирует.

## Ограничения

- Вход - существующий портал Jira «Центр поддержки»: типы заявок уже заведены, формы дорабатываются, workflow статусов подгоняется под существующий.
- Jira при заполнении формы никуда не ходит: на её стороне только статичные проверки, живая валидация - на стороне системы после вебхука.
- Prod и критичные инстансы: всегда approval, критичные - только у DBA-администраторов.
- Пароль новой учётки не попадает в Jira, журнал и логи; отправляется автору защищённым каналом (сейчас корпоративная почта), всегда временный.
- Журнал не редактируется.
- Мониторинг - существующий Zabbix, алармы приходят вебхуком.
- Для живых проверок системе нужен read-доступ к словарям целевых БД; где его нет - проверка сводится к формату и ручному разбору.

## Открытые вопросы

Полные формулировки — в [[CONCEPT]] П. 10. Владелец ответов — DBA, дедлайн: __.

1. Перечень операций для автоматизации: скрипты, подставляемые значения, частота, СУБД.
2. Какие операции допустимы в auto и на каких окружениях.
3. Схема апрува: кто подтверждает, нужен ли двойной апрув и для каких БД.
4. Каталог алармов Zabbix: где реакция типовая (кандидаты в auto), где нужен человек.
5. Реакция на аларм по шагам: проверка -> действие -> контроль -> что делать при неуспехе.
6. Типовые ошибки выполнения: где нужен rollback-скрипт, где ручной разбор и чей.
7. Уведомления: о чём, кому, каким каналом, с какой срочностью.
