# ADR-008: Координация джобов Core

Дата: 2026-08-11
Статус: принят

## Контекст

Core может работать в нескольких экземплярах. Все его фоновые процессы — джобы:
доставка outbox, контроль зависших задач, очистки (см. 01-design «Джобы»). Прогоны
одного джоба не должны накладываться: двойная доставка письма с паролем недопустима,
а порядок доставки outbox в пределах задачи держится на том, что диспетчер в каждый
момент один.

## Варианты

1. **Один экземпляр Core, координацию отложить.** Ничего не делать, пока прогоны не
   начнут накладываться (прежнее решение дизайна).
   - плюсы: нулевая стоимость сейчас;
   - минусы: единственный экземпляр — ограничение выкладки и доступности; допущение
     «экземпляр один» нигде не контролируется, второй экземпляр ломает гарантии молча.

2. **Локи в БД системы** (ShedLock JDBC или advisory locks).
   - плюсы: без новых инфраструктурных зависимостей — БД уже есть;
   - минусы: зависший держатель требует таймаута и ручного разбора протухших локов;
     нестандартно для команды — свой код обвязки.

3. **Локи в ZooKeeper** через внутренний `zookeeper-client-starter`.
   - плюсы: командный стандарт координации сервисов, готовый стартер; ephemeral-локи
     освобождаются сами при падении держателя;
   - минусы: зависимость Core от кластера ZooKeeper.

## Решение

Вариант 3. Координатор джобов с локами в ZooKeeper — с самого начала, не отложенно.

Схема: расписание срабатывает на каждом экземпляре; перед прогоном джоб берёт свой лок
(лок на джоб, не глобальный), не взявший пропускает прогон — пропуск виден в логе и
метрике. ZooKeeper недоступен — прогоны пропускаются с ошибкой в логе, приложение
продолжает работать; фоновые процессы догоняют после восстановления.

Главное основание — командный стандарт: единый подход к координации сервисов и готовый
стартер вместо собственной обвязки над БД-локами. Ephemeral-локи снимают проблему
зависшего держателя без таймаутов и ручной чистки.
