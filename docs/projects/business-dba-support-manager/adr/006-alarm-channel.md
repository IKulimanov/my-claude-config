# ADR-006: Канал получения алармов Zabbix

Дата: 2026-07-31
Статус: предложен

## Контекст

Типовые алармы Zabbix (ZBX-1 «заполнение tablespace») должны становиться задачами
системы. Канал получения событий не выбран. Требования к каналу:

- событие несёт данные из 01-design («Данные, необходимые в событии аларма»):
  идентификатор БД/инстанса, имя tablespace, тип аларма, текущее заполнение,
  время срабатывания и id события;
- идемпотентность приёма по id события (повторная доставка не создаёт дубль задачи);
- потерянный аларм хуже повторного: канал должен переживать недоступность
  дашборда без потери событий.

## Варианты

1. Kafka-топик: Zabbix (или прослойка) публикует события, дашборд — потребитель.
   Буферизация и переигрывание из коробки, недоступность дашборда не теряет
   события. Минусы: неизвестно, умеет ли текущая установка Zabbix публиковать в
   Kafka (может понадобиться прослойка); зависимость от кластера Kafka и его
   сопровождения.

2. REST-вебхук от Zabbix: media type «webhook» шлёт HTTP-вызов в дашборд при
   срабатывании триггера. Штатная возможность Zabbix, без новой инфраструктуры,
   состав полей события задаётся в настройке media type. Минусы: доставка
   best-effort — ретраи Zabbix ограничены, при долгой недоступности дашборда
   событие теряется; дашборд должен принимать входящие от Zabbix.

3. SQL-опрос таблиц БД Zabbix: Zabbix хранит события в своей БД — система
   периодически читает новые события скриптом по курсору (id последнего
   обработанного). Не требует доработок Zabbix, переигрывание и надёжность
   контролируем сами, недоступность дашборда ничего не теряет. Минусы: привязка
   к схеме БД Zabbix (меняется между версиями); нужен доступ к чужой БД;
   задержка реакции равна интервалу опроса.

## Решение

Не принято.
