# ADR-001: Хранение и выдача кредов к целевым БД

Дата: 2026-07-21
Статус: предложен

## Контекст

Исполнитель подключается к 100+ БД (stage/prod, включая критичные). Креды нельзя держать в коде, конфиге и открытом виде в БД системы. Компрометация одного компонента не должна отдавать доступ ко всем базам.

Использование Vault пока под вопросом: неизвестно дадут ли возможность развернуть vault
под эту систему. Привилегированный секрет существует в любой схеме; варианты различаются тем, где он лежит, кто имеет к нему доступ, сколько живут производные креды и есть ли аудит обращений.

## Варианты

1. Vault KV: постоянные креды, по секрету на БД.
   Исполнитель читает секрет по мере надобности. Vault НЕ требует сетевого доступа к
   СУБД — нужен только канал исполнитель -> Vault. Самый простой вариант.
   Минусы: креды долгоживущие, ротация ручная; Vault концентрирует доступ ко всем БД
   (компенсация: аудит-лог Vault, отдельная policy только для исполнителя).

2. Vault database secrets engine: разовые креды на операцию.
   Vault сам создаёт временную учётку в целевой СУБД и удаляет по TTL. Короткое окно
   атаки, встроенная ротация. Минусы: Vault хранит рутовую учётку каждой БД — та же
   концентрация privileged-доступа (частично компенсируется rotate-root и аудитом);
   нужна сетевая связность Vault -> каждая СУБД; engine для Oracle — отдельный плагин;
   самый сложный вариант в эксплуатации.

3. Без Vault: Монтировать файлом, не в env: env-переменные утекают в дампы, логи и дочерние процессы, а смонтированный файл к тому же обновляется без рестарта пода.
   RBAC ограничивает чтение секрета сервис-аккаунтом исполнителя; дашборд доступа
   не имеет. Не требует нового инфраструктурного компонента.
   Минусы: нужен encryption at rest для etcd (иначе секрет читается с ноды);
   доступ есть у всех, кто администрирует пространство имён кластера; ротация руками через перевыкладку секрета.

## Решение

Не принято.
