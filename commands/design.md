# /design — документы проектирования

Процесс и форматы — `~/.claude/my-claude-config/playbook/projects-playbook.md`, шаблоны —
`playbook/templates/`, чек-листы и позиции для вариантов — скил `design-docs` (загрузи первым).
Артефакты живут в `~/.claude/my-claude-config/docs/projects/<проект>/`.

Аргументы: `$ARGUMENTS` = "$ARGUMENTS". Первый токен — имя проекта по `playbook/project-naming.md`
(`префикс-домен-функциональность`); нет имени — спроси. Второй токен — шаг; без него шаг определяется
по файлам.

## Шаг 0 — Состояние

```bash
DIR=$(~/.claude/my-claude-config/scripts/helpers/design-init.sh "<проект>")
```

Прочитай статусы в шапках `00-brief.md` и `01-design.md`:
- brief в статусе «черновик» или пустой по шаблону → шаг **brief**;
- brief «согласован», design «черновик» → шаг **doc**;
- design «approved» → шаг **plan**;
- явный `review <файл>` → шаг **review**.
Статусы меняет только автор: словами «согласован», «утверждаю», «approved» в чате или правкой файла.

## Шаг brief

1. Вход: ТЗ, файл, ссылка на задачу или разговор. Прочитай, что дано; в коде и в ТЗ не переспрашивай.
2. Первый вопрос — «Твой вариант решения в 1–3 строках или «не знаю»?» (AskUserQuestion, правило 08).
3. Остальные вопросы — одним пакетом, не больше пяти: заказчик, проверяемый результат с числом, что вне
   scope, appetite, ограничения. Только то, чего нет во входе.
4. Заполни `00-brief.md` по шаблону: проблема без технологий, результат проверяемый, Out of scope не пустой,
   вариант автора записан. Покажи файл и остановись: «согласуй или поправь».

## Шаг doc

1. Масштаб: проект больше двух недель или новый сервис, или флаг `--варианты N` → соревнование
   вариантов; иначе — один `architect` с двумя-тремя вариантами внутри документа.
2. Соревнование: запусти параллельно `architect` ×3 (роль «вариант», позиции: минималист, надёжность
   и эксплуатация, развитие; вход одинаковый — `00-brief.md`, контекст кода; выход `options/A.md`,
   `B.md`, `C.md`). Затем `architect` в роли «судья» → `options/verdict.md`. Флаг `--критика` добавляет
   один раунд: каждый автор получает чужие варианты и пишет только замечания о корректности
   и выполнимости в `options/critique-<буква>.md`.
3. Покажи таблицу судьи и рекомендацию. AskUserQuestion: «Какой вариант?» — A / B / C / смешать (как).
4. Разверни выбранное в `01-design.md` по шаблону: схема ≤ 7 блоков, модель данных и контракты по
   чек-листам `playbook/task-writing.md`, сценарии отказа, NFR числами, остальные варианты — по абзацу
   в «Рассмотренные альтернативы». Не длиннее 400 строк.
5. Прогони чек-лист «до approved» из шаблона; незакрытые пункты — в «Риски и открытые вопросы»
   с владельцем. Остановись: «ревью коллегой или сутки, затем approved».

## Шаг plan

1. Заполни `02-plan.md`: вехи как работающие вертикали, первая — сквозной сценарий; задачи 3–7 часов,
   рискованные первыми; отложенное явно.
2. Текст каждой задачи — по `playbook/templates/task-template.md` (можно через `/jira`).
3. Решения, принятые по ходу (технология, паттерн с последствиями, отказ от очевидного), — через `/adr`
   в `adr/`; в design — только ссылка.
4. Дальше: `/task <задача>` по каждой задаче.

## Шаг review

`architect` в роли «ревью» с файлом: не больше десяти замечаний (суть → почему важно → что дописать,
оценка «блокирует / стоит / по желанию»). Покажи список; правки в документ — только после ответа автора.

## Правила

- Один вызов — один шаг. Не перескакивать: следующий шаг только при статусе предыдущего.
- Ролевые формулировки («как профессиональный архитектор») не нужны и не используются: работают
  чек-листы и позиции.
- Русский, без слопа (правило 07); идентификаторы кода в design не фиксируются — назначение, а не имена.
- В конце шага — три строки в чат: что написано, куда, что нужно от автора.
