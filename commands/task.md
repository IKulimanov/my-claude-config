# /task — оркестратор больших задач

Главный поток тонкий: держит список фаз, статусы и короткие сводки. Работа идёт в свежих подагентах,
передача между шагами — только файлы каталога задачи `.claude/tasks/<ключ>/`. Остановок две: согласование
плана и согласование кейсов; дальше — только стоп-точки `[#]`, поставленные оператором, и `[!]`, когда
агент упёрся.

Аргументы: `$ARGUMENTS` = "$ARGUMENTS". Пусто — спроси, что делать.

## Шаг 0 — Сортировка

Определи по тексту, что это, и не запускай лишнего:
- вопрос, анализ, объяснение без изменения кода → ответь сам (при нужде один `Explore`) и остановись;
- правка в одно предложение без изменения поведения → скажи «это /quick» и сделай по `/quick`;
- баг или малое изменение поведения → «это /fix», сделай по `/fix`;
- фича в один контекст (одна фаза, не больше 8 правок файлов) → сделай по `/feature`;
- иначе — полный цикл ниже. Сомневаешься между `/feature` и `/task` — бери `/feature`.

Правило 08: если в постановке нет варианта автора («думаю», «предлагаю», «мой вариант») — один
вопрос через AskUserQuestion: «Твой вариант в 1–3 строках?» с вариантами «есть: …», «не знаю — предложи».
Follow-up вида «продолжай», «следующая фаза» — не спрашивать. Запомни время старта.

## Шаг 1 — Каталог задачи

Каталог привязан к ветке: ключ — Jira-ID из имени ветки, иначе имя ветки без типового префикса
(`feature/export-csv` → `export-csv`). Старый `.ai/` скрипт переносит сюда сам.

```bash
DIR=$(~/dev/my-claude-config/scripts/helpers/ai-init.sh)   # .claude/tasks/<ключ>/ — последний каталог ветки
```

- В `$DIR` нет `plan.md` — новая задача, дальше по шагам.
- Есть `plan.md`, нет `summary.md` — незаконченная задача («продолжай»): прочитай статусы плана и
  продолжай с того шага, где остановились; согласованное заново не согласовывай.
- Есть `summary.md` — доработка: `PREV=$DIR`, затем `DIR=$(ai-init.sh --new)` (каталог `<ключ>-2`, `-3` …);
  `summary.md` и `plan.md` из `$PREV` — на вход Explore и planner.

Файлы каталога. Для человека — в `$DIR`: `plan.md`, `tests.md`, `review.md` (итог ревью), `summary.md`
(итог задачи). Для агентов — в `$DIR/agent/`: `context.md`, `scope.txt`, `critique1..3.md`, `sonar.md`,
`review-raw-1..2.md`. Слепок репозитория — `.claude/tasks/about.md`, один на репозиторий. Каталог git
игнорирует глобально; ничего из него не удаляй.

## Шаг 2 — Контекст (`Explore`)

Промпт: сначала `~/dev/my-claude-config/shared/stack-detection.md`; прочитать локальный `CLAUDE.md` и весь
код, относящийся к задаче; для доработки — `summary.md` и `plan.md` из `$PREV`. Написать
`.claude/tasks/about.md` (проект как будто уже готов: архитектура, решения, области кода, без «TODO»;
если файл есть и не старше месяца — только дополнить) и `$DIR/agent/context.md` — не длиннее 300 строк:
постановка задачи дословно, вариант автора, относящиеся файлы с диапазонами строк, паттерны, структуры
данных, внешние контракты, команды сборки и тестов. Ссылки на код вместо цитат. Проверь, что оба файла
написаны и читаются.

## Шаг 3 — План (`planner`, режим «план»)

Промпт: пути к `$DIR/agent/context.md`, `.claude/tasks/about.md`, brief и design из `docs/projects/`, если
есть; вариант автора; формат — `~/dev/my-claude-config/playbook/templates/plan-template.md`; выход —
`$DIR/plan.md` и `$DIR/agent/scope.txt` (все файлы, которые шаги создают или меняют, и каталоги тестов).
После агента проверь: план не длиннее 150 строк, у шагов статусы `[ ]`, проверка и номера кейсов,
«Решение» называет вариант автора, каждый файл из шагов есть в `scope.txt`. Не так — перезапусти
планировщика с точным замечанием.

## Шаг 4 — Критика плана (`critic`, точка 1)

Промпт: `agent/context.md`, `plan.md`, brief/design; выход `$DIR/agent/critique1.md`. Затем `planner` в режиме
«правка по критике»: внести «блокирует» и «стоит», «по желанию» — в «Границы»; `scope.txt` обновить.

## Шаг 5 — Согласование плана (остановка 1)

Покажи в чат секцию «Решение», список шагов (строки `- [`) и замечания критика одной строкой каждое.
AskUserQuestion: «Согласовать план?» с вариантами «да», «поправить: …», «поставить стоп-точки на шаги …».
Стоп-точка ставится скриптом: `plan-status.sh <plan.md> <шаг> stop`. Правки плана — через `planner`,
он же обновляет `scope.txt`. После «да» замени в `plan.md` `Статус: черновик` на `Статус: согласован <дата>`.

## Шаг 6 — Кейсы (`planner`, режим «кейсы»)

Промпт: согласованный `plan.md`, формат `playbook/templates/tests-template.md`; выход `$DIR/tests.md`.

## Шаг 7 — Критика кейсов (`critic`, точка 2)

Выход `$DIR/agent/critique2.md`; недостающие кейсы дописать в `tests.md` с пометкой «предложил критик».

## Шаг 8 — Согласование кейсов (остановка 2)

Покажи кейсы. AskUserQuestion: «Согласовать кейсы?» с вариантами «да», «добавить свои: …», «поправить: …».
По правилу 06 автор добавляет хотя бы один свой случай или говорит «случаи твои». После — в `tests.md`
`Статус: согласованы <дата>`. Дальше без остановок.

## Шаг 9 — Реализация по фазам

Для каждой фазы плана по порядку:
1. **RED-тесты фазы.** Стек-тест-райтер (`test-writer` / `go-test-writer` / `vue-test-writer`) получает
   кейсы фазы из `tests.md` и `agent/context.md`, возвращает код тестов. Запиши файлы (их каталоги уже в
   `scope.txt`), запусти через `scripts/helpers/test-summary.sh <команда>`: тесты должны падать по
   правильной причине; ошибка компиляции из-за ещё не написанных классов допустима.
2. **`implementer`.** Промпт: пути к `plan.md`, `tests.md`, `agent/scope.txt`, `agent/context.md`; номер фазы,
   стек, команда тестов. Напомни: требования — только из плана и кейсов, писать — только в файлы из
   `scope.txt`, тесты не редактировать, перед `[#]` остановиться.
3. **После агента.** Прочитай строки шагов фазы в `plan.md`. Появился `[!]` — доложи вопрос и жди ответа.
   Ответ требует файла вне scope — `scope.sh $DIR add <путь>` и перезапусти фазу. Хук спросил про файл
   вне scope во время фазы — тот же порядок: подтверждение пользователя, `scope.sh add`, дальше.
   Агент остановился перед `[#]` — доложи и жди «дальше», затем `plan-status.sh <шаг> todo` и продолжай.
   Иначе — следующая фаза.
4. **В чат после фазы:** только строки `- [` из «Шаги» и последняя строка «Журнала».

## Шаг 10 — Проверка и Sonar

Полный прогон тестов проекта через `test-summary.sh` (`mvn -q test`, `go test ./...`, `npx vitest run`
или из `CLAUDE.md`). Падения чинить по TDD; тесты не менять без вопроса.

Рабочий Java-проект при заданных `SONAR_HOST_URL` и `SONAR_TOKEN`: `scripts/helpers/sonar-local.sh`
→ `$DIR/agent/sonar.md`. Цикл исправлений: собственные правила (`nurtelecomconventionjavarules`) и
встроенные BLOCKER/HIGH — исправить; MEDIUM механические (импорт, модификатор, дубликат) — исправить,
требующие переделки — спросить; LOW, INFO и спорные — один вопрос пакетом: исправить / пропустить /
отложить. Ответы записать в `agent/sonar.md`. Повторный прогон после правок; не больше двух кругов.
Sonar не настроен — строка в журнале и дальше.

## Шаг 11 — Критика результата и ревью (параллельно)

Запусти одновременно: `critic` (точка 3 → `$DIR/agent/critique3.md`), `convention-reviewer` (дифф +
`agent/sonar.md`) и стек-ревьюер (`java-reviewer` / `go-reviewer` / `vue-reviewer`; при миграциях ещё
`migration-reviewer`). Слей находки в `$DIR/agent/review-raw-1.md`: сначала коды конвенции, затем CRITICAL,
WARNING, SUGGESTION, блоки «Упростить» и «Тесты», замечания критика; дубли убрать.

Фиксер — свежий `implementer` с промптом «правки по ревью» и тем же `scope.txt`: закрыть «блокирует»,
«стоит», CRITICAL и WARNING по TDD; новый кейс — в `tests.md` и на согласование. Повторное ревью — один
раз (`agent/review-raw-2.md`). Больше двух итераций не делать: остаток — «известные замечания».

Итог для человека — `$DIR/review.md`, не длиннее 40 строк: находки по серьёзности с пометкой
«закрыто», «осталось» или «отклонено: причина».

## Шаг 12 — Итог

`scope.sh $DIR done`. Сводка в `$DIR/summary.md` и в чат: что сделано и какие файлы; тесты; Sonar; ревью
(итерации, что осталось); вопросы, на которые отвечал пользователь; время от старта. Доработка —
`/task <описание>` на той же ветке: каталог `<ключ>-2` создастся сам. Коммит — по правилу 09: только
локальная ветка, и только если пользователь попросил.

## Ошибки

- Подагент завис или не дописал артефакт — перезапусти шаг свежим агентом с более точной инструкцией.
- Не получается написать падающий тест первым — пауза и вопрос (правило 06), не пропускать молча.
- Хвосты после завершения: мелочь — `/quick` или `/fix`; недоделанный кусок — `/task <описание>` на той же ветке.
