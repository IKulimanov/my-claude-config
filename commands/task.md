# /task — оркестратор больших задач

Главный поток тонкий: держит список фаз, статусы и короткие сводки. Работа идёт в свежих подагентах,
передача между шагами — только файлы в `.ai/<проект>/<буква>/`. Остановок две: согласование плана
и согласование кейсов; дальше — только стоп-точки `[#]`, поставленные оператором, и `[!]`, когда агент
упёрся.

Аргументы: `$ARGUMENTS` = "$ARGUMENTS". Пусто — спроси, что делать.

## Шаг 0 — Сортировка

Определи по тексту, что это, и не запускай лишнего:
- вопрос, анализ, объяснение без изменения кода → ответь сам (при нужде один `Explore`) и остановись;
- правка в одно предложение без изменения поведения → скажи «это /quick» и сделай по `/quick`;
- баг или малое изменение поведения → «это /fix», сделай по `/fix`;
- фича в один контекст (одна фаза, не больше 8 правок файлов) → сделай по `/feature`;
- иначе — полный цикл ниже. Сомневаешься между `/feature` и `/task` — бери `/feature`.

Правило 08: если в постановке нет варианта автора («думаю», «предлагаю», «мой вариант») — один
вопрос через AskUserQuestion: «Твой вариант в 1–3 строках?» с вариантами «есть: …», «не знаю — предложи».
Follow-up вида «продолжай», «следующая фаза» — не спрашивать. Запомни время старта.

## Шаг 1 — Каталог задачи

Первый токен аргументов — имя проекта в `.ai/`? Есть `.ai/<токен>/about.md` → follow-up: проект = токен,
описание = остаток, буква = следующая. Нет → новый проект: короткое kebab-имя, буква `a`.

```bash
DIR=$(~/dev/my-claude-config/scripts/helpers/ai-init.sh "<проект>" "<буква>")
```

Файлы задачи: `about.md` (слепок проекта, переписывается), `context.md`, `plan.md`, `tests.md`,
`critique1.md`…`critique3.md`, `sonar.md`, `review1.md`, `review2.md`.

## Шаг 2 — Контекст (`Explore`)

Промпт: сначала `~/dev/my-claude-config/shared/stack-detection.md`; прочитать локальный `CLAUDE.md`
и весь код, относящийся к задаче; для follow-up — прочитать `about.md` и `context.md` предыдущей буквы.
Написать `about.md` (проект как будто уже готов: архитектура, решения, области кода, без «TODO») и
`context.md` — не длиннее 300 строк: описание задачи, вариант автора, относящиеся файлы с диапазонами
строк, паттерны, структуры данных, внешние контракты, команды сборки и тестов. Ссылки на код вместо
цитат. Проверь, что оба файла написаны и читаются.

## Шаг 3 — План (`planner`, режим «план»)

Промпт: пути к `context.md`, `about.md`, brief и design из `docs/projects/`, если есть; вариант автора;
формат — `~/dev/my-claude-config/playbook/templates/plan-template.md`. После агента проверь: план не
длиннее 150 строк, у шагов статусы `[ ]`, проверка и номера кейсов, «Решение» называет вариант автора.
Не так — перезапусти планировщика с точным замечанием.

## Шаг 4 — Критика плана (`critic`, точка 1)

Промпт: `context.md`, `plan.md`, brief/design; выход `critique1.md`. Затем `planner` в режиме «правка
по критике»: внести «блокирует» и «стоит», «по желанию» — в «Границы».

## Шаг 5 — Согласование плана (остановка 1)

Покажи в чат секцию «Решение», список шагов (строки `- [`) и замечания критика одной строкой каждое.
AskUserQuestion: «Согласовать план?» с вариантами «да», «поправить: …», «поставить стоп-точки на шаги …».
Стоп-точка ставится скриптом: `plan-status.sh <plan.md> <шаг> stop`. После «да» замени в `plan.md`
`Статус: черновик` на `Статус: согласован <дата>`.

## Шаг 6 — Кейсы (`planner`, режим «кейсы»)

Промпт: согласованный `plan.md`, формат `playbook/templates/tests-template.md`; выход `tests.md`.

## Шаг 7 — Критика кейсов (`critic`, точка 2)

Выход `critique2.md`; недостающие кейсы дописать в `tests.md` с пометкой «предложил критик».

## Шаг 8 — Согласование кейсов (остановка 2)

Покажи кейсы. AskUserQuestion: «Согласовать кейсы?» с вариантами «да», «добавить свои: …», «поправить: …».
По правилу 06 автор добавляет хотя бы один свой случай или говорит «случаи твои». После — в `tests.md`
`Статус: согласованы <дата>`. Дальше без остановок.

## Шаг 9 — Реализация по фазам

Для каждой фазы плана по порядку:
1. **RED-тесты фазы.** Стек-тест-райтер (`test-writer` / `go-test-writer` / `vue-test-writer`) получает
   кейсы фазы из `tests.md` и `context.md`, возвращает код тестов. Запиши файлы, запусти через
   `scripts/helpers/test-summary.sh <команда>`: тесты должны падать по правильной причине; ошибка
   компиляции из-за ещё не написанных классов допустима.
2. **`implementer`.** Промпт: пути к `plan.md` и `tests.md`, номер фазы, стек, команда тестов, напоминание
   про запрет редактировать тесты и про `[#]`.
3. **После агента.** Прочитай строки шагов фазы в `plan.md`. Появился `[!]` — доложи вопрос и жди ответа.
   Агент остановился перед `[#]` — доложи и жди «дальше», затем `plan-status.sh <шаг> todo` и продолжай.
   Иначе — следующая фаза.
4. **В чат после фазы:** только строки `- [` из «Шаги» и последняя строка «Журнала».

## Шаг 10 — Проверка и Sonar

Полный прогон тестов проекта через `test-summary.sh` (`mvn -q test`, `go test ./...`, `npx vitest run`
или из `CLAUDE.md`). Падения чинить по TDD; тесты не менять без вопроса.

Рабочий Java-проект при заданных `SONAR_HOST_URL` и `SONAR_TOKEN`: `scripts/helpers/sonar-local.sh`
→ `sonar.md`. Цикл исправлений: собственные правила (`nurtelecomconventionjavarules`) и встроенные
BLOCKER/HIGH — исправить; MEDIUM механические (импорт, модификатор, дубликат) — исправить, требующие
переделки — спросить; LOW, INFO и спорные — один вопрос пакетом: исправить / пропустить / отложить.
Ответы записать в `sonar.md`. Повторный прогон после правок; не больше двух кругов. Sonar не настроен —
строка в журнале и дальше.

## Шаг 11 — Критика результата и ревью (параллельно)

Запусти одновременно: `critic` (точка 3 → `critique3.md`), `convention-reviewer` (дифф + `sonar.md`) и
стек-ревьюер (`java-reviewer` / `go-reviewer` / `vue-reviewer`; при миграциях ещё `migration-reviewer`).
Слей находки в `review1.md`: сначала коды конвенции, затем CRITICAL, WARNING, SUGGESTION, блоки
«Упростить» и «Тесты», замечания критика; дубли убрать.

Фиксер — свежий `implementer` с промптом «правки по ревью»: закрыть «блокирует», «стоит», CRITICAL
и WARNING по TDD; новый кейс — в `tests.md` и на согласование. Повторное ревью — один раз (`review2.md`).
Больше двух итераций не делать: остаток — «известные замечания» в журнале.

## Шаг 12 — Итог

Сводка: что сделано и какие файлы; тесты; Sonar; ревью (итерации, что осталось); время от старта;
имя проекта для follow-up: `/task <проект> <описание>`. Коммит — по правилу 09: только локальная ветка,
и только если пользователь попросил.

## Ошибки

- Подагент завис или не дописал артефакт — перезапусти шаг свежим агентом с более точной инструкцией.
- Не получается написать падающий тест первым — пауза и вопрос (правило 06), не пропускать молча.
- Хвосты после завершения: мелочь — `/quick` или `/fix`; недоделанный кусок — `/task <проект> <описание>`.
