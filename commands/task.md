# Task — многофазный оркестратор больших фич

Для **крупных** фич, которые не помещаются в один контекст и идут несколькими последовательными
задачами. Главный поток остаётся тонким: он держит только список задач и компактные сводки фаз. Вся
тяжёлая работа (контекст, план, реализация, ревью) идёт в свежих подагентах, чей контекст
выбрасывается. Передача между фазами — **только файлы на диске** в `.ai/`, не история чата.

Для обычной работы используй `/feature` (он легче). `/task` — осознанный выбор под большой объём.

Идея и структура заимствованы из конфигурации Telegram Desktop, но с ключевым отличием: **здесь
действует TDD iron-law** (rule 06) — на каждой фазе реализации падающий тест пишется ПЕРЕД прод-кодом.

**Аргументы:** `$ARGUMENTS` = "$ARGUMENTS". Если пусто — спроси, что реализовать.

## Конвенция артефактов (тяжёлый вариант, см. `~/.claude/my-claude-config/docs/AI_ARTIFACTS.md`)

```
.ai/<project>/
  about.md            # вневременной слепок проекта; переписывается на каждой задаче
  a/                  # первая задача (буквы a, b, c, ...)
    context.md        # самодостаточный контекст; подагенты читают его вместо чата
    plan.md
    review1.md        # до 3 итераций ревью
  b/ ...
```

## Фаза 0 — Подготовка

1. Запомни время старта (`date`) как `$START_TIME` — покажешь общее время в конце.
2. **Детект follow-up (СНАЧАЛА).** Возьми первый токен `$ARGUMENTS` как `FIRST_TOKEN`. Параллельно:
   `ls .ai/` и `ls .ai/<FIRST_TOKEN>/about.md`.
   - Файл есть → **follow-up**: проект = `FIRST_TOKEN`, описание = остаток `$ARGUMENTS`. Новая буква =
     следующая после максимальной существующей.
   - Файла нет → **новый проект**: выбери короткое kebab-имя, не конфликтующее со списком. Буква = `a`.
3. Создай скелет:
   ```bash
   DIR=$(~/.claude/my-claude-config/scripts/helpers/ai-init.sh "<project>" "<letter>")  # .ai/<project>/<letter>/ + gitignore
   ```

## Фаза 1 — Сбор контекста (свежий подагент)

Перед запуском подагентов — rule 08: если в `$ARGUMENTS` нет собственного варианта решения/гипотезы
пользователя, задай один вопрос («Твой первый вариант?»); ответ положи в `context.md` как «Вариант автора».
Follow-up вида «продолжай / следующая фаза» — не спрашивать.

Запусти агента `Explore` (read-only). В промпте:
- Сначала следуй `~/.claude/my-claude-config/docs/shared/stack-detection.md` (детект стека, нужные скилы).
- Прочитай локальный `CLAUDE.md` и весь код, релевантный задаче. Лучше прочитать больше.
- Для нового проекта напиши ДВА файла; для follow-up — сначала прочитай `.ai/<project>/about.md` и
  `context.md` предыдущей буквы, пойми, что уже сделано, затем напиши файлы.

**Файл 1 — `.ai/<project>/about.md`** (вневременной слепок; для follow-up — ПЕРЕПИСАТЬ, не дописывать):
Project / Architecture / Key Design Decisions / Relevant Codebase Areas. Описывай так, будто всё уже
сделано — без «TODO», «текущее состояние», «пока не реализовано».

**Файл 2 — `.ai/<project>/<letter>/context.md`** (главный документ; его одного хватает downstream-фазам):
Task Description · Relevant Files (пути + диапазоны строк) · Key Code Patterns · Data Structures ·
External contracts (API/Kafka/DB) · Build/Test commands · Reference Implementations. Самодостаточно:
агент с нулевым контекстом должен всё понять, читая только этот файл.

После завершения прочитай оба файла — проверь, что написаны нормально.

## Фаза 2 — Планирование (свежий подагент)

Запусти агента `Plan`. В промпте: прочитать `.ai/<project>/<letter>/context.md` и упомянутые в нём
исходники, затем написать `.ai/<project>/<letter>/plan.md` по формату
`~/.claude/my-claude-config/docs/shared/plan-template.md`. **Секция «Каким путём идём» обязательна** —
план должен объяснять выбранный подход и почему именно он (какие варианты отклонили), простым
русским, а не только перечислять шаги. Каждый шаг — конкретный (точные пути, имена функций, что и
где добавить/изменить) с проверкой. Группируй шаги в фазы, если их больше ~8. В конце plan.md —
секция Status с чек-боксами по фазам + строкой про тесты и ревью.

## Фаза 3 — Оценка плана (свежий подагент)

Запусти агента `Plan`. Прочитать `context.md` + `plan.md` + реальные исходники. Проверить:
корректность путей/имён, полноту (пропущенные шаги, краевые случаи), минимизацию дублирования,
соответствие конвенции стека, размер фаз (одна фаза = одна сессия одного агента; больше ~8-10
изменений — дробить), **и что секция «Каким путём идём» реально объясняет решение понятным русским,
а не пересказывает шаги**. Обновить `plan.md`; внизу добавить `Assessed: yes` и `Phases: <N>`.

## Фаза 4 — Реализация (свежий подагент на каждую фазу плана) — TDD iron-law

Прочитай `plan.md` сам, пойми фазы. Для каждой невыполненной фазы запусти свежего агента
(`general-purpose`). **Порядок для каждого шага — RED → GREEN → REFACTOR (rule 06):**

1. **RED:** падающий тест пишется ПЕРВЫМ. Делегируй дизайн теста профильному агенту: Java/Spring →
   `test-writer`, Go → `go-test-writer`, Vue/Vite → `vue-test-writer` (они read-only, возвращают код
   теста). Запиши тест в файл, запусти, убедись, что падает по правильной причине (не из-за
   компиляции). Для прочих стеков — напиши падающий тест напрямую. Либо тест пишет пользователь, если
   он взял это на себя (см. rule 06).
2. **GREEN:** минимальный прод-код, чтобы тест прошёл. Запусти — убедись, что зелёный.
3. **REFACTOR:** почисти код и тест без смены поведения. Перезапусти тесты.

Правила фазы: следуй плану и конвенции стека; НЕ трогай `.ai/`-файлы, кроме секции Status в `plan.md`
(отметь фазу `[x]`); не работай над другими фазами. После каждого агента прочитай `plan.md` и проверь,
что статус обновлён. Если что-то пошло не так — пауза и доклад пользователю.

## Фаза 5 — Валидация

Запусти проверку по стеку из репозитория (или из `CLAUDE.md`):
- **Java**: `mvn verify`
- **Go**: `go test ./... && go vet ./...`
- **Vue/Vite**: `npm run test` (или `npx vitest run`)

Почини падения (с соблюдением TDD: если меняешь поведение — тест первым). Отметь Build/тесты в Status.

## Фаза 6 — Цикл ревью (до 3 итераций)

`R = 1`. Делегируй профильному ревьюеру (`java-reviewer` / `go-reviewer` / `vue-reviewer`; прочие
стеки или если профильный агент недоступен — ревью напрямую по `~/.claude/my-claude-config/commands/review.md`).
Передай агенту дифф (`git diff`) и формат находок. **Для Java в профиле work (rule «Профили проектов»)
ревьюер обязан сверить дифф с Sonar-выжимкой**
`~/.claude/my-claude-config/skills/java-service-convention/references/sonar-rules.md` по кодам
(LANG-/SPR-/DB-) — это предфильтр перед CI Sonar, финальный вердикт даёт quality gate.
`sonar-rules.md` — внутренний материал: цитируй коды правил, не вставляй его текст/примеры
дословно в артефакты ревью (`.ai/`, отчёты).
Агент пишет вердикт в `.ai/<project>/<letter>/review<R>.md`.
- `APPROVED` → выход из цикла.
- Иначе → свежий агент-фиксер чинит находки (соблюдая TDD), затем перезапуск валидации. `R = R + 1`;
  если `R > 3` — выход (зафиксируй остаток как известные замечания).

Отметь Code review в Status.

## Завершение

1. Сводка по `plan.md`: что сделано, какие файлы изменены/созданы.
2. Итоги ревью: сколько итераций, что найдено и починено.
3. Общее время с `$START_TIME` (`Xh Ym Zs`, опуская нулевые компоненты).
4. Напомни имя проекта для follow-up: `/task <project> <описание доработки>`.

## После задачи — что делать с недоделками

`/task` уже содержит цикл ревью (Фаза 6, до 3 итераций) и валидацию (Фаза 5). Но если после
завершения остались хвосты (что-то не доделано или сделано плохо), выбирай команду по размеру
проблемы — не запускай тяжёлый `/task` заново ради мелочи:

1. **Сначала получи объективный список.** Запусти `/review` на итоговом диффе — он выдаст находки
   по стеку (баги, нарушения конвенции, пропущенные тесты). Не чини «на глаз».
2. **Дальше — по размеру каждой находки:**
   - Мелочь (пропущенная функция, краевой случай, мелкая правка) → `/fix`. Лёгкая команда, минимум
     контекста.
   - Работает неправильно, непонятно почему → `/fix` (шаг 3a: сначала причина, потом правка).
   - Целый недоделанный кусок или новая под-задача → `/task <project> <описание доработки>`
     (follow-up: переиспользует контекст в `.ai/<project>/`), либо `/feature`, если это отдельная
     самостоятельная возможность.
   - Только нарушения конвенции/стиля → `/convention-check` (Java) или `/review`, затем `/fix`.
3. **Правило масштаба:** `/task` — большой объём на несколько контекстов; `/feature` — обычная
   возможность; `/fix` — мелкая правка и разбор бага; `/review` — получить список
   проблем. Хвост почти всегда чинится через `/fix` или follow-up `/task`, а не полным перезапуском.

## Обработка ошибок

- Если подагент завис или не дописал артефакт — перезапусти эту фазу свежим агентом с более точными
  инструкциями; не «вытягивай» pre-build фазу в главный поток без необходимости.
- Если `context.md`/`plan.md` написаны плохо — перезапусти соответствующую фазу.
- Если не можешь написать падающий тест первым (genuine UI-only без поведения) — пауза и обсуждение с
  пользователем (rule 06). Не пропускай тест «по-тихому».
