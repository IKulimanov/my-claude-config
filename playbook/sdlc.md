## Введение

Документ описывает процесс Java-разработки в ОРСП (Отдел развития сервисов и продуктов): путь задачи от появления до релиза и поддержки.
Дата документа — 14 мая 2026 г. На титуле версия 0.0.2, в блоке «Информация о документе» — 0.0.1.

### Глоссарий
- dev-задача — задача в проекте ORSP, в которой ведётся вся разработка по бизнес-задаче: статусы, подзадачи, оценки, учёт времени.
- подзадача — единица декомпозиции dev-задачи; отдельный логический кусок работ с чётким результатом; по подзадачам ведутся реализация и
  учёт времени.
- бизнес-эпик — эпик в проекте бизнеса; инициирует разработку, содержит контекст и требования бизнеса.
- технический эпик — эпик по инициативе команды разработки (например, в проекте DEVDIT) для технических работ.
- Bug-задача — задача на дефект, найденный в тестировании или эксплуатации; проходит SDLC отдельно от исходной dev-задачи.
- дежурство — формат эксплуатации: дежурный разработчик отвечает за стабильную работу сервисов 1–3 дня.
- Менеджер по задаче — представитель бизнеса, ответственный за бизнес-задачу со стороны заказчика.
- Руководитель команды — тимлид Java-команды; к нему идут согласования, эскалации и паузы задачи.
- Разработчик, ответственный по задаче — главный по объёмной задаче с несколькими участниками; через него идут уточнения требований.

### Цель и формат документа
- Цели: описать текущий процесс прохождения задачи с точки зрения Разработчика; дополнить Должностные инструкции Разработчиков; дать
  рекомендации по работе с задачами.
- Документ построен по этапам жизненного цикла задачи. Каждый раздел: что происходит на этапе, с чем работает Разработчик, какие инструменты
  и системы используются.

### Как организована работа
- Работа не по чётким Scrum или Kanban; спринтов и фиксированных итераций нет; задачи идут непрерывным потоком.
- Каждый этап применяется на уровне отдельной бизнес-задачи. Возвращённая в работу задача может пройти этапы повторно.

### Этапы SDLC
1. Создание dev-задачи и анализ — создание dev-задачи, изучение требований, проектирование, оценка.
2. Реализация — разработка по подзадачам, фиксация изменений в системе контроля версий, учёт времени.
3. Тестирование — проверка функционала разработчиком или отделом тестирования.
4. Документирование — актуализация документации, проект в Backstage, публикация в TechDocs.
5. Релиз и деплой — выкладка изменений, настройка мониторинга.
6. Эксплуатация и сопровождение — дежурства, заявки пользователей, реакция на инциденты.

Чтение диаграммы процесса:
- сплошные стрелки — основной поток задачи; ромбы — точки решения (есть ли вопросы, кто тестирует, тип задачи);
- пунктирные стрелки — исключения и циклы: возврат к уточнению требований при новых вопросах, Пауза при отсутствии ответа более 8 рабочих
  часов, возврат новой задачи или Bug-задачи в начало SDLC;
- возврат из тестирования в реализацию — при замечаниях или Bug-задачах по dev-задаче;
- новая задача или Bug-задача из эксплуатации проходит SDLC с начала; исходная dev-задача не переоткрывается.

Дополнительные разделы: Рекомендации по коммуникациям; Использование LLM (правила для чата, IDE-интеграции, агентов; применяются на любом
этапе, если LLM используется).

### Пример прохождения задачи
- Бизнес-эпик DEVMP-73 «Доработка отображения PUG тарифов в Мой О!» (приоритет High, автор — менеджер по задаче): изменить отображение
  стоимости и даты списания в PUG-тарифах для добавленных (дочерних) номеров в «Мой О!».
- dev-задача ORSP-1556 «LK. Реализация функционала по определению номеров PUG» в проекте ORSP, привязана к эпику через Epic Link.
- Инициация: эпик создан 20/янв/26, dev-задача — 22/янв/26; в описание перенесены ссылки на confluence-страницы (экраны мобильного
  приложения, логика выбора цены тарифа и даты списания) — чтобы зафиксировать входные материалы на момент старта.
- Анализ: подзадача «Анализ задачи»; изучены требования эпика и материалы; зафиксировано: определять PUG-номера на бэкенде, корректно
  показывать стоимость и дату списания для дочерних номеров.
- Проектирование: дорабатывать существующий функционал без нового сервиса; подзадачи реализации «Доработка кэша тарифов и свойств» и
  «Реализация логики проверки PUG номеров».
- Оценка: у каждой подзадачи оценка в Jira; сумма по dev-задаче — 1d 7h (около 15 рабочих часов).
- Реализация: подзадачи последовательно, коммиты привязаны к подзадачам, время в Jira; факт — 2d 5h (около 21 часа). Расхождение оценки и
  факта — нормальная ситуация; главное — факт зафиксирован и виден в задаче.
- Тестирование: после проверок разработчиком и merge ветки задачи в staging эпик передан в отдел тестирования (задачи DEVQA в эпике).
- Релиз и деплой: merge ветки задачи в master по правилам работы с Git.
- Эксплуатация: dev-задача в статусе «Готово», функционал в продакшене. Новые проблемы — отдельные Bug-задачи через SDLC заново; ORSP-1556
  не переоткрывается.

### Структура задач
- Бизнес-эпик живёт в проекте бизнеса и инициирует работу.
- dev-задача в ORSP держит всю разработку: статусы, оценки, учёт времени, связи с подзадачами.

- Bug-задача создаётся отдельно при дефекте в тестировании или эксплуатации и проходит SDLC заново; исходная dev-задача не переоткрывается.

## Инициация и поступление задач

Задачи приходят в ОРСП как бизнес-эпики от подразделения-заказчика. Разработчик включается на следующем этапе — при создании dev-задачи в
проекте ORSP.

### Кто создаёт бизнес-задачи
- Эпик создаёт инициатор: бизнес-заказчик из Подразделения или менеджер проектов Коммерческой дирекции.
- Канал передачи в Разработку — список задач MP: его ведут менеджеры проектов, задачи ранжированы по приоритетам с учётом интересов всех
  подразделений Компании.
- Статусы бизнес-эпика двигает только инициатор: создаёт эпик в Jira-проекте своего подразделения; переводит в «В работе»; решает о начале
  тестирования; сам уведомляет группу тестирования и согласует с ней приоритет; решает о выпуске в Production.
- Разработчик не двигает бизнес-эпик; его зона — dev-задача в ORSP. Действие инициатора (например, передачу на тестирование) запрашивайте у
  Менеджера по задаче.

поступления задачи к Разработчику в источнике показан только схемой.

### Что должно быть в бизнес-эпике до передачи в разработку
- описание целей и мотивации задачи;
- ссылки на ТЗ, спецификации, макеты (если есть);
- ссылки на внешние ресурсы (openAPI-спецификации, документация внешних систем), если нужна интеграция;
- контакты ответственного со стороны бизнеса (Менеджера по задаче);
- приоритет.

Нехватка чего-то — не блокер анализа; недостающее запросите у Менеджера по задаче на шаге изучения требований.

### Чек-лист завершения этапа
- бизнес-эпик создан в Jira-проекте подразделения-инициатора и переведён в «В работе»;
- эпик передан в команду ОРСП.

### Частые ошибки
- Самостоятельно переводить бизнес-эпик в новый статус («На тестирование», «Готово») → рассинхрон статусов бизнеса и разработки, задача
  уходит в тестирование без согласования приоритета. Статусы эпика двигает только инициатор; Разработчик — только dev-задачу и подзадачи.

## Создание dev-задачи и анализ

### Создание dev-задачи
После согласования бизнес-задачи и передачи в разработку Разработчик создаёт dev-задачу:
- в проекте ORSP;
- Эпик задачи — бизнес-задача, которая инициировала работу;
- в описание перенесена информация из бизнес-задачи, относящаяся к работам бэкенд-команды ОРСП;
- контент внешних ресурсов из Эпика (openAPI-спецификации, документация внешней системы) настоятельно рекомендуется перенести в описание —
  чтобы закрепить их состояние на момент начала разработки и не зависеть от изменений во внешних системах;
- приложенное к Эпику ТЗ рекомендуется скопировать в файлы dev-задачи — чтобы зафиксировать версию ТЗ.

Частая ошибка: dev-задача в проекте бизнеса (DEVMP, DEVBACK) → задачи команды теряются в чужом проекте, отчёты по ORSP не сходятся, время
логируется не туда. dev-задачи ОРСП всегда в ORSP, связь с бизнес-эпиком через Epic Link.

### Анализ. Общее
Разработчик изучает бизнес-задачу, определяет подходы к реализации, выявляет сложности и риски, корректирует описание dev-задачи, оценивает
трудозатраты. Три шага строго по порядку:
1. Изучение требований — погружение в задачу, фиксация неясностей, получение ответов.
2. Проектирование — подход к реализации, декомпозиция на подзадачи.
3. Оценка — каждая подзадача в часах.

Возврат из проектирования к изучению требований при новых вопросах — нормальный сценарий.
- Старт этапа: dev-задача создана в ORSP и переведена в рабочий статус («В работе»).
- Лимит длительности анализа — 7 часов для задач без создания новых сервисов, без взаимодействия трёх и более систем и без тотального
  рефакторинга; не уложились — зафиксируйте причины и сообщите Руководителю команды.
- Для сложных задач превышение лимита допустимо, но анализ не должен зависать без результата и дальнейших действий.
- Обращение за помощью: не получается выбрать решение, решить проблему или разобраться в функционале дольше 4 часов — консультация у команды
  (правила — в Рекомендациях по коммуникациям).
- LLM: анализ требований, архитектурный набросок, декомпозиция — типовые места применения; правила (собственный черновик до запроса,
  проверка фактов, формат критики) — в разделе про LLM.

Чек-лист завершения этапа анализа (все три шага):
- подзадача анализа выполнена и закрыта с зафиксированным временем;
- нет открытых вопросов по требованиям;
- задача декомпозирована на подзадачи (если реализация требует более 7 часов);
- каждая подзадача описана с учётом ответов на вопросы и уточнений;
- каждая подзадача имеет оценку в часах в Jira.

### Анализ. Изучение требований
Разработчик: создаёт отдельную подзадачу для анализа; изучает описание задачи, вложения, бизнес-эпик; проверяет входные требования и
ограничения; фиксирует неполные, противоречивые и неясные моменты.

Уточнение требований:
- вопросы формулируются и направляются Менеджеру по задаче через разработчика, ответственного по задаче (объёмная задача с несколькими
  участниками), Руководителя команды, начальника отдела или самостоятельно (если такой способ согласован по задаче);
- в вопросе — критичность и желаемый срок ответа (правила — в Рекомендациях по коммуникациям);
- нет ответа 8 рабочих часов — перевести задачу в Паузу с указанием причины и сообщить Руководителю команды.

Чек-лист: подзадача анализа создана; описание, вложения и бизнес-эпик изучены; входные требования и ограничения проверены; неясности
зафиксированы; получены ответы на вопросы (или приняты допущения).

Частая ошибка: не уточнять непонятные или противоречивые требования в надежде разобраться по ходу → реализация не того, переделки, потеря
времени. Все неясности — в вопросы; ответы — до завершения анализа.

### Анализ. Проектирование
Начинается, когда требования полностью понятны и открытых вопросов нет; ведётся в подзадаче Анализа. Разработчик:
- определяет общий подход к реализации;
- решает: доработка существующих сервисов или создание нового;
- продумывает взаимодействие компонентов;
- декомпозирует задачу на подзадачи реализации и формирует полный набор, включая инфраструктурные (заявка на деплой, кастомные метрики,
  health-checks);
- обязательно создаёт подзадачу на документирование независимо от ожидаемого объёма;
- описывает каждую подзадачу по требованиям к описанию задач.

Архитектура:
- новое приложение или сервис — схема обязательна: взаимодействие компонентов, внешние интеграции, основные потоки данных;
- доработка существующих сервисов — при необходимости: затронуто взаимодействие нескольких систем или существенно меняется логика;
- есть заготовка Draw.io для диаграммы компонентов.

Декомпозиция: реализация дольше 7 часов — разбивать на подзадачи; каждая подзадача укладывается в те же 7 часов, иначе дробится дальше;
подзадача — отдельный логический кусок работ с чётким результатом.

Подзадача «Документирование» — всегда: оценка до 7 часов — остаётся подзадачей внутри dev-задачи; больше 7 часов — отдельная Task в ORSP,
обязательно связанная с dev-задачей.

Чек-лист:
- подход определён; решение «доработка или новый сервис» принято;
- задача полностью декомпозирована (порог дробления — 7); все подзадачи созданы в dev-задаче и описаны;
- созданы подзадачи на технические аспекты (метрики, health-checks, заявка на деплой);
- создана подзадача на документирование (или Task в ORSP при оценке >7 часов);
- для нового приложения или сервиса подготовлена компонентная диаграмма.

Частые ошибки:
- Слишком абстрактные подзадачи → неясен объём, трудно оценить время, теряется прозрачность. Формулируйте с чётким и подробным описанием.
- Болванки с названиями без описания → неясность для команды (и для себя после выходных), сложности с оценкой и планированием. Описывайте
  так, чтобы контекст восстанавливался спустя долгое время.
- Нет подзадач на технические аспекты (метрики, health-checks, заявка на деплой) → делаются впопыхах в последний момент. Создавайте их сразу
  при проектировании.
- Нет архитектуры для нового сервиса → нет общего понимания, сложно согласовать подход и передать знания. Даже простая схема лучше её
  отсутствия.
- Нет подзадачи на документирование → документация «когда-нибудь» или никогда, знания теряются. Заводите всегда; при оценке >7 часов —
  отдельная Task в ORSP, связанная с dev-задачей.

### Анализ. Оценка
Начинается после проектирования, когда объём каждой подзадачи понятен. Разработчик оценивает каждую подзадачу в часах, вносит оценку в поле
подзадачи в Jira, при необходимости согласует с Руководителем команды.

Правила оценки:
- оценивать каждую подзадачу, а не только основную задачу;
- подзадача не должна превышать 6–7 часов реализации; не укладывается — декомпозировать дополнительно;
- зафиксировать оценки до начала реализации;
- буфер на «непредвиденные трудности» — не более 10% от оценки задачи или подзадачи.

Чек-лист: у каждой подзадачи оценка в часах в Jira; оценки зафиксированы до начала реализации; заложен буфер (≤10% от оценки); общая оценка
(сумма оценок подзадач) согласована с Руководителем команды.

Частые ошибки:
- Оценка «на глаз» без продумывания деталей → задача занимает значительно больше времени. Мысленно пройдите шаги реализации; при неясности —
  оценка с запасом, но не более 10% от изначальной.
- Слишком мелкие подзадачи (меньше 2 часов) → бюрократия, время на переключения и администрирование. Целевой размер — от 3 до 6–7 часов.
- Не учтено время на проверку собственного кода → подзадача формально готова, код с ошибками. Закладывайте время на код и на его проверку.
- Оценки не внесены в задачу → нельзя отследить прогресс и сравнить план с фактом. Вносите в Jira сразу после оценки.

Источник: SDLC-Orsp-0_0_2.pdf, с. 9–13

## Реализация

Разработка по подзадачам, фиксация изменений в системе контроля версий, учёт времени. Начинается после оценки, когда все подзадачи имеют
зафиксированные оценки; ведётся по подзадачам внутри dev-задачи.

Разработчик: берёт подзадачи из основной задачи; фиксирует результаты в системе контроля версий; привязывает каждый коммит к задаче или
подзадаче; ведёт учёт времени по подзадачам; закрывает подзадачи по факту завершения работ.

Параллельная работа: в работе одна подзадача одномоментно — проще фокус, быстрее завершение; несколько подзадач параллельно — только в
исключительных случаях.

### Привязка коммитов к задачам
Каждый коммит привязан к задаче или подзадаче: видно, какие изменения относятся к задаче; проще искать причины проблем; процесс прозрачен.
Формат commit-message:

```
TASKCODE-123: Краткое описание изменений на русском языке

опциональное расширенное описание изменений. обязательно после одной пустой строки после основного описания.
```

### Учёт рабочего времени
- Способы: «Вести журнал работы» в Jira; Tempo в Jira; веб-хук интеграция проекта в GitLab; Tasks и учёт времени в IDEA.
- При ручном учёте — минимум дважды в день: перед обедом (12:30–13:00) и перед концом рабочего дня (17:30–18:00). Так часы не забываются,
  записи не теряются, меньше вопросов от Руководителя команды.

### Обращение за помощью и LLM
- Не получается выбрать решение, решить проблему или разобраться дольше 4 часов — консультация у команды.
- LLM для генерации кода, ревью или агента: размер итераций, чтение диффа, scope для агентов, подача командных конвенций — в разделе про
  LLM.

### Чек-лист завершения этапа
- все подзадачи реализации закрыты;
- все изменения закоммичены и привязаны к задачам;
- фактическое время учтено;
- нет незавершённых подзадач по задаче.

### Частые ошибки
- Большие изменения одним коммитом → трудно читать историю, делать ревью, откатывать конкретное изменение. Небольшие логические коммиты,
  каждый — завершённый кусок функциональности.
- Логировать время раз в несколько дней → детали забываются, учёт неточный. Дважды в день в установленное время.
- Несколько подзадач параллельно без необходимости → рассеянное внимание, ниже продуктивность. Закрыли — берите следующую.
- Не обращаться за помощью → часы на поиск, когда коллега подсказал бы за 15 минут. Правило 4 часов.

Источник: SDLC-Orsp-0_0_2.pdf, с. 14–15

## Тестирование

Проверка корректности функционала и соответствия требованиям. Выполняет Разработчик или подразделение тестирования: Отдел тестирования ДИТ
(Jira-проект TST) или Группа тестирования Разработки (Jira-проект DEVQA). Начинается после закрытия всех подзадач реализации; ведётся внутри
dev-задачи.

### Кто тестирует
Два независимых фактора:
- тип эпика (бизнес-эпик или технический) — как задача попадает на тестирование: через project-менеджера или через Руководителя команды;
- область задачи (NurCRM, МойО, тарифы и т.д.) — в какое подразделение передаётся.

Эпик любого типа может уйти в любое из двух подразделений; выбор только по области:
- Отдел тестирования ДИТ (TST) — NurCRM, Целевой маркетинг, ОПиО, тарифы / услуги / абонент Сотового оператора.
- Группа тестирования Разработки (DEVQA) — приложение МойО и его бэкенды, прочие внутренние задачи Службы разработки и ОРСП.
- Задача на стыке областей (например, изменение тарифа, видимое и в МойО, и в NurCRM) — уточнить у Руководителя команды; возможно,
  понадобятся оба подразделения.

### Тестирование разработчиком
Сами проверяете корректность изменений, подтверждаете соответствие требованиям, дорабатываете при проблемах.

### Тестирование по бизнес-эпику
- Тестирует одно из подразделений тестирования (выбор по области).
- Передаётся не dev-задача, а основная задача бизнес-эпика; передачу инициирует project-менеджер, он же согласует приоритет с
  подразделением.
- Дефекты — запросите оформление отдельными Bug-задачами, связанными с dev-задачей.
- Тестирование подразделением не снимает с разработчика ответственность за качество и корректную работу ДО передачи.

### Тестирование по техническому эпику
- Эпик от команды разработки (например, DEVDIT): при необходимости проверки задачу можно отдать одному из подразделений; выбор тот же, по
  области.
- Пример: рефакторинг legacy-кода и вынос логики в отдельный сервис — обязательно проверить, что контракт роутов и логика не изменились;
  разработчик может не заметить изменение контракта, тестировщики выявят.
- Заводится отдельная задача на тестирование с описанием, что проверять (например, полный список перенесённых роутов); передача через
  Руководителя команды; он определяет подразделение по области.

### Возврат задачи в реализацию
Проблемы при тестировании (любым исполнителем) → возврат на этап реализации; доработки по замечаниям или Bug-задачам; повторное
тестирование.

### Чек-лист завершения этапа
- тестирование выполнено (разработчиком или подразделением тестирования);
- нет открытых замечаний или Bug-задач;
- результат соответствует требованиям.

### Частые ошибки
- Тестировать только «хороший путь» → проблемы проявляются в продакшене, где исправлять дороже. Проверяйте обработку ошибок, граничные
  значения, некорректный ввод.
- Держать найденные при самостоятельном тестировании проблемы в голове → детали забываются, часть не исправляется. Сразу исправляйте и
  коммитьте или создавайте Bug-задачу.
- Исправлять найденное подразделением без Bug-задачи → нет прозрачности, Руководителю неясно, свободен ли разработчик; в итоге и новая
  задача со сроками, и старые правки впопыхах. Требуйте Bug-задачу на каждую проблему, даже очевидную; в ней: действия, фактический
  результат, ожидаемый результат.
- Не то подразделение (задачу по NurCRM — в DEVQA вместо TST) → задача зависает в чужой очереди, передачу переоформляют. Сверяйтесь с
  правилами выбора подразделения; в сомнении — Руководитель команды.
- Передавать подразделению самостоятельно, минуя project-менеджера или Руководителя команды → приоритет не согласован, возможен отказ.
  Передачу инициирует project-менеджер (бизнес-эпик) или Руководитель команды (технический эпик); Разработчик только сообщает о готовности.

### Автоматизированные тесты
- Отдел автотесты не пишет (организационные ограничения); этапа написания автотестов в процессе нет.
- По собственной инициативе можно, если это не более 10% времени на реализацию; больше 10% — согласовать с Руководителем команды.
- LLM для тест-кейсов, тестовых данных или автотестов: каждый сгенерированный тест прочитан и понят, его падение и прохождение проверены
  руками.

Источник: SDLC-Orsp-0_0_2.pdf, с. 16–20

## Документирование

Начинается после успешного тестирования и до релиза; в идеале документация готова к запуску в прод. Ведётся в подзадаче «Документирование»
внутри dev-задачи или, для крупных работ, в отдельной Task в ORSP, связанной с dev-задачей.

Исключение: релиз назначен на дату, а документация не готова — запуск допустим, документация дописывается; обязательно согласование с
Руководителем команды.

Разработчик:
- актуализирует или создаёт документацию для нового или изменённого функционала;
- для нового сервиса заводит проект в Backstage;
- для существующего актуализирует метаданные в Backstage (catalog-info, владельцы, ссылки);
- публикует документацию в Backstage (модуль TechDocs/mkdocs);
- логирует время в подзадачу или Task на документирование.

### Backstage
- Для нового сервиса заведение проекта обязательно; для существующего обязательна актуализация метаданных при изменениях, влияющих на
  каталог.
- Состав полей catalog-info.yaml и правила обновления — в Рекомендациях по документированию → Backstage.

### Форматы и требования к документации
- TechDocs (mkdocs) в репозитории сервиса — основной формат: архитектура, конфигурация, особенности работы.
- README.md в корне проекта — короткое описание проекта, модулей, инструкции по запуску.
- Публичные API — Springdoc/OpenAPI для REST; AsyncApi для Kafka не стандарт, но если есть — должен быть актуальным.
- Новый сервис: архитектура, основные сценарии, конфигурация, способы запуска и интеграции. Изменения в существующем: актуализация
  затронутых разделов. Публичные API и контракты: актуальные описания.
- LLM для README, описаний API, текстов разделов: собственный черновик до запроса, режим критики, проверка фактов.

### Учёт времени и оформление работы
- Подзадача «Документирование» создаётся на этапе анализа всегда — чтобы документация не забывалась.
- Оценка до 7 часов — подзадача внутри ORSP-задачи; время логируется в неё.
- Оценка больше 7 часов — отдельная задача в ORSP, связанная с dev-задачей; проходит упрощённый SDLC: анализ → оценка → реализация.
- Правила учёта времени (журнал работы, дважды в день, инструменты) — те же, что на реализации.

### Чек-лист завершения этапа
- подзадача или отдельная ORSP-задача на документирование закрыта;
- для нового сервиса проект заведён в Backstage; для существующего метаданные актуализированы при необходимости;
- документация (TechDocs / README / контракты публичных API) обновлена и опубликована;
- фактическое время залогировано в подзадачу или Task.

### Частые ошибки
- Не создать подзадачу на документирование при анализе → документация забывается. Создаётся всегда (правило шага Проектирование).
- Логировать время документации в основную dev-задачу → теряется фактический объём работ, трудно планировать похожие задачи. Только в
  подзадачу «Документирование» или связанную Task.
- Многодневная документация без отдельной Task → нет анализа, согласованной оценки, прогресса. Больше 7 часов — отдельная Task в ORSP.
- Подзадача «Документирование» >7 часов без выноса в Task → нарушено правило декомпозиции, оценка неточная. Видно на оценке — заводите Task
  сразу.
- Новый сервис без проекта в Backstage → сервис не виден в каталоге, нет владельцев и ссылок. Заведение обязательно.
- Документировать «как всё устроено вообще», а не дельту → дублирование кода, быстрое устаревание. Фиксируйте архитектурные решения,
  публичные контракты, нетривиальные особенности; очевидное из кода не описывать.

Источник: SDLC-Orsp-0_0_2.pdf, с. 21–23

## Релиз и деплой

Выкладка изменений в целевое окружение и настройка мониторинга. Начинается после документирования: подзадачи реализации закрыты,
тестирование пройдено, документация подготовлена и опубликована. Ведётся внутри dev-задачи.

### Сценарии деплоя
- Новый проект — деплой через заявку: создать заявку на деплой, связать с dev-задачей; после первичного деплоя проверить корректность
  запуска сервиса.
- Существующий проект — merge в интеграционную ветку (правила веток — в Java Convention); ветка используется для дальнейшего тестирования;
  по его результатам — исправления.
- Подготовка к продакшену: решение о готовности к выкладке, merge в продакшен-ветку, продакшен-деплой по правилам Java Convention.

### Настройка мониторинга и алертов
После деплоя: настроить сбор кастомных метрик (если добавлены по задаче), алармы для критических метрик, проверить работу мониторинга.
Настройка — обязательная часть передачи сервиса в эксплуатацию.

### Чек-лист завершения этапа
- выполнен деплой по сценарию;
- изменения применены в целевом окружении;
- система в рабочем состоянии;
- мониторинг и аларты настроены.

### Частые ошибки
- В продакшен без тестирования на интеграционной ветке → проблемы сразу в проде. Сначала интеграционная ветка, после успешного тестирования
  — продакшен.
- Не настроить мониторинг и аларты → проблемы обнаруживаются с задержкой или никогда. Обязательный пункт чек-листа деплоя.
- Не проверить сервис сразу после деплоя → разбираться позже сложнее. Сразу проверить: запустился, отвечает на запросы, работает как
  ожидалось.

Источник: SDLC-Orsp-0_0_2.pdf, с. 24–25

## Эксплуатация и сопровождение

Разработчики поддерживают стабильную работу задеплоенных сервисов, реагируют на инциденты, обрабатывают заявки пользователей, фиксируют
проблемы. Начинается после релиза, когда система в рабочем состоянии и dev-задача завершена с точки зрения разработки.

### Дежурства
- Формат — дежурства разработчиков внутри отдела Java-разработки по графику; дежурный отвечает за стабильную работу сервисов; обычно 1–3
  дня.
- График формируется автоматически в duty-scheduler.o.kg по установленному порядку следования разработчиков.
- В дежурство входит: отслеживание состояния сервисов и метрик; реакция на алерты; анализ проблем из мониторинга; тикеты и заявки на
  дежурство из jirasd.o.kg; первичное устранение инцидентов или инициирование дальнейших действий.

### Работа с заявками пользователей
- Заявки создаются в jirasd.o.kg и автоматически делятся по очередям по проекту и ответственному отделу.
- Дежурный работает только с обращениями, оформленными заявкой в jirasd.o.kg; обращения из других каналов (например, мессенджеры) —
  попросить оформить заявку.

### Мониторинг и алерты
Стандартные метрики сервисов плюс кастомные, добавленные при разработке; для кастомных настраивается сбор и при необходимости алармы.
Мониторинг и аларты — для выявления проблем в работе сервисов.

### Обращение за помощью и LLM
- По заявке на дежурство не получается разобраться дольше 2 часов — консультация у команды.
- LLM для разбора инцидента, чтения логов, поиска причины: проверка фактов, запрет на действия в проде без подтверждения.

### Фиксация проблем в эксплуатации
- Немассовые или периодические проблемы: завести задачу на исправление или доработку и добавить в бэклог команды; в задаче — что именно и
  где исправлять, чтобы коллега не проводил анализ повторно.
- Массовые проблемы или требующие менее 2 часов на исправление и тестирование: желательно исправить и обновить затронутый функционал по
  заявке на дежурство.
- Общие правила: проблемы оформляются отдельными задачами или Bug-задачами; Bug-задачи связываются с исходной dev-задачей или с сервисом.

### Жизненный цикл Bug-задач
- Из тестирования: создаёт отдел тестирования или разработчик при дефекте; связь с dev-задачей, где реализован функционал.
- Из дежурств: создаёт дежурный при проблемах продакшен-систем; связь с исходной dev-задачей (недавно задеплоенный функционал) или напрямую
  с сервисом (проблема не связана с конкретной задачей).
- Все Bug-задачи проходят стандартный SDLC с этапа анализа требований; исходная dev-задача не переоткрывается — Bug-задача самостоятельна.

### Завершение дежурства и возврат в цикл SDLC
- К концу рабочего дня все заявки на дежурство в идеале решены; стремитесь к этому.
- Bug-задача с описанием «что-то там не работает» перекладывает проблему на коллег: опишите, что сломалось, где искать причину, какие
  проверки уже проведены.
- Задачи и Bug-задачи из эксплуатации — новые единицы работы; проходят стандартный SDLC отдела с этапа анализа требований; исходная
  dev-задача не переоткрывается.

### Частые ошибки
- Разбирать проблему больше 2 часов без обращения к команде → потеря времени, копятся заявки. Правило 2 часов.
- Исправлять «на месте» без задачи в системе учёта → исправление не задокументировано, в следующий раз разбираться заново. Даже быстрые
  исправления — задачей; это база знаний о проблемах.
- Bug-задачи с неинформативным описанием → коллега повторяет анализ и отвлекает вопросами. Описывайте: что сломалось, шаги воспроизведения,
  предположения о причинах, что уже проверили.
- Работать с обращениями в обход jirasd.o.kg → обращения теряются, нет учёта, нарушается приоритизация. Только оформленные заявки.
- Не обновить документацию после разбора проблемы → следующий дежурный повторит разбор. Выяснили особенность работы сервиса — обновите
  документацию.

## Рекомендации по коммуникациям

### Обратная связь на вопросы коллег
- Отвечайте всегда, даже без полного ответа: «Проанализирую код и вернусь с ответом», «Уточню вопрос и вернусь с ответом» — лучше молчания.
- Ещё лучше с ориентировочным сроком: «Вернусь с ответом ориентировочно через два часа», «Вернусь с ответом завтра до обеда» — избавляет от

### Уведомление об изменении сроков
- Не успеваете к названному сроку (функционал сложнее, сбои в проде, жизненные обстоятельства — это нормально) — сообщите, как только
  поняли; назовите новый срок, если возможно.
- Не можете продолжать работу над вопросом вообще — сообщите и укажите, кто из команды теперь им занимается.

### Когда вы задаёте вопрос
- Всегда указывайте критичность и срок, до которого желателен ответ. Срок разумный, реальный и выполнимый; никаких «нужно вчера».
- Формулировки: «Вопрос не критичный, но буду признателен за ответ до обеда / вечера / завтра / обеда четверга»; «Вопрос критичен, потому
  что лежит прод / большое количество обращений в саппорт — прошу рассмотреть и по возможности ответить в максимально короткие сроки».

- Заблокированы и не можете продвинуться — консультация у команды. Лимиты до обращения: анализ требований — 4 часа; реализация — 4 часа;
  дежурство — 2 часа.
- Подготовьте контекст: задача и текущий прогресс; опробованные варианты решения и причины затруднения; чётко сформулированные вопросы. Это
  ускоряет получение конкретного ответа.

### Что документировать
Обязательно:
- публичные API и контракты — REST-эндпоинты;
- архитектура нового сервиса — компонентная диаграмма, внешние интеграции, основные потоки данных;

## Использование LLM в процессе разработки

LLM участвует на всех этапах — от анализа до сдачи. Рекомендации действуют при любом использовании: одиночный чат, IDE-интеграция с
автодополнением, агент. «Агент» — LLM, которая сама выполняет действия (читает и правит файлы, запускает команды), а не только отвечает
текстом.

### Что делает Разработчик при работе с LLM
- принимает решения по задаче сам;
- сначала формирует собственное решение (понимание задачи, неясные вопросы, архитектура, код), затем отдаёт LLM на критику;
- ограничивает контекст модели тем, что относится к задаче;
- читает и понимает каждую строку, попадающую в коммит;
- проверяет фактические утверждения модели по документации;
- фиксирует решения и обоснования в файлах задачи.

### Принципы
- Ответственность: решения принимаете вы, модель помогает их находить и оформлять. Модель не знает контекста команды и звучит уверенно, даже
  когда ошибается; архитектура, паттерны и библиотеки — за Разработчиком и фиксируются явно.
- Объяснение вслух: понимание — условие коммита. Не можете объяснить строку вслух — она не уходит в репозиторий. «Работает же» и «модель так
  предложила» — не аргументы.
- Собственный черновик: до запроса на анализ, проектирование или код — своя версия (понимание задачи своими словами, набросок решения,
  первый вариант кода). Без него вы делегируете мышление, а не получаете помощь; после ответа модели её формулировки незаметно становятся
  вашими по умолчанию (anchoring).
- Размер итераций: десять коротких запросов с проверкой каждого лучше одного «сделай мне фичу»; чем длиннее автономный участок, тем выше
  вероятность тихой ошибки. С агентом — по шагам: после каждого читать изменения, потом следующий.
- Проверка фактов: модель уверенно выдумывает API, параметры функций, поведение библиотек, наличие методов; любое утверждение про внешний
  мир проверяется по документации. Приём: «Оцени уверенность по каждому пункту от 1 до 5 и объясни почему» — модель часто сама признаёт
  догадки.
- Сохранение навыка: регулярно решайте задачи без LLM — понимание атрофируется, если каждая функция начинается с автодополнения. На
  предложение модели спрашивайте себя: пришёл бы я к этому сам? если нет — почему, что узнал? если да — что модель сделала лучше?

### Ревью своих артефактов через LLM
Шаблон один для всех артефактов: своя версия → модели в режиме критики → разбор замечаний (пустые отбросить, полезные исправить). Модель
проверяет вашу работу, а не делает первичную часть за вас.
- Постановка задачи: своими словами понимание, сценарии, неясные места, вопросы к заказчику, риски; затем: «Вот моё понимание задачи и мои
  открытые вопросы. Что я упустил? Какие сценарии не учёл? Какие предположения делаю неявно? Где двусмысленность, которую я не заметил?»
- Архитектурный набросок: подход, рассмотренные альтернативы, почему отвергнуты, принятые компромиссы; затем: «Вот мой подход и обоснование.
  Какие проблемы я не вижу? Какие альтернативы не рассмотрел? Где компромиссы недооценены? Что станет проблемой при росте в 10x?»
- Свой код: отдельным запросом в режиме ревью с явным запретом генерации: «Прочти этот файл/диф. Не пиши код. Найди баги, race conditions,
  утечки, необработанные ошибки, плохие имена, дублирование, нарушения SRP. Отсортируй по важности.»
- Документация: «Прочти это так, как будто видишь проект впервые. Что непонятно? Какие предположения я не объяснил? Где можно неправильно
  понять?»
- MR перед отправкой коллегам: диф в режиме критики, как для кода — снимает тривиальные замечания с ревьюеров и экономит круги обсуждения.

### Работа с агентами
Агенты действуют без вашего непрерывного участия — контроль встраивается в процесс, а не остаётся на дисциплине в моменте.
- Plan → Act как явный режим: сначала агент только проектирует и обсуждает без правок в файлах; план — артефакт, который вы вычитываете и
  правите; реализация только по утверждённому плану.
- Узкий, явный контекст: не «посмотри весь репо и разберись»; сами определяете пакеты и классы задачи. Чем шире контекст, тем выше шанс, что
  агент пойдёт чинить несломанное.
- Явный negative scope: «что не трогать» — отдельный пункт, прописанный заранее; иначе агент рефакторит смежный код «заодно».
- Командные правила и конвенции — на вход с самого начала, иначе агент выдаёт «средний код из GitHub» (типовые имена, дефолтные паттерны из
  туториалов), который редко совпадает с тем, как пишет команда.
- Передавайте агенту заранее: стиль и конвенции именования; предпочитаемые и запрещённые библиотеки; обязательные паттерны логирования,
  метрик, обработки ошибок; формат API-ответов; подход к конфигурации, БД и кэшу.
- Удобно держать это отдельным документом или набором документов (в т.ч. skills), которые агент читает на каждом запуске; иначе будете
  переписывать его решения вручную и пропускать места «работает, но не по-нашему».
- Подтверждение действий: каждое изменение файла и каждая команда — с явным согласием; медленнее, зато не обнаружите через час переписанную
  миграцию или удалённые тесты.
- Чтение диффа обязательно: не «агент сказал, что готово», а каждая строка в коммите прочитана; непонятная — не уходит.
- Проверки руками: тесты, линтер, билд запускаете сами; агент умеет «запускать» тесты в голове и отчитываться об успехе.
- Отдельные сессии для несвязанных задач: старый контекст тянет к старым решениям; смешение задач даёт каскадные ошибки.
- Разделение ролей: проектировщик, исполнитель, ревьюер — разные агенты или сессии; один агент не решает «как» и не оценивает «правильно ли
  получилось» одновременно.
- Чувствительные зоны без явной отмашки не автоматизируются: инфраструктура, секреты, CI, миграции, удаления — даже если агент уверен, что
  «безопасно».

### Пример организации флоу с агентами
Контроль переносится из «дисциплины в моменте» в документы-гейты: каждый шаг производит файл, Разработчик вычитывает и правит, только потом
запускается следующий шаг; следующий шаг читает артефакт предыдущего, а не «всё подряд» — меньше дрейфа решений и галлюцинаций.
1. Анализ задачи — артефакт: суть своими словами, затронутые файлы, что не трогать, применимые конвенции команды, технические риски,
   открытые вопросы; Разработчик отвечает на вопросы прямо в артефакте и при необходимости переписывает суть.
2. План имплементации — какие изменения в каких файлах и в каком порядке, отвергнутые альтернативы с обоснованием, критерии приёмки;
   Разработчик вычитывает, правит, при необходимости отправляет на пересмотр.
3. Реализация — исполнитель идёт по списку задач из плана по одной, отмечая выполненные; Разработчик читает диф; выход за рамки плана —
   возврат.
4. Самостоятельное ревью — другой агент или чистая сессия получает план и диф, выдаёт замечания с градацией Blocking / Important / Minor;
   артефакт читается как код-ревью от коллеги.
5. План фиксов (при блокирующих проблемах) — отдельный артефакт с конкретными фиксами и критериями приёмки; предыдущая версия плана уходит в
   архив, а не переписывается.
6. Фиксы — исполнитель работает по плану фиксов.
7. Цикл — повторное ревью при необходимости, пока не останется блокирующих замечаний.

Механизмы флоу: артефакты вместо разговоров (решения и контекст в файлах, а не в чате); гейты на открытых вопросах (не ответили — следующий
шаг не запускается);
контекст не повторяется (каждый шаг читает только артефакт предыдущего); разделённые роли; архивирование итераций (история фиксов отдельно);
явный scope с двух сторон (что делаем + что не делаем).

### Чек-лист правильного использования LLM
- решения по задаче приняты Разработчиком, а не моделью;
- перед каждым запросом к модели был собственный черновик;
- все фактические утверждения модели про API и библиотеки проверены по документации;
- каждая строка кода в коммите прочитана и понята;
- для агентов: явно задан scope «что трогать / что не трогать»;
- для агентов: на вход поданы командные конвенции и правила;
- для агентов: диф вычитан построчно, тесты и линтер запущены руками;
- решения и обоснования зафиксированы в артефактах задачи.

### Частые ошибки
- Первичный анализ или архитектура от LLM вместо своего черновика → формулировки модели становятся вашими, оценить критику нечем,
  ответственность размывается. Сначала свой черновик, даже плохой и неполный; потом LLM в режиме критики.
- «Accept all» не читая → в коммите код, который вы не понимаете; тихие ошибки копятся до прода. Каждая строка читается; не объясняется
  вслух — не коммитится.
- Длинная автономная сессия «сделай мне фичу» с возвратом через час → агент уходит в сторону на одном шаге, «исправляется» на следующем,
  результат не о задаче; найти дрейф дорого. Маленькие шаги с подтверждением, диф после каждого.
- Доверять утверждениям про API, версии, поведение библиотек без проверки → несуществующие методы, падение в рантайме. Проверка по
  документации; при сомнениях — запросить оценку уверенности.
- Агент без командных конвенций на входе → «средний код из GitHub», ручная переделка, часть несоответствий пропускается. Правила и
  ограничения отдельным документом на каждый запуск.
- Нет negative scope → агент рефакторит смежный код, задевает чужие модули, ломает зелёный билд. Два списка в постановке: «затронутые файлы»
  и «не трогать».
- «Выбери за меня и сделай» → решение по частоте в обучающей выборке, а не по проекту; ответственность размывается. Запрашивать альтернативы
  с компромиссами; выбор делает Разработчик и фиксирует обоснование.
- Доверять отчёту «тесты прошли, линтер чистый» → реальное состояние ветки расходится с отчётом. Тесты, линтер, билд — руками перед
  коммитом.

## Руководство по SonarQube for IDE

Плагин для IntelliJ IDEA со статическим анализом кода в редакторе. Connected Mode синхронизирует правила, профили качества и результаты с
корпоративным сервером SonarQube — вся команда работает с одним набором правил; без него каждый видит свой локальный набор.

### Установка плагина
- File → Settings (Ctrl+Alt+S) → Plugins → Marketplace → поиск «SonarQube for IDE» → Install → Restart IDE.
- Проверка: после перезагрузки в нижней панели есть вкладка SonarQube for IDE.

### Подключение к серверу
- Settings → Tools → SonarQube for IDE → блок Connections to SonarQube → «+» → SonarQube Server.
- Поля: Connection Name — произвольное имя (пример: Nur SonarQube Server); SonarQube URL — https://sonarqube.o.kg.
- Next → Create token → в браузере Allow connection (токен подставится автоматически) → Next до конца → Create → Apply.

### Привязка проекта
- Settings → Tools → SonarQube for IDE → Project Settings → флажок Bind project to SonarQube → выбрать подключение → Search in list →
  выбрать проект на сервере → OK.
- Проверка: нарушить любое серверное правило и запустить анализ файла — нарушение подсвечено, синхронизация работает.

### Запуск анализа
- Автоматический анализ при редактировании включён по умолчанию; подсветка как у инспекций IDEA: Bugs — красная волнистая линия,
  Vulnerabilities — оранжевая, code smells — жёлтая или зелёная.
- Слабая машина (зависания, лаги): Settings → Tools → SonarQube for IDE → Settings → снять Automatically Trigger Analysis; далее анализ
  запускать вручную для нужных файлов.
- Текущий файл: вкладка SonarQube for IDE → Analyze Current File (зелёный треугольник) или сочетание клавиш из Keymap.
- Несколько файлов: выделить файлы или папку в панели Project → ПКМ → SonarQube for IDE → Analyze with SonarQube for IDE.
- Изменённые файлы: Analyze VCS Changed Files — только файлы, изменённые в текущей ветке; полезно перед пушем. Файлы, не отслеживаемые в
  VCS, в анализ не попадают.
- Анализ при коммите (рекомендуется включить): окно коммита (Alt+0 или Ctrl+K) → шестерёнка справа снизу → флажок Perform SonarQube for IDE
  analysis. Проверка: закоммитить изменение — при найденных проблемах плагин покажет диалог.

### Чек-лист настройки
- плагин SonarQube for IDE установлен;
- создано подключение к https://sonarqube.o.kg;
- проект привязан к проекту на сервере (Connected Mode);
- на слабых машинах отключён автоматический анализ;
- включён Perform SonarQube for IDE analysis при коммите.

### Частые проблемы
- Плагин не видит сервер: проверить URL (включая порт); токен действителен и не истёк; сеть (proxy, VPN, firewall); версия SonarQube не ниже
  8.9.
- Анализ слишком медленный: исключить сгенерированные файлы и папки сборки; увеличить память IDE в idea.vmoptions; анализировать только
  изменённые файлы; отключить Automatically Trigger Analysis.
- Ошибки, которых нет на сервере: Standalone-режим использует встроенный набор правил; решение — Connected Mode.
- Без корпоративного сервера: Standalone-режим работает локально со встроенными правилами; для командной работы не рекомендуется —
  используйте Connected Mode.
