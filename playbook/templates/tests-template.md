# Шаблон: тест-кейсы (`tests.md`)

Кейсы пишутся до кода, по шагам плана, человеческим языком (Дано / Когда / Тогда). Их
подтверждает автор задачи вместе с планом; в work после подтверждения кейсы и код тестов не меняются
без вопроса оператору (правило 06). Пишет `planner`, проверяет `critic`, код по кейсам пишут тест-райтеры.

## Правила
- Один кейс — одно поведение с наблюдаемым результатом (ответ, статус, запись, лог, метрика).
- Конкретные значения вместо «корректный запрос». Файл нужен в режиме `Тесты: tdd`: до трёх кейсов на шаг
  с поведением; в режиме `ключевые` кейсы живут в разделе «Тесты» плана.
- Обязательны: обычный путь, граница (пустое, дубль, максимум), ошибка (невалидный вход, отказ
  зависимости, таймаут).
- Уровень указан у каждого кейса: unit, интеграционный (Testcontainers, WireMock), контрактный.
- Статус меняет только исполнитель скриптом `tests-status.sh`.

## Формат

```markdown
# Тест-кейсы: <задача> (<JIRA-ID>)
Статус: черновик | согласованы <дата> (<кто добавил свои кейсы>)
Правило: после согласования кейсы и код тестов не меняются без вопроса оператору.
Легенда: [ ] не написан · [~] написан, падает (RED) · [x] зелёный · [!] изменён с разрешения (дата, причина)

## Фаза 1. <название>
- [ ] T1.1 (unit) Дано <состояние>; когда <действие>; тогда <результат>.
- [ ] T1.2 (unit) Дано <граница>; когда <действие>; тогда <результат>.
- [ ] T1.3 (интеграционный) Дано <ошибочное условие>; когда <действие>; тогда <ошибка, код, поведение>.

## Фаза 2. <название>
- [ ] T2.1 …
```

Пример строки: `- [x] T2.2 (unit) Дано только ru; когда запрашиваем kg; тогда возвращается ru
и пишется лог уровня warn без PII.`
