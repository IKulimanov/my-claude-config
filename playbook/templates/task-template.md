# Shared: задача / подзадача для человека (Jira)

Источник истины по процессу — `playbook/projects-playbook.md`
и «Рекомендации по описанию задач». Здесь — формат текста задачи и правила Given/When/Then.

Задача пишется **для разработчика, не для агента**: он придёт максимум с вопросом «а точно так?», а не «а как?».
Норма размера подзадачи — 4–10 часов; сложность выражать оценкой и открытыми вопросами, а не дроблением.

## Формат подзадачи (Jira-разметка)

```
h3. <Глагол + объект>                             — [Core]/[Cockpit]/[Backend]/[Frontend] префикс, если эпик смешанный

*Дизайн:* <ссылка на раздел design / ADR>          — там, где суть задачи определена разделом; иначе не писать
*Что сделать:* 2–4 предложения с бизнес-правилами. Без имён классов, DDL и колонок — назначение, а не идентификаторы.

*Критерии приёмки:*
* Дано <состояние/предусловие>, когда <действие>, тогда <наблюдаемый результат>.
* Дано …, когда …, тогда … .
* Дано <ошибочное условие>, когда …, тогда <ошибка/код/поведение>.   — минимум один сценарий ошибки

*Открытые вопросы:*                                — только настоящие; с владельцем; решаются в «Анализе» до реализации
* <вопрос> — <кто отвечает>

*Не входит:* <что осознанно за рамками>
*Зависимости:* <задачи / внешние контракты>        — только если есть
*Оценка:* <ч>
```

Дев-задача (родитель) — «Зачем», «Результат этапа», «Состав», «Зависимости»; подзадача «Анализ» — одна на этап:
вход (задачи этапа с открытыми вопросами), выход (решения зафиксированы, оценки уточнены), лимит 7 ч.

## Дано / Когда / Тогда — что это и как писать

Это Given/When/Then — язык Gherkin из BDD (Dan North, 2006; Cucumber; «Specification by Example», Adzic).
Given — состояние мира до действия, When — одно действие, Then — наблюдаемый результат, который можно проверить.

Правила, которые делают критерии проверяемыми:
- Один сценарий — одно поведение. Несколько «когда» подряд — это два сценария.
- Конкретные значения вместо «корректный запрос»: «Дано клиент с ролью DBA и заявка PG-1 в статусе Ожидает».
- «Тогда» — только наблюдаемое: ответ, статус, запись, письмо, метрика. Не «система корректно обрабатывает».
- Обязателен сценарий отказа: невалидный вход, недоступная зависимость, дубль, таймаут — что видит пользователь.
- Без деталей реализации: не «в таблице X появляется строка», а «заявка видна в списке со статусом Y».
- ≤5 сценариев на подзадачу. Больше — подзадача слишком крупная или это уже design.
- «И» для дополнительных условий/результатов: «Дано …, и …, когда …, тогда …, и …».
- Согласованный словарь: те же имена статусов, ролей и сущностей, что в design и в интерфейсе.

Технику подготовки — Example Mapping (Wynne): на задачу выписать правила → на каждое 1–2 примера (они и
становятся сценариями) → непонятное вынести в «Открытые вопросы». 10–15 минут на задачу.

## Чем задача «для человека» отличается от постановки агенту

- Меньше текста, больше ссылок: дизайн по ссылке, а не пересказ. Человек умеет ходить по ссылкам.
- «Зачем» — одно предложение или ссылка на этап; агенту нужен полный контекст, человеку — указатель.
- Не копировать типовой Definition of Done в каждую задачу («ревью, тесты, Sonar») — это командный стандарт;
  писать только нестандартное («миграция проверена на копии prod», «инструкция DBA обновлена»).
- Не выдумывать «Технические заметки» с реализацией — это решает исполнитель в «Анализе»; если решение уже
  принято — ссылка на ADR.
- Открытые вопросы — явно и с владельцем; недосказанность в задаче для человека дороже лишнего вопроса.
- Оценка — в задаче; буфер ≤10%; приоритет — порядок в плане, отдельного поля не нужно.
