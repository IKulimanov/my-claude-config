# Шаблон: план реализации (`plan.md`)

Единый формат для `/task` (пишет `planner`) и `/feature` (пишет главный агент по умению `planning`).
План читает человек: короткий, конкретный, со статусами. Исследование и цитаты кода живут
в `context.md`, не здесь.

## Правила

- План пишется один раз на всю задачу; реализация идёт по нему без нового анализа.
- Одна веха — не длиннее 150 строк; секция «Решение» — не длиннее 15 строк; шаг — одна строка.
- Каждый шаг: статус, номер, что сделать, файл, проверка, кейсы. Исполнитель ничего не додумывает.
- Статусы: `[ ]` не начат · `[~]` в работе · `[x]` готов · `[!]` вопрос агента (работа стоит) ·
  `[#]` стоп-точка оператора (агент останавливается перед шагом и ждёт «дальше»).
  Статус меняет только исполнитель шага и только скриптом `scripts/helpers/plan-status.sh`.
- Фаза — набор шагов на одну сессию одного агента: не больше 8 правок файлов, сборка после
  фазы зелёная, между фазами нет полусделанных контрактов. Больше трёх фаз — вехи внутри этого
  же плана: у вехи цель и «готово, когда», ревью — по вехе.
- Шапка `Тесты:` и `Коммиты:` — ответы из начала задачи; кейсы по режиму: `tdd` — `tests.md`,
  `ключевые` — раздел «Тесты» плана, `нет` — без кейсов.
- Русский, простыми словами; идентификаторы как есть. Без «улучшим», «оптимизируем» без конкретики.
- Замечания критика «блокирует» и «стоит» вносятся с пометкой «критик»; «по желанию» — в «Границы».
- План согласовывает автор задачи; после согласования меняются только статусы и журнал.
- Файлы всех шагов и каталоги тестов дублируются в `agent/scope.txt` (`scope.sh add`); запись вне списка
  требует подтверждения оператора.

## Формат

```markdown
# План: <название задачи> (<JIRA-ID>)
Статус: черновик | согласован <дата> · Обновлён: <дата время>
Тесты: ключевые | tdd | нет · Коммиты: после каждой фазы | в конце | нет | по просьбе
Легенда: [ ] не начат · [~] в работе · [x] готов · [!] вопрос агента · [#] стоп-точка оператора

## Цель
1–2 предложения: какую проблему решаем и какой результат должен получиться.

## Решение (почему так)
Вариант автора: <кратко или «не было»>. Итог: совпадает | отличается: <чем>.
Подход: <одно-два предложения простым языком>.
Отклонили: <вариант> (<причина>); <вариант> (<причина>).
Критик: <что внесено по critique1.md, что отклонено и почему>.
Слои: <порядок прохода, например миграция → репозиторий → сервис → API; что не трогаем>.

## Шаги
### Веха 1. <название> — готово, когда: <проверяемый результат>
#### Фаза 1. <название>
- [ ] 1. <Что сделать> — `путь/к/файлу`. Проверка: `<команда>`. Кейсы: T1.1–T1.2
- [ ] 2. <Что сделать> — `путь/к/файлу`. Проверка: `<команда>`. Кейсы: T1.3
#### Фаза 2. <название>
- [ ] 3. …
### Веха 2. <название> — готово, когда: <…>
- [ ] 4. …

## Тесты
`tdd`: `tests.md`, статус: черновик | согласованы <дата>.
`ключевые`: кейсы здесь, по вехам — `T1.1 (unit) Дано …; когда …; тогда …`.
`нет`: раздел пустой.

## Риски
- <реальный риск> → <как страхуемся, каким кейсом проверяем>.

## Границы
- <что осознанно не делаем, чтобы работа не расползлась>.

## Вопросы
- Шаг N: <вопрос> — <владелец>.

## Журнал
- <дата время> <фаза готова или начата; тесты; ревью — одной строкой>.
```
