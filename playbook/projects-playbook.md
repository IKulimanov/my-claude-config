# Плейбук документов проекта: от brief до задач

Канонический процесс проектирования. Сводит корпоративный SDLC (`sdlc.md`), «Рекомендации по
описанию задач» (`task-writing.md`), «Рекомендации по процессу разработки» (`dev-process.md`)
и общие практики: Working Backwards, Google Design Doc, ADR, C4, Shape Up. Шаблоны документов —
`templates/`. Команды: `/design` ведёт по шагам, `/adr` пишет решения, `/jira` — задачи,
`/task` — реализацию по задаче.

## Правило масштаба

| Объём работы              | Документы                                         |
| ------------------------- | ------------------------------------------------- |
| < 3 дней                  | Только задача с критериями приёмки                |
| 3 дня – 2 недели          | Brief + задачи                                    |
| > 2 недель / новый сервис | Полный флоу: brief → design → ADR → plan → задачи |

## Флоу и структура

```
Запрос → [1] 00-brief.md → [2] 01-design.md → [3] adr/ (по ходу) → [4] 02-plan.md → [5] задачи (Jira)
             ↑ согласовать с заказчиком   ↑ ревью коллегой / сутки вылёживания
```

```
docs/projects/<project-name>/      # имя по project-naming.md: префикс-домен-функциональность
  00-brief.md                      # templates/brief-template.md
  01-design.md                     # templates/design-template.md
  02-plan.md                       # templates/project-plan-template.md
  adr/0001-<decision>.md           # templates/adr-template.md
  options/                         # варианты из соревнования (A.md, B.md, C.md, verdict.md)
  assets/                          # схемы, входные материалы заказчика (скрипты, инструкции)
```

Каркас создаёт `scripts/helpers/design-init.sh <project-name>`. Не переходить к следующему
документу, пока предыдущий не согласован. Изменился scope → правка brief и пересогласование.
Изменилось решение → новый ADR.

---

## 1. Brief (`00-brief.md`) — 30–60 мин

Зачем: зафиксировать проблему и результат до обсуждения технологий. Аналог «что должно быть
в бизнес-эпике» из SDLC: цели и мотивация, ограничения, контакты ответственного, приоритет.

Обязательные секции:

| Секция | Содержание |
|---|---|
| Проблема | Кто страдает, от чего, сколько стоит (время/деньги/риски). 1–3 предложения, без технологий |
| Результат | Проверяемая формулировка «как выглядит мир, когда сделано», с числами где можно |
| Пользователи и сценарии | Роль → что делает в новой системе, 3–5 строк |
| Scope In / Out | Out — явно: главная защита от расползания |
| Ограничения | Реальные: инфраструктура, версии СУБД, лицензии, регламенты безопасности |
| Appetite | Лимит, не оценка: «N недель одного человека». Решение подгоняется под лимит |
| Контакты | Заказчик/менеджер по задаче — кому задавать вопросы (SDLC: уточнения через ответственного) |
| Вариант автора | Первый вариант решения автора до анализа, 1–3 строки или «не знаю»; design потом сверяется с ним |

Чек-лист:
- [ ] заказчик прочитал и сказал «да, это оно»
- [ ] проблема сформулирована без упоминания технологий
- [ ] результат проверяем (можно ответить да/нет «достигнут?»)
- [ ] Out of scope не пустой
- [ ] appetite указан

## 2. Design Doc (`01-design.md`) — 2–8 часов

Зачем: ответить «как это будет работать» до кода. По SDLC архитектурная схема для нового сервиса
обязательна. Ревью хотя бы одним коллегой; нет коллеги — сутки вылёживания и перечитать самому.
Для проекта больше двух недель `/design` сначала запускает соревнование вариантов: три
независимых варианта с разными позициями и судья; выбранный разворачивается в design, остальные
идут в «Рассмотренные альтернативы».

Обязательные секции:

| Секция | Содержание |
|---|---|
| Статус / Ревьюеры / Brief | черновик → ревью → approved → as-built; ссылка на brief |
| Контекст | Что есть сейчас, почему не работает. Ссылки на системы/код |
| Цели / не цели | Измеримые цели дизайна; что осознанно не решаем в этой версии |
| Обзор | Одна схема C4 Container-уровня, ≤ 7 блоков (mermaid) + абзац: как основной сценарий проходит через компоненты |
| Модель данных | ERD или таблицы с ключевыми полями. По `task-writing.md`: бизнес-смысл сущности, владелец данных, объёмы и прирост, связи, уникальность, основные выборки/индексы, utf8-поля, дефолты boolean, начальное заполнение |
| API и контракты | По `task-writing.md` для роутов: контекст вызова, метод и URI, параметры с обязательностью, auth, роли/скоупы, тело запроса/ответа по назначению полей, валидация, идемпотентность, формат ошибок с кодами, ожидаемый rps. Внешние контракты — OpenAPI/AsyncAPI рядом |
| Ключевые сценарии | Sequence для 1–3 неочевидных сценариев. Обязательно сценарии отказа: упала БД, нет ответа, дубль, таймаут. Точки невозврата |
| Джобы | Для каждого: назначение, критерии отбора, расписание, объём за запуск, параллельность/партиционирование, батч, повторная обработка, single-instance или нет, поведение при ошибке, метрики |
| Хранение и инфраструктура | Где живёт, деплой, конфигурация, секреты (Vault, не в коде) |
| NFR | Нагрузка, latency, retention, доступность — числами |
| Рассмотренные альтернативы | 2–3 отвергнутых варианта по абзацу: что и почему нет |
| Риски и открытые вопросы | Открытые вопросы — с владельцем и дедлайном |
| Тестирование и выкатка | Уровни тестов, что руками; выкатка (feature flag, параллельный запуск, миграции данных); откат; мониторинг и алерты (по SDLC — обязательная часть передачи в эксплуатацию) |

Чек-лист:
- [ ] схема Container-уровня есть, блоков ≤ 7
- [ ] описаны сценарии отказа, не только happy path
- [ ] контракты API зафиксированы до кода
- [ ] по каждой сущности: объёмы, владелец, основные выборки
- [ ] альтернатив ≥ 2
- [ ] NFR числами, не «быстро и надёжно»
- [ ] секция «Тестирование и выкатка» заполнена, включая откат и мониторинг
- [ ] ревьюер прочитал (или сам через 24 часа)
- [ ] design не длиннее 400 строк: детально — только рискованное и неочевидное, CRUD — одной строкой

Требование задачи не привязывать к имплементации (классы, DDL, имена колонок) действует и здесь:
описывай назначение, а не финальные идентификаторы.

## 3. ADR (`adr/NNNN-title.md`) — 15 мин на решение, по ходу проекта

Писать когда: выбор технологии, паттерн с последствиями, отказ от очевидного варианта, изменение
решения из design doc. Формат и правила письма — `templates/adr-template.md` (Контекст и проблема →
Рассмотренные варианты → Решение → Последствия → Ссылки); пишет `/adr`. ADR не переписываются:
передумали → новый ADR, старому статус «Заменён ADR-NNNN».

## 4. Plan (`02-plan.md`) — 1–2 часа

Шаблон — `templates/project-plan-template.md`.

| Секция | Содержание |
|---|---|
| Вехи | M1..Mn с датами. Веха = работающая вертикаль (walking skeleton), не «закончен слой БД». M1 — сквозной сценарий end-to-end, пусть примитивный |
| Задачи | Список или ссылки на Jira. Порядок: сначала задачи, снимающие риски и неизвестность |
| Отложено | Что осознанно не делаем в этой итерации |

Чек-лист:
- [ ] каждую веху можно показать/пощупать
- [ ] первая веха — end-to-end срез
- [ ] рискованные задачи в начале

## 5. Задачи (Jira: dev-задача → подзадачи)

Оформление по SDLC:
- dev-задача в ORSP, Epic Link → бизнес-эпик; материалы и ТЗ скопированы в задачу
  (зафиксировать состояние входных данных).
- Подзадача «Анализ» — одна на dev-задачу (изучение требований → проектирование → оценка;
  лимит анализа 7 ч, помощь после 4 ч).
- Подзадачи реализации: каждая 3–7 часов (порог дробления 7 ч), отдельный логический кусок
  с чётким результатом. Включая технические: метрики, health-checks, заявка на деплой.
- Подзадача «Документирование» — всегда; по оценке > 7 ч — отдельная Task в ORSP.
- Оценки в Jira до начала реализации, буфер ≤ 10%.
- Коммиты: `TASKCODE-123: описание на русском` (подробно — скил `git-convention`).

Формат текста подзадачи — `templates/task-template.md` (Jira-разметка, Дано/Когда/Тогда);
пишет `/jira`. Кратко:

```markdown
## <Глагол + объект>                      # [Backend]/[Frontend] префикс, если эпик смешанный
Дизайн: ссылка на секцию / ADR
Проект (система): где ведётся доработка
Что сделать: 2–4 предложения с бизнес-правилами, без привязки к имплементации
Критерии приёмки: Дано/Когда/Тогда, каждый проверяем; минимум один сценарий ошибки
Зависимости: задачи, внешние контракты (файл контракта приложен к задаче)
Не входит: что не делаем
Оценка: часы (3–7)
```

Свойства задачи (все бинарно проверяемы): необходима для цели, не привязана к имплементации,
непротиворечива, завершена (кто/что/когда/условия/результат/ограничения), атомарна (одна фича),
отслеживаема (trace до brief/design), осуществима, проверяема (тест/метрика/лог).

Тест качества: разработчик без контекста делает задачу, не приходя с вопросами «а как?».

Чек-листы по типу работ (роут, страница, таблица, форма, сущность, джоб) — `task-writing.md`;
использовать при описании соответствующих подзадач.

## Во время разработки и после

- Изменилось решение → новый ADR, правка только затронутой секции design.
- Изменился scope → правка brief, пересогласование.
- Документация обновляется в той же MR, что и код (публичные API, конфигурация).
- README: описание сервиса, стек, модули, безопасный локальный запуск. Не дублирует design.
- Для нового сервиса: заведение в Backstage (catalog-info.yaml), TechDocs.
- После релиза: design → `as-built`, открытые вопросы закрыты или перенесены.

## Чего не писать

- BRD, SRS, ТЗ по ГОСТ — роль закрывают brief + design.
- Полная C4 — достаточно Context (если внешних систем > 2) и Container.
- Диаграммы классов, детальные BPMN — устаревают быстрее, чем читаются.
- Документировать «как всё устроено вообще» вместо дельты изменений.
- Оценки в часах на каждую задачу плана — даты вех и appetite работают лучше; часы — в подзадачах Jira.
