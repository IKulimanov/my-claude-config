# My Claude Config

Репозиторий с личной конфигурацией для Claude Code.

Его задача не просто "хранить промпты", а задавать понятную систему работы агента:
- что загружать всегда
- что подключать только по необходимости
- как планировать изменения
- как проверять код
- как учитывать командные конвенции
- как переиспользовать одну конфигурацию в нескольких проектах

Репозиторий настроен под три основных сценария:
- рабочие Java-сервисы на `Maven + Spring Boot + Hibernate/JPA + Oracle/PostgreSQL/ClickHouse + Kafka`
- фронтенд на `Vue 3 + Vite + Pinia + TypeScript`
- побочные проекты на `Go`

Базовый принцип здесь такой:
- глобальный слой должен быть маленьким
- стековая и командная специфика должна лежать в модульных `skills`
- проектные ограничения должны жить в локальном `CLAUDE.md` конкретного репозитория

## Что Это И Зачем Нужен Этот Репозиторий

Обычная проблема конфигов для ИИ-агентов в том, что они быстро превращаются в большую смесь:
- общих правил
- случайных предпочтений
- stack-specific инструкций
- одноразовых промптов
- противоречащих друг другу ограничений

В итоге агент либо знает слишком много и работает шумно, либо знает слишком мало и начинает ошибаться в важных местах.

Этот репозиторий нужен, чтобы решить это структурно:
- вынести стабильные правила в `rules/`
- повторяемые сценарии в `commands/`
- сложные роли в `agents/`
- глубокие знания по домену и стеку в `skills/`
- локальные особенности сервиса в `CLAUDE.md`

То есть это не "папка с инструкциями", а каркас управления поведением агента.

## Для Кого Подходит

Сейчас конфиг ориентирован на:
- Java / Spring Boot сервисы (основной профиль)
- Vue 3 / Vite фронтенд (Composition API, Pinia, TypeScript)
- Go-сервисы и побочные проекты
- отдельные сервисные репозитории, а не монорепы
- консервативный режим работы агента: сначала план, потом вопросы, потом реализация
- работу по командной конвенции

## Основные Принципы

1. Тонкий always-on слой  
Всегда загружены только короткие и стабильные правила.

2. Plan-first поведение  
Для нетривиальных задач агент должен сначала понять контекст, составить план и поднять неясности.

3. Конвенция важнее generic best practices  
Если проект явно живет по внутренней конвенции, агент должен подчиняться ей, а не абстрактным рекомендациям из интернета.

4. Проектный контекст живет в проекте  
Всё локальное должно описываться в `CLAUDE.md` конкретного репозитория, а не тащиться в глобальный конфиг.

5. Расширяемость без prompt-bloat  
Новые возможности добавляются через `skills`, `commands` и `agents`, а не через бесконечное разрастание глобальных правил.

## Профили

### `java-service`

Основной профиль для рабочих сервисов.

Он учитывает:
- Maven
- Spring Boot
- Hibernate / JPA
- Oracle и PostgreSQL как сервисные БД
- ClickHouse как аналитическое хранилище
- Kafka
- внутреннюю командную Java-конвенцию
- staging-based git flow

Этот профиль подходит для большинства боевых сервисов.

### `vue-app`

Профиль для Vue 3 + Vite фронтенда.

Покрывает:
- Composition API с `<script setup>`
- Pinia для state management
- Vue Router
- Vitest + Vue Test Utils
- TypeScript интеграция
- Vite конфигурация

### `go-service`

Упрощенный профиль для Go-проектов.

Он не тянет за собой enterprise Java-правила и оставляет только то, что полезно для:
- package boundaries
- `context.Context`
- error wrapping
- table-driven tests
- небольших HTTP/CLI приложений

### `docker-service`

Профиль для проектов, где основная работа — контейнеризация и оркестрация.

Покрывает:
- Dockerfile authoring и multi-stage builds
- Docker Compose — infra, networking, volumes, profiles
- локальный dev-воркфлоу с контейнерами
- отладку container runtime проблем

## Как Устроен Репозиторий

```text
my-claude-config/
  docs/
  rules/
  commands/
  agents/
  skills/
  hooks/
  templates/
  scripts/
```

Ниже кратко, зачем нужна каждая часть.

### `docs/`

Документация о самой системе конфигурации.

Здесь лежит:
- зачем так устроен репозиторий
- как встроена командная конвенция
- чем отличаются профили
- как публиковать этот репозиторий в GitHub

Читать это нужно не агенту, а тебе как владельцу системы.

### `rules/`

Короткие always-on правила.

Загружаются глобально: `setup-global.sh` генерирует `~/.claude/CLAUDE.md`, который через `@import`
подключает каждый файл `rules/*.md`. Так правила реально попадают в каждую сессию (и в субагентов).

Это слой, который должен быть:
- стабильным
- универсальным
- коротким
- безопасным

Сюда не стоит складывать все подряд.

Что здесь должно быть:
- как агент работает с контекстом
- как относится к рисковым изменениям
- что делать при неоднозначности
- как относиться к локальной конвенции проекта

Что сюда не нужно класть:
- длинные stack-specific playbooks
- подробные чеклисты review
- специфичные для одного проекта договоренности

### `commands/`

Повторяемые рабочие сценарии.

Это хороший слой, когда у задачи есть понятная последовательность шагов.

Примеры:
- планирование фичи
- review изменений
- планирование миграции
- Spring feature flow
- review интеграций

Команда нужна, когда ты хочешь, чтобы агент каждый раз проходил один и тот же процесс.

### `agents/`

Специализированные роли.

Нужны для задач, где фиксированного сценария мало и нужен judgment.

Примеры:
- `planner`
- `reviewer`
- `java-reviewer`
- `migration-reviewer`
- `prompt-auditor`

Агент нужен, когда задача требует:
- анализа trade-offs
- поиска рисков
- интерпретации конвенции
- более глубокого code review

### `skills/`

Основной модульный слой.

Сюда вынесены:
- знания о Java/Spring
- git flow
- JPA и БД
- Kafka и REST integrations
- Go profile
- meta-skills для проектирования агентов и аудита промптов

Почему это важно:
- skill загружается только тогда, когда реально нужен
- это экономит контекст
- это упрощает поддержку
- это не засоряет always-on слой

Именно сюда лучше всего добавлять новые стековые и доменные знания.

### `hooks/`

Легкие guardrails.

Они нужны не для того, чтобы управлять всей логикой агента, а чтобы ловить самые опасные действия:
- destructive commands
- force push
- другие простые и дорогие ошибки

Это последний слой защиты, а не основная система управления.

### `templates/`

Шаблоны для новых проектов.

Здесь лежат:
- шаблон `CLAUDE.md` под Java-сервис
- шаблон `CLAUDE.md` под Go-сервис
- профильные `settings.json`

Зачем это нужно:
- быстро поднимать новый проект
- не писать каждый раз руками структуру локального конфига
- стандартизировать стартовую точку

### `scripts/`

Служебные скрипты:
- `setup-global.sh` — установка конфига глобально в `~/.claude/` (dry-run по умолчанию, `--apply` для реального применения)
- `install-hooks.sh` — установка хуков в `~/.claude/settings.json` (вызывается из `setup-global.sh`)
- `analyze-usage.sh` — аналитика использования по логам в `~/.claude/logs/*.jsonl`

## Быстрый Старт

### На новой машине

```bash
git clone <repo-url> ~/dev/my-claude-config
cd ~/dev/my-claude-config
./scripts/setup-global.sh install          # dry-run: покажет что сделает
./scripts/setup-global.sh install --apply  # реально установит
```

После этого `skills/`, `agents/`, `commands/` доступны глобально во всех проектах.

### В новом проекте

```bash
cd /path/to/project
claude
> /onboard
```

Команда `/onboard` определит стек, задаст несколько вопросов и сгенерирует `CLAUDE.md`.

## Что Появится В Проекте

После `/onboard`:

```text
your-project/
  CLAUDE.md        ← единственный файл, нужный в проекте
```

### Зачем нужен локальный `CLAUDE.md`

Это самый важный файл конкретного проекта.

Именно сюда надо писать:
- что делает сервис
- какие у него границы ответственности
- какие команды запускать
- какие папки трогать нельзя
- какие есть локальные исключения из общей конвенции
- какие rollout или migration ограничения есть именно у этого сервиса

Глобальный репозиторий не должен знать такие вещи заранее.

## Как Этим Пользоваться Каждый День

Для Java-сервиса типовой режим такой:

1. Подключить конфиг в проект.
2. Заполнить локальный `CLAUDE.md`.
3. На нетривиальной задаче сначала использовать `plan` или `feature`.
4. Если затронуты БД или JPA, подключать `jpa-db-review`.
5. Если затронуты Kafka или REST integrations, подключать `integration-patterns`.
6. Перед финализацией изменений использовать `review`, `convention-check` или `java-reviewer`.

Для Go-проекта типовой режим проще:

1. Подключить профиль `go-service`.
2. Заполнить `CLAUDE.md`.
3. Для нетривиальной задачи сначала план.
4. Использовать skill `go-service` для реализации и review.

## Какие Skills Когда Использовать

### Для Java-сервисов

- `java-service-convention`
  Когда меняешь Spring Boot код, сервисы, контроллеры, конфиг, исключения, logging, JPA boundaries.

- `spring-best-practices`
  Когда работаешь со Spring Security, кэшированием, async, scheduling, @ConfigurationProperties, ProblemDetail, Actuator, Micrometer.

- `java-patterns`
  Когда проектируешь новые абстракции, выбираешь паттерн, рефакторишь к SOLID, работаешь с Optional/Stream/functional.

- `testing`
  Когда пишешь или ревьюишь тесты. Покрывает JUnit 5, Mockito, AssertJ, @WebMvcTest, @DataJpaTest, Testcontainers.

- `git-convention`
  Когда обсуждаются branch naming, commit messages, staging-flow, merge-порядок.

- `jpa-db-review`
  Когда меняются entities, repositories, SQL, индексы, схема, workload-sensitive куски, Oracle/PostgreSQL/ClickHouse.

- `integration-patterns`
  Когда меняются Kafka consumers/producers, REST clients, secrets, correlation IDs, logging интеграций.

### Для DevOps

- `gitlab-ci`
  Когда пишешь или правишь `.gitlab-ci.yml`, настраиваешь stages, caching, artifacts, environments, secrets.

- `kubernetes`
  Когда пишешь Deployment, Service, ConfigMap, Ingress, HPA, PDB манифесты. Включает resource limits, probes, rollout strategy.

- `helm`
  Когда создаёшь или меняешь Helm chart: structure, values, templates, hooks, multi-env overrides.

- `terraform`
  Когда пишешь Terraform: module structure, state, providers, variables, CI integration.

- `docker`
  Когда пишешь Dockerfile, Docker Compose, локальное dev-окружение, оптимизируешь образы.

### Для Vue/Vite

- `vue-frontend`
  Когда работаешь с Vue 3 + Vite фронтендом: компоненты, Pinia, Router, Vitest, TypeScript.

### Для Go

- `go-service`
  Когда работаешь с Go-сервисом или домашним проектом.

### Для мета-работы над самим конфигом

- `repo-onboarding`
- `agent-design`
- `prompt-audit`

## Как Добавлять Новые Части В Репозиторий

Ниже правило выбора слоя.

### Когда добавлять в `rules/`

Добавляй в `rules/`, только если правило:
- почти всегда актуально
- короткое
- стабильное
- реально влияет на качество или безопасность

Пример хорошего кандидата:
- "для нетривиальных задач сначала читать локальный `CLAUDE.md`"

Пример плохого кандидата:
- подробный playbook по Kafka consumers

### Когда добавлять в `commands/`

Добавляй в `commands/`, если:
- у задачи есть стабильный порядок шагов
- её приходится повторять снова и снова
- нужен предсказуемый output format

Примеры:
- migration plan
- Spring feature flow
- integration review

### Когда добавлять в `agents/`

Добавляй в `agents/`, если:
- нужен отдельный role mindset
- фиксированного workflow мало
- важны judgment и trade-offs

Примеры:
- reviewer под Java
- reviewer под DB/migrations
- prompt auditor

### Когда добавлять в `skills/`

Это основной способ расширения репозитория.

Добавляй в `skills/`, если:
- знание не должно быть always-on
- оно относится к конкретному стеку, домену или workflow
- его можно переиспользовать в нескольких проектах

Примеры:
- новый skill под `spring-api-contracts`
- skill под `clickhouse-analytics`
- skill под `oracle-postgres-migrations`

### Когда добавлять в `templates/`

Добавляй или меняй шаблоны, если:
- меняется стартовая структура локального `CLAUDE.md`
- нужен новый профиль
- нужны другие `settings.json` по типу проекта

### Когда добавлять в `hooks/`

Добавляй hook, только если:
- ошибка частая
- ошибка дорогая
- правило ловится надежно
- false positive будет редким

Не надо делать hooks для стилистических мелочей.

## Как Добавить Новый Skill

Минимальная структура:

```text
skills/my-new-skill/
  SKILL.md
```

Если skill большой, добавляй references:

```text
skills/my-new-skill/
  SKILL.md
  references/
    something.md
```

### Рекомендованный процесс

1. Определи, точно ли это skill, а не rule или command.
2. Дай узкое имя.
3. Напиши короткое `description`, чтобы skill правильно триггерился.
4. В `SKILL.md` оставь только workflow и guardrails.
5. Подробные материалы вынеси в `references/`.
6. Проверь, не дублирует ли skill уже существующие.
7. При необходимости обнови `README.md` и профильные docs.

### Что важно не делать

- не делать skill слишком широким
- не копировать туда полдокументации без необходимости
- не дублировать одни и те же инструкции в нескольких skills
- не тащить project-specific договоренности в общий skill

## Как Добавить Новую Command

Новая команда нужна, если хочется зафиксировать workflow.

Минимальный процесс:

1. Создать файл в `commands/`
2. Добавить короткий `description`
3. Описать, когда применять команду
4. Описать шаги
5. Описать ожидаемый формат результата

Хорошая команда должна вести агента по процессу, а не просто быть длинным куском текста.

## Как Добавить Нового Agent

Добавляй нового агента только если реально нужна новая роль.

Перед добавлением ответь на вопросы:
- какая у него зона ответственности
- чем он отличается от уже существующих
- какие tools ему действительно нужны
- где он должен остановиться и задать вопрос
- как выглядит успешный результат его работы

Если это неясно, скорее всего нужен не новый agent, а новый command или skill.

## Как Добавить Новое Правило

Перед тем как добавлять новый файл в `rules/`, проверь:
- правило относится почти ко всем проектам?
- оно короткое?
- оно устойчиво во времени?
- оно не должно жить в project `CLAUDE.md`?
- оно не лучше оформляется как skill?

Если хотя бы на один из этих вопросов ответ "нет", скорее всего это не `rule`.

## Как Развивать Репозиторий Без Хаоса

Рекомендуемый порядок роста:

1. Сначала доописывать `CLAUDE.md` конкретных проектов.
2. Потом выносить повторяемые знания в `skills`.
3. Потом фиксировать устойчивые процессы в `commands`.
4. Потом добавлять узких `agents`.
5. И только в самом конце расширять `rules`.

Это защищает от разрастания always-on слоя.

## С Чего Начать После Клонирования

1. Запустить `./scripts/setup-global.sh install --apply`
2. Открыть новый проект и выполнить `/onboard`
3. Заполнить локальный `CLAUDE.md`
4. Обкатать 2-3 типовых сценария
5. Посмотреть, каких skills или commands не хватает
6. Только потом расширять репозиторий
